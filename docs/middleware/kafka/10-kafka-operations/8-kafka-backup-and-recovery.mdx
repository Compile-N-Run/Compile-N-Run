# Backup and Recovery Strategies

## Introduction

"Kafka replicates everything three times, so we do not need backups." This is one of the most common beliefs about Kafka, and it is half true. Replication protects you against hardware: a disk dies, a broker crashes, an availability zone goes dark. It does nothing against the failures that destroy data on purpose or by mistake, because replication copies those too. If someone deletes a topic, all three replicas are deleted. If a buggy producer writes a million corrupt records, all three replicas store them faithfully.

Whether Kafka needs backups depends on what Kafka is in your architecture. If every topic can be rebuilt from an upstream database, Kafka is a pipe, and losing it costs time but not data. If Kafka is the system of record (an event-sourced ledger, a compacted topic holding the only copy of customer preferences), losing it means losing the business's data.

This page helps you decide which situation you are in, describes the main backup approaches and their trade-offs, and walks through restoring after the kinds of accidents that actually happen.

## What Can Go Wrong

List the failures before choosing tools. Each one needs a different kind of protection.

| Failure | Does replication help? | What does help |
|---|---|---|
| Disk or broker failure | Yes | RF 3, `min.insync.replicas=2` |
| Availability zone outage | Yes, with `broker.rack` across zones | Rack-aware placement |
| Region outage | No | A second cluster in another region (MirrorMaker 2, Cluster Linking) |
| Topic deleted by mistake | No, deletion replicates instantly | A copy outside the cluster, plus delete protection |
| Corrupt or bad records written | No | Point-in-time copies; ability to replay from a source of truth |
| Retention misconfigured, data expired | No | A copy with longer retention |
| Ransomware or compromised admin credentials | No | Immutable copies in a separate account |
| Cluster metadata lost or corrupted | Partly, through the controller quorum | Configuration as code; controller quorum across zones |

Two numbers from your business drive the design. The **recovery point objective (RPO)** is how much data you can afford to lose, measured in time. The **recovery time objective (RTO)** is how long you can be down. A clickstream might accept an RPO of hours; a payment ledger might accept seconds.

## Strategy 1: Rebuild From the Source

The cheapest backup is the one you do not need. If a topic is derived from somewhere else, you can recreate it:

- Topics fed by [Debezium CDC](../8-kafka-connect/5-kafka-connect-debezium-cdc.mdx) can be rebuilt by re-snapshotting the source database.
- Topics produced by a [Kafka Streams](../7-kafka-streams/0-kafka-streams-introduction.mdx) application can be regenerated by resetting the application and reprocessing its inputs.
- Topics fed by an [outbox table](../9-kafka-patterns/1-kafka-outbox-pattern.mdx) can be replayed if the outbox keeps history.

Classify every topic as **derived** or **source of truth**. Derived topics need a documented, tested rebuild procedure, not a backup. Only source-of-truth topics need the strategies below. In most organizations that is a short list.

## Strategy 2: Mirror to Another Cluster

[MirrorMaker 2](./5-kafka-mirrormaker.mdx) continuously copies topics, configs and consumer offsets to a second cluster. Managed alternatives include Confluent Cluster Linking and MSK Replicator. This gives the best RPO (typically seconds) and RTO (minutes, by repointing clients).

But a mirror is a hot standby, not a backup. A deleted topic is no longer replicated, and corrupt records are replicated within seconds. Mirroring protects against losing a cluster or a region; it does not let you go back in time.

## Strategy 3: Archive to Object Storage

For point-in-time recovery, copy records out of Kafka to object storage (Amazon S3, Google Cloud Storage, Azure Blob) with a Kafka Connect sink connector. Records land as files partitioned by topic, partition and time, and you can restore by replaying them back into Kafka with a source connector or a small program.

```json
{
  "name": "ledger-archive",
  "config": {
    "connector.class": "io.confluent.connect.s3.S3SinkConnector",
    "tasks.max": "4",
    "topics": "ledger.entries,customer.preferences",
    "s3.bucket.name": "acme-kafka-archive",
    "s3.region": "eu-west-1",
    "storage.class": "io.confluent.connect.s3.storage.S3Storage",
    "format.class": "io.confluent.connect.s3.format.avro.AvroFormat",
    "partitioner.class": "io.confluent.connect.storage.partitioner.TimeBasedPartitioner",
    "path.format": "'year'=YYYY/'month'=MM/'day'=dd/'hour'=HH",
    "partition.duration.ms": "3600000",
    "locale": "en-US",
    "timezone": "UTC",
    "flush.size": "10000",
    "rotate.interval.ms": "600000",
    "store.kafka.keys": "true",
    "store.kafka.headers": "true"
  }
}
```

Points to get right:

- **Keep keys and headers**, not just values. Compacted topics are meaningless without keys, and headers often carry tracing or schema information.
- **Keep the original offsets and timestamps** in the file names or record metadata, so you can map a restore back to a point in time.
- **Use a separate account with object lock** (S3 Object Lock or the equivalent) so a compromised Kafka admin cannot delete the archive.
- **Check the licence** of the connectors you choose. Confluent's S3 sink is under the Confluent Community License; alternatives such as the Aiven and Apache Camel connectors use the Apache License.

:::note
Tiered storage is not a backup. It moves older segments of a topic to object storage, but Kafka still owns them: delete the topic and Kafka deletes the remote segments too. Use it to cut storage cost, and use an archive connector for recovery.
:::

## Strategy 4: Disk Snapshots

Taking cloud volume snapshots of every broker is tempting because it needs no extra software. It is also the weakest option. Snapshots of different brokers are taken at slightly different moments, so partitions are captured at different offsets on different replicas; restoring them gives a cluster whose replicas disagree. A snapshot of a running broker also captures the active segment mid-write, so the broker must run log recovery on restore.

Snapshots are reasonable for one narrow case: quickly replacing a single broker's disk, where Kafka's replication fills in the gap after the restore. For whole-cluster recovery, prefer mirroring or archives.

## Protecting Metadata and Configuration

Data is only half of a Kafka cluster. Topic definitions, partition counts, configs, ACLs, quotas, SCRAM credentials and consumer group offsets all live in the KRaft metadata log and internal topics. Rebuilding a cluster without them is slow and error-prone.

The best protection is to **not treat the cluster as the source of truth for its configuration**. Define topics, ACLs and quotas as code, in Terraform, Strimzi `KafkaTopic` and `KafkaUser` resources, or a GitOps pipeline of your own. Then a new cluster can be configured from Git in minutes.

Also take a regular export of what is actually there, to catch drift:

```bash
#!/usr/bin/env bash
# Nightly export of cluster configuration to a dated folder (commit it to Git or upload to S3).
set -euo pipefail
BS=kafka-1.internal:9092
OUT=backup/$(date +%F)
mkdir -p "$OUT"

kafka-topics.sh --bootstrap-server "$BS" --describe > "$OUT/topics.txt"
kafka-configs.sh --bootstrap-server "$BS" --describe --all --entity-type topics > "$OUT/topic-configs.txt"
kafka-configs.sh --bootstrap-server "$BS" --describe --entity-type brokers --entity-default > "$OUT/broker-defaults.txt"
kafka-acls.sh --bootstrap-server "$BS" --list > "$OUT/acls.txt"
kafka-consumer-groups.sh --bootstrap-server "$BS" --describe --all-groups > "$OUT/group-offsets.txt"
```

For the metadata itself, the controller quorum is your replication: three or five controllers in different zones. Kafka also writes periodic metadata snapshots (`.checkpoint` files in the metadata log directory), which you can inspect read-only with `kafka-metadata-shell.sh` during an investigation.

## Guarding Against Accidents

Prevention is cheaper than recovery. A few settings remove whole classes of incidents:

- `auto.create.topics.enable=false`, so typos do not create stray topics.
- Restrict `DELETE` on topics with [ACLs](../11-kafka-security/3-kafka-acls-authorization.mdx) to an admin role; applications should never hold it.
- Require topic deletion to go through the same reviewed pipeline as creation (a pull request against the topic definitions).
- Set `unclean.leader.election.enable=false` (the default), so Kafka never elects an out-of-sync replica and silently drops acknowledged writes.
- Review `retention.ms` changes as carefully as code: lowering retention deletes data the next time the cleaner runs.

## A Worked Scenario: The Deleted Ledger Topic

A fintech company runs an event-sourced ledger: every account movement is a record in `ledger.entries` (48 partitions, infinite retention), and account balances are projections built from it. Kafka is the system of record. Their protections are a MirrorMaker 2 flow to a DR region, an S3 archive with object lock written by a sink connector every ten minutes, and topic definitions in Terraform.

On a Monday morning an engineer runs a cleanup script against production instead of staging, and `ledger.entries` is deleted. Within seconds MirrorMaker 2 stops replicating it, but the DR cluster's copy stays intact, because MM2 does not propagate topic deletions.

Recovery:

1. **Freeze writes.** Producers to the ledger are paused (the topic no longer exists, so they are already failing). Nothing new is being lost because the ledger service writes to an outbox table first.
2. **Pick the source.** The DR cluster's `ledger.entries` is complete up to the moment of deletion, minus about one second of replication lag. The S3 archive is complete to within ten minutes. DR is the better source.
3. **Recreate the topic** from Terraform with the same partition count, which matters because the ledger is keyed by account ID and each account must land in the same partition as before.
4. **Copy back.** A temporary MirrorMaker 2 flow from DR to primary with `IdentityReplicationPolicy` copies all records partition by partition, preserving keys, headers and timestamps. Offsets on the restored topic differ from the originals; consumers resume using translated offsets or by rebuilding projections from the start.
5. **Fill the gap.** The outbox relay replays the last minute of entries; consumers are idempotent on entry ID, so the overlap is harmless.
6. **Verify.** A reconciliation job compares record counts and a hash of entry IDs per partition between primary, DR and the S3 archive.

The ledger is back in 50 minutes with no lost entries. The follow-up: a new ACL so that only the Terraform pipeline's identity may delete topics, and a quarterly restore drill from the S3 archive, because the team realizes they have never actually tested that path.

## Common Mistakes

- Believing RF 3 is a backup. It protects against hardware, not against deletion, corruption or bad configuration.
- Treating a MirrorMaker 2 mirror as point-in-time backup; it replicates bad records within seconds.
- Relying on tiered storage as a backup, then losing the remote copy when the topic is deleted.
- Archiving only record values and losing keys, which makes compacted topics unrestorable.
- Recreating a keyed topic with a different partition count, breaking per-key ordering and co-partitioning.
- Never testing a restore, so the first attempt happens during a real incident.
- Giving application credentials permission to delete topics.

## Summary

- Replication protects against hardware failures; it does not protect against deletions, bad data or misconfiguration.
- Classify topics as derived (rebuild from source) or source of truth (needs protection), and set RPO and RTO for each.
- Mirror to another cluster for fast failover, and archive to object storage with immutability for point-in-time recovery.
- Disk snapshots and tiered storage are not whole-cluster backups.
- Keep topics, ACLs and quotas as code, export the live state regularly, and restrict who can delete topics.
- Practise restores on a schedule.
