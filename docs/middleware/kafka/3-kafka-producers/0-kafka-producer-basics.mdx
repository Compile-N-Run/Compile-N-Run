# Producer Basics: Sending Records

## Introduction

Everything in Kafka starts with a producer. A producer is the client library that takes a record from your application, decides which partition it belongs to, packs it into a batch and ships it to the broker that leads that partition. Consumers, Kafka Streams, Connect sources and ksqlDB all sit on top of this one piece of code.

This page shows how the producer works internally, how to configure one, and the three ways you can call `send()` and what each one promises. You will also see the same program in Java, Python, Node.js and Go so you can recognize the shared shape no matter which client you use. By the end you should be able to write a service that publishes events reliably and know exactly when a record is "safe".

We use one running example: an order service in an online shop that publishes an `OrderPlaced` event to an `orders` topic every time a customer checks out. The alternative would be calling the warehouse, billing and email services directly over HTTP; the producer lets the order service publish once and forget about who is listening.

## What a Producer Does Between send() and the Broker

Calling `send()` does not write to the network. It hands the record to a pipeline that runs in the background. Knowing the stages explains most of the producer's configuration keys.

```mermaid
flowchart LR
    A["Application calls send()"] --> B["Interceptors"]
    B --> C["Serializer: key and value to bytes"]
    C --> D["Partitioner: pick a partition"]
    D --> E["Record accumulator: one batch per partition"]
    E --> F["Sender thread: one request per broker"]
    F --> G["Broker: leader for the partition"]
    G --> H["Callback or Future completes"]
```

1. **Serialization** turns your key and value objects into byte arrays. Kafka brokers only ever see bytes; the serializer is where your data model and the wire format meet. See [Serializers and Record Headers](./5-kafka-producer-serialization.mdx).
2. **Partitioning** chooses which partition of the topic receives the record. If you set a partition explicitly it is used; if you set a key the key is hashed; otherwise the producer fills one partition at a time. See [Keys, Partitioners and Sticky Partitioning](./1-kafka-producer-keys-and-partitioners.mdx).
3. **Accumulation** appends the record to an in-memory batch for that partition. Batches are what cross the network, not single records. See [Batching, Linger and Compression](./4-kafka-producer-batching-and-compression.mdx).
4. **Sending** is done by a single background I/O thread (the "sender") that groups ready batches by destination broker, sends them, waits for acknowledgements and retries on transient failures. See [Producer Errors, Retries and Timeouts](./6-kafka-producer-errors-and-retries.mdx).
5. **Completion** happens when the broker answers. The producer completes the `Future` and runs your callback with a `RecordMetadata` (topic, partition, offset, timestamp) or an exception.

The important consequence: `send()` is asynchronous. It returns as soon as the record is in the accumulator. If your process crashes a millisecond later, the record is gone unless you waited for the acknowledgement.

## Creating a Producer

A producer needs three things: where the cluster is, how to turn keys into bytes and how to turn values into bytes. Everything else has a default.

```java
import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerConfig;
import org.apache.kafka.common.serialization.StringSerializer;

import java.util.Properties;

public class ProducerFactory {
    public static KafkaProducer<String, String> create() {
        Properties props = new Properties();
        // A list of a few brokers; the producer discovers the rest of the cluster from them.
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker-1:9092,broker-2:9092");
        // Shows up in broker logs, metrics and quotas. Always set it.
        props.put(ProducerConfig.CLIENT_ID_CONFIG, "order-service");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        return new KafkaProducer<>(props);
    }
}
```

The Java client is the dependency `org.apache.kafka:kafka-clients`. Its defaults are already production-minded since Kafka 3.0: `acks=all`, `enable.idempotence=true`, `retries` effectively unlimited and `delivery.timeout.ms=120000`. You do not have to turn durability on; you would have to turn it off.

| Setting | Default (Kafka 4.x) | What it controls |
|---|---|---|
| `bootstrap.servers` | none, required | Initial brokers to contact for cluster metadata |
| `key.serializer`, `value.serializer` | none, required | Classes that convert objects to bytes |
| `client.id` | empty string | Name used in logs, metrics and quotas |
| `acks` | `all` | How many replicas must store the record before it counts as sent |
| `enable.idempotence` | `true` | Broker drops duplicates created by producer retries |
| `linger.ms` | `5` | How long a batch may wait for more records |
| `batch.size` | `16384` | Upper bound in bytes for one partition batch |
| `delivery.timeout.ms` | `120000` | Total time budget for a record including retries |
| `max.block.ms` | `60000` | How long `send()` may block waiting for metadata or buffer space |

Two lifecycle rules matter more than any setting. First, a `KafkaProducer` is thread-safe and expensive to create: it owns a TCP connection per broker, a 32 MiB buffer and a background thread. Create one per application (or per distinct configuration), not one per request. Second, you must `close()` it. Closing flushes buffered records and releases the connections; forgetting it leaks threads and loses the tail of your data.

## Three Ways to Send

Every client offers the same three styles. They differ in what you learn about the result and when.

### Fire and Forget

```java
producer.send(new ProducerRecord<>("orders", "order-1001", orderJson));
```

You hand the record over and move on. The producer still retries transient failures in the background, so this is more reliable than it sounds, but you will never find out about a permanent failure such as a record that is too large or a topic you are not authorized to write to. Use it for data where occasional silent loss is acceptable: debug traces, sampled metrics, a clickstream where one lost page view does not matter.

### Synchronous Send

```java
RecordMetadata meta = producer.send(record).get();   // blocks until the broker acknowledges
System.out.printf("stored in %s-%d at offset %d%n", meta.topic(), meta.partition(), meta.offset());
```

Calling `get()` on the returned `Future` waits for the acknowledgement or throws the failure. It is the simplest way to be certain. The cost is throughput: the calling thread sends one record per round trip, so a 5 ms broker round trip caps that thread at about 200 records per second. For an order service that handles a few hundred checkouts per minute this is perfectly fine, and the simplicity is worth it. For a sensor fleet emitting 100,000 readings per second it is not.

### Asynchronous Send with a Callback

```java
producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        // Permanent failure after all retries. Log, count, maybe write to a dead-letter store.
        log.error("could not publish order {}", record.key(), exception);
        return;
    }
    log.debug("order {} stored at {}-{}@{}", record.key(),
        metadata.topic(), metadata.partition(), metadata.offset());
});
```

This keeps the pipeline full while still telling you the outcome of every record. Callbacks for the same partition run in the order the records were sent, and they run on the producer's single I/O thread. That last point is the one trap: anything slow inside the callback stalls every other record's delivery. Log, increment a counter, hand the work to an executor; do not call a database and never call `send()` recursively with a blocking `get()` or `flush()` inside a callback (since Kafka 4.1, `flush()` from a callback throws, per KIP-1118).

| Style | You learn about failures | Throughput | Typical use |
|---|---|---|---|
| Fire and forget | Never | Highest | Low-value, high-volume telemetry |
| Synchronous | Immediately, in the calling thread | Lowest | Low volume where simplicity wins, tests |
| Asynchronous callback | Later, on the I/O thread | High | Most production services |

## The Same Program in Four Languages

The producer API is remarkably similar across clients because most of them either wrap `librdkafka` (the C library behind `confluent-kafka` for Python and `@confluentinc/kafka-javascript` for Node) or re-implement the Java design closely (`franz-go`).

### Python with confluent-kafka

```python
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092",
    "client.id": "order-service",
})

def on_delivery(err, msg):
    if err is not None:
        print(f"send failed for key {msg.key()}: {err}")
    else:
        print(f"stored in {msg.topic()}-{msg.partition()} at offset {msg.offset()}")

producer.produce(
    "orders",
    key="order-1001",
    value='{"orderId": "1001", "total": 42.5}',
    on_delivery=on_delivery,
)
producer.poll(0)      # run delivery callbacks that are already due; call this regularly
producer.flush()      # block until every queued record is acknowledged or failed
```

The one difference to remember: `librdkafka` runs callbacks only when you call `poll()` or `flush()`. A loop that calls `produce()` a million times without `poll()` will eventually raise `BufferError` because the queue is full and no delivery reports have been drained.

### Node.js with @confluentinc/kafka-javascript

```javascript
const { Kafka } = require('@confluentinc/kafka-javascript').KafkaJS;

const kafka = new Kafka({ 'bootstrap.servers': 'localhost:9092', 'client.id': 'order-service' });
const producer = kafka.producer();

async function main() {
  await producer.connect();
  // send() resolves when the broker has acknowledged every message in the call.
  const result = await producer.send({
    topic: 'orders',
    messages: [{ key: 'order-1001', value: JSON.stringify({ orderId: '1001', total: 42.5 }) }],
  });
  console.log(result); // [{ topicName: 'orders', partition: 0, baseOffset: '17', ... }]
  await producer.disconnect();
}

main().catch(console.error);
```

The API mirrors KafkaJS on purpose so code can be migrated with a one-line import change. KafkaJS itself still works but has seen little development since 2024, which is why the Confluent client is the usual choice for new projects.

### Go with franz-go

```go
package main

import (
	"context"
	"fmt"

	"github.com/twmb/franz-go/pkg/kgo"
)

func main() {
	client, err := kgo.NewClient(
		kgo.SeedBrokers("localhost:9092"),
		kgo.ClientID("order-service"),
	)
	if err != nil {
		panic(err)
	}
	defer client.Close()

	record := &kgo.Record{
		Topic: "orders",
		Key:   []byte("order-1001"),
		Value: []byte(`{"orderId":"1001","total":42.5}`),
	}
	// ProduceSync blocks until acknowledged. Produce(ctx, record, callback) is the async form.
	results := client.ProduceSync(context.Background(), record)
	if err := results.FirstErr(); err != nil {
		fmt.Println("send failed:", err)
		return
	}
	r := results[0].Record
	fmt.Printf("stored in %s-%d at offset %d\n", r.Topic, r.Partition, r.Offset)
}
```

## Flush and Close

`flush()` blocks until every record handed to the producer so far has been acknowledged or has failed for good. It does not stop the producer; you can keep sending afterwards. Use it at natural checkpoints: the end of a batch job, before committing a database transaction that assumes the event is out, or before replying to an HTTP request when the caller must be sure the event exists.

`close()` does a final flush and then releases resources. `close(Duration)` bounds the wait; records still unsent when the timeout expires fail with a `TimeoutException`. In a long-running service, register close on shutdown (a JVM shutdown hook, a SIGTERM handler in Python or Go) so a deploy does not drop the last few seconds of events.

:::tip
Calling `flush()` after every single `send()` turns the asynchronous producer into a synchronous one with extra steps. If you need per-record confirmation, use the synchronous `get()` or the callback instead, and reserve `flush()` for checkpoints.
:::

## Worked Scenario: The Order Service

The order service receives a checkout, writes the order to its own database and must tell the rest of the company. Three teams consume `orders`: the warehouse reserves stock, billing charges the card, and the notification service emails the customer.

Requirements shape the choice of send style:

- Losing an `OrderPlaced` event means a customer pays and never receives goods. Fire and forget is out.
- The checkout endpoint has a latency budget of 300 ms, so one synchronous send (a few milliseconds) is affordable. Volume is a few hundred per minute, so synchronous throughput is not a concern either.
- The order must exist in the database before the event is published, otherwise billing might charge for an order the database never stored.

```java
public void placeOrder(Order order) {
    orderRepository.save(order);                       // 1. durable in our own database
    ProducerRecord<String, String> record =
        new ProducerRecord<>("orders", order.id(), toJson(order));
    try {
        RecordMetadata meta = producer.send(record).get(5, TimeUnit.SECONDS);   // 2. wait for acks
        log.info("published order {} to {}-{}", order.id(), meta.partition(), meta.offset());
    } catch (ExecutionException | TimeoutException e) {
        // The order is saved but not announced. Mark it for a retry sweep instead of failing checkout.
        orderRepository.markUnpublished(order.id());
        log.warn("order {} saved but not yet published", order.id(), e);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException(e);
    }
}
```

Note what the code does when the send fails: it does not roll back the order and it does not loop forever. The database row carries a flag that a background job uses to republish. This "save, then publish, then reconcile" approach is a lightweight version of the [transactional outbox pattern](../9-kafka-patterns/1-kafka-outbox-pattern.mdx), which removes the window entirely by having the publisher read from the database table.

Why a key? `order.id()` as the key sends every event about a given order to the same partition, so a later `OrderCancelled` event cannot overtake its own `OrderPlaced`. The warehouse consumer relies on that order.

Run it locally against the cluster from [Running Kafka Locally with Docker Compose](../1-kafka-getting-started/0-kafka-docker-compose.mdx) and check the result with the console consumer:

```bash
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --from-beginning \
  --property print.key=true --property print.offset=true
```

```text
Offset:0	order-1001	{"orderId":"1001","total":42.5}
```

## Common Mistakes

- **Creating a producer per request.** Each instance opens connections and allocates a 32 MiB buffer; a web server doing this falls over under modest load. Share one instance.
- **Exiting without `close()` or `flush()`.** The last records sit in the accumulator and vanish with the process. Short scripts are the usual victim.
- **Assuming `send()` returning means the record is stored.** It only means the record is buffered. Use the `Future` or the callback for certainty.
- **Blocking inside a callback.** The callback runs on the one I/O thread; a slow database call there stalls every partition.
- **Catching the exception from `send()` but not from the `Future` or callback.** Most failures (broker down, record too large, topic missing) surface asynchronously.
- **Not setting `client.id`.** When a producer floods a cluster, operators see an anonymous client in the metrics and have no idea which service to call.
- **Never calling `poll()` in librdkafka-based clients.** Delivery callbacks do not run and the local queue fills up.

## Summary

- A producer serializes, partitions, batches and sends records on a background thread; `send()` returns before anything reaches the network.
- Fire-and-forget, synchronous `get()` and asynchronous callbacks trade certainty against throughput; most services use callbacks, low-volume services can use synchronous sends.
- Defaults since Kafka 3.0 (`acks=all`, idempotence on, generous retries) make the producer durable out of the box.
- Share one producer per application, keep callbacks fast, and always `flush()` or `close()` before exiting.
- Python, Node and Go clients follow the same model; librdkafka-based clients additionally need regular `poll()` calls.
