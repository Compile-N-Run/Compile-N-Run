# Managing Secrets and Client Credentials

## Introduction

A secured Kafka setup is full of secrets: keystore and key passwords, SCRAM passwords, OAuth client secrets, delegation token keys, and the private keys themselves. In many real clusters these end up pasted into `server.properties`, committed to Git, baked into container images and printed into CI logs. At that point the TLS and SASL work on the previous pages protects very little.

This page is about the less glamorous half of security: where secrets live, how they reach brokers and clients, and how to replace them without an outage. After reading it you will be able to:

- keep secrets out of property files using Kafka's config providers;
- deliver credentials to clients on Kubernetes and from HashiCorp Vault;
- rotate SCRAM passwords, OAuth client secrets and certificates without downtime;
- decide when delegation tokens or short-lived credentials are worth the effort.

## Where Secrets Hide in a Kafka Deployment

| Secret | Where it is used | Typical risk |
| --- | --- | --- |
| Keystore and key passwords | `ssl.keystore.password`, `ssl.key.password` on every node and mTLS client | Plain text in `server.properties` |
| TLS private keys | Keystore or PEM files | Copied around by hand, never rotated |
| SCRAM passwords | `sasl.jaas.config` on clients | Committed in application config, shared between services |
| OAuth client secrets | `clientSecret` in client JAAS config | Long-lived, same secret in every environment |
| Delegation token secret | `delegation.token.secret.key` on brokers and controllers | Stored in plain text in `server.properties` |
| Connector credentials | Kafka Connect connector configs (database passwords) | Visible to anyone with access to the Connect REST API |

Kafka helps a little by default: when it logs its configuration at startup, it masks values of password-type settings as `[hidden]`. But it cannot protect a file that anyone on the host can read, or a repository that every developer can clone.

## Config Providers: Indirection for Secrets

A config provider lets a property value be a *reference* that Kafka resolves at startup, instead of the secret itself. The syntax is `${provider:path:key}`. Kafka ships three providers:

| Provider class | Reference syntax | Resolves to |
| --- | --- | --- |
| `org.apache.kafka.common.config.provider.FileConfigProvider` | `${file:/etc/kafka/secrets.properties:keystore.password}` | A key in a properties file |
| `org.apache.kafka.common.config.provider.DirectoryConfigProvider` | `${directory:/var/run/secrets/kafka:keystore-password}` | The contents of one file in a directory (ideal for Kubernetes Secret volumes) |
| `org.apache.kafka.common.config.provider.EnvVarConfigProvider` | `${env:KEYSTORE_PASSWORD}` | An environment variable |

Providers work in broker, controller, client and Kafka Connect configuration. A broker using a mounted secrets directory:

```properties
# Register the provider under the alias "secrets"
config.providers=secrets
config.providers.secrets.class=org.apache.kafka.common.config.provider.DirectoryConfigProvider
# Restrict which paths the provider may read (Kafka 3.8+)
config.providers.secrets.param.allowed.paths=/var/run/secrets/kafka

ssl.keystore.location=/var/run/secrets/kafka/keystore.p12
ssl.keystore.password=${secrets:/var/run/secrets/kafka:keystore-password}
ssl.key.password=${secrets:/var/run/secrets/kafka:key-password}
ssl.truststore.location=/var/run/secrets/kafka/truststore.p12
ssl.truststore.password=${secrets:/var/run/secrets/kafka:truststore-password}
```

The property file can now live in Git and be reviewed like any other configuration, while the secrets come from a separate, access-controlled place. A Java client works the same way:

```properties
config.providers=env
config.providers.env.class=org.apache.kafka.common.config.provider.EnvVarConfigProvider

security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-512
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="payments-writer" password="${env:KAFKA_PASSWORD}";
```

Non-Java clients such as `confluent-kafka` (Python), `@confluentinc/kafka-javascript` and `franz-go` do not have config providers. Read the secret from the environment or a file in application code and pass it into the config dictionary, as the Python examples on the [SASL page](./2-kafka-sasl-authentication.mdx) do.

:::warning
Config providers are powerful: anyone who can submit configuration can ask Kafka to read files or environment variables. On a Kafka Connect cluster where users submit connector configs through the REST API, that could expose arbitrary files on the worker. Restrict providers with `allowed.paths`, or disable automatic providers entirely with the JVM property `-Dorg.apache.kafka.automatic.config.providers=none`, and secure the Connect REST API.
:::

## Delivering Secrets on Kubernetes and from Vault

On Kubernetes, the usual path is a Secret mounted as a volume, read through `DirectoryConfigProvider`. Mounted Secrets update in place when the Secret changes, while environment variables only change when the pod restarts, which matters for rotation.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: payments-writer-kafka
type: Opaque
stringData:
  password: "generated-by-provisioning-pipeline"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-service
  template:
    metadata:
      labels:
        app: payments-service
    spec:
      containers:
        - name: app
          image: registry.example.com/payments-service:1.14.2
          env:
            - name: KAFKA_USERNAME
              value: payments-writer
          volumeMounts:
            - name: kafka-credentials
              mountPath: /var/run/secrets/kafka
              readOnly: true
      volumes:
        - name: kafka-credentials
          secret:
            secretName: payments-writer-kafka
```

If you run Kafka on Kubernetes with Strimzi, its User Operator creates SCRAM users or mTLS certificates from a `KafkaUser` resource and writes the credentials into a Secret automatically. See [Kafka on Kubernetes with Strimzi](../10-kafka-operations/6-kafka-kubernetes-strimzi.mdx).

With HashiCorp Vault, two patterns are common:

- **Vault Agent or the Vault Secrets Operator** writes secrets into files or Kubernetes Secrets, and Kafka reads them through `DirectoryConfigProvider` or `FileConfigProvider`. Kafka needs no Vault-specific code.
- **A Vault config provider** (third-party implementations exist) resolves `${vault:...}` references directly. This avoids secrets on disk, but adds a dependency in every client.

Vault's PKI engine is also a convenient source of short-lived TLS certificates for brokers and clients.

## Rotating Credentials Without Downtime

Every credential will need replacing: a laptop is stolen, an engineer leaves, an auditor asks. Plan rotation before you need it.

### SCRAM Passwords

A SCRAM user has one credential per mechanism, so changing a password immediately breaks every client still using the old one. Two safe approaches:

1. **Two mechanisms.** Clients use SCRAM-SHA-512. Add the new password under SCRAM-SHA-256 for the same user, move clients to SCRAM-SHA-256 with the new password, then replace the SCRAM-SHA-512 credential. This works but is easy to confuse.
2. **Two users (recommended).** Create `payments-writer-v2` with the new password and the same ACLs and quotas, roll the application over, then delete `payments-writer`. ACLs and quotas are easier to duplicate if they are managed as code.

```bash
BS="--bootstrap-server kafka-1.example.com:9094 --command-config admin.properties"

kafka-configs.sh $BS --alter --entity-type users --entity-name payments-writer-v2 \
  --add-config "SCRAM-SHA-512=[password=$(openssl rand -base64 32)]"

# ...copy ACLs and quotas, deploy the app with the new user, then:
kafka-configs.sh $BS --alter --entity-type users --entity-name payments-writer \
  --delete-config SCRAM-SHA-512
```

Existing connections stay authenticated after the old user is deleted, unless `connections.max.reauth.ms` is set on the brokers. Set it, so that removing a credential actually removes access.

### OAuth Client Secrets

Most identity providers allow two active secrets per client. Add a second secret, deploy clients with it, then revoke the first. Because access tokens live only minutes, revocation takes effect quickly. Even better, use the identity provider's support for certificate-based client authentication or workload identity, so there is no shared secret at all.

### TLS Certificates

Use short lifetimes and automate renewal with cert-manager, Vault or your cloud PKI. Brokers reload keystores dynamically with `kafka-configs.sh`, as shown in [TLS Encryption in Transit](./1-kafka-tls-encryption.mdx). Java clients load their keystore at startup, so plan for a rolling restart of clients when their certificate renews, or use a certificate lifetime longer than your deployment cadence.

## Delegation Tokens for Distributed Jobs

Some workloads spawn many short-lived workers, such as Spark or Flink jobs. Distributing the job owner's main credential to every worker widens the exposure. Delegation tokens solve this: the driver authenticates once, asks the cluster for a token, and gives workers the token instead. Tokens expire (by default after 24 hours unless renewed, and after 7 days at most) and can be revoked.

On KRaft clusters, delegation tokens need `delegation.token.secret.key` set to the same value on all brokers and controllers, and SCRAM enabled on the listener, because token authentication is carried over SCRAM.

```bash
# Create a token valid for 2 hours that the "spark-jobs" user can renew
kafka-delegation-tokens.sh --bootstrap-server kafka-1.example.com:9094 \
  --command-config admin.properties --create \
  --max-life-time-period 7200000 --renewer-principal User:spark-jobs
```

A worker then authenticates with SCRAM using the token ID as username, the token HMAC as password, and `tokenauth="true"` in its JAAS config.

## A Worked Scenario: Cleaning Up After a Leak

A developer at an insurance company accidentally pushed a branch containing `application-prod.properties` to a public GitHub repository. The file held the SCRAM password for `claims-service` and the keystore password for its mTLS certificate. A secret scanner flagged it within ten minutes.

Because the team had followed the practices above, the response was routine:

1. Created `claims-service-v2` with a new random password; ACLs and quotas were applied from the Git-managed definitions in one CI run.
2. Updated the Kubernetes Secret through their provisioning pipeline; pods picked up the new mounted file and were restarted in a rolling deploy.
3. Deleted the `claims-service` SCRAM credential. With `connections.max.reauth.ms=3600000`, any attacker connection would have ended within an hour; the authorizer log showed none.
4. Revoked and reissued the client certificate from Vault, since the keystore password alone is worthless without the keystore file, but the policy was to rotate everything in a leaked file.

The alternative they had before, a single shared `apps` SCRAM user for all services, would have meant rotating credentials for forty services at once. Moving to one principal per application a year earlier turned a company-wide incident into a one-hour task for one team.

## Common Mistakes

- Committing `server.properties` or client configs with real passwords to Git, including "temporary" test clusters that later become production.
- Baking credentials into container images, where anyone who can pull the image can read them.
- Passing secrets on the command line (for example `--add-config` with a literal password in shell history or CI logs) without cleaning up.
- Sharing one SCRAM user or OAuth client across many services, making rotation a company-wide event.
- Never setting `connections.max.reauth.ms`, so deleted credentials keep working on existing connections.
- Leaving config providers unrestricted on a Kafka Connect cluster that accepts connector configs from many users.

## Summary

- Secrets in Kafka include keystore passwords, private keys, SCRAM passwords, OAuth client secrets and delegation token keys.
- Config providers (`FileConfigProvider`, `DirectoryConfigProvider`, `EnvVarConfigProvider`) let property files reference secrets instead of containing them.
- On Kubernetes, mount Secrets as files and read them with `DirectoryConfigProvider`; Strimzi and Vault can generate credentials for you.
- Rotate SCRAM credentials by creating a new user, OAuth secrets by overlapping two secrets, and certificates through automated short lifetimes.
- Set `connections.max.reauth.ms` so revoked credentials stop working promptly.
- Use delegation tokens to avoid spreading long-lived credentials across distributed jobs.
