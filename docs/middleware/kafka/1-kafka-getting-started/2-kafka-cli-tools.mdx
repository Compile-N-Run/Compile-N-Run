# The Kafka CLI Tools

## Introduction

Every Kafka installation ships with a folder of shell scripts in `bin/`. They look old-fashioned next to a web UI, but they are the tools you will reach for at 3 a.m. when a consumer group stops moving: they work over SSH, they work inside a container, they never need a browser, and they talk to the cluster through the same public APIs your applications use.

This page is a guided tour of the scripts you will use in the first months: `kafka-topics.sh`, the console producer and consumer, `kafka-consumer-groups.sh`, `kafka-configs.sh`, `kafka-get-offsets.sh` and the KRaft-specific `kafka-metadata-quorum.sh`. By the end you will know the handful of flags every tool shares, how to point them at a secured cluster, how to read their output, and which ones can change data so you treat them with care.

All examples assume a broker on `localhost:9092`, such as the one from the [Docker Compose page](./0-kafka-docker-compose.mdx). If your broker runs in Docker and you have not installed the binaries locally, prefix each command with `docker compose exec kafka /opt/kafka/bin/`; the [binary installation page](./1-kafka-local-installation.mdx) shows how to get the scripts on your own `PATH`.

## How the Tools Are Built

Each `kafka-*.sh` script is a short wrapper that calls `kafka-run-class.sh` with a Java class name. That shared launcher builds the classpath from `libs/`, picks up `KAFKA_HEAP_OPTS` and `KAFKA_OPTS`, and starts a small JVM. Two consequences follow.

First, every tool starts a JVM, so each command takes a second or two even when the answer is tiny. If you script dozens of calls in a loop, that adds up; the [Admin API](../2-kafka-topics-and-storage/6-kafka-admin-api.mdx) is the better choice for automation at scale.

Second, the tools share an argument style. Nearly all of them accept:

| Flag | Meaning |
|---|---|
| `--bootstrap-server host:port` | Any one or more brokers to start from; the tool discovers the rest |
| `--command-config file` | A client properties file for TLS, SASL or timeouts |
| `--help` | The full option list for that tool and version |
| `--version` | The Kafka version of the tool itself |

Older tutorials use `--zookeeper` or `--broker-list`. Both are gone: ZooKeeper was removed in Kafka 4.0, and every tool now speaks to brokers only through `--bootstrap-server`. Kafka 4.2 also tidied up the console tools' option names, so `--producer.config`, `--consumer.config` and `--property` now print deprecation warnings; their replacements are `--command-config`, `--reader-property` and `--formatter-property`, used throughout this page.

Think of the tools as a Swiss Army knife sorted by blade:

| Job | Script |
|---|---|
| Topics: create, list, describe, add partitions, delete | `kafka-topics.sh` |
| Send and read records by hand | `kafka-console-producer.sh`, `kafka-console-consumer.sh` |
| Consumer groups: lag, members, offset resets | `kafka-consumer-groups.sh`, `kafka-groups.sh` |
| Dynamic configuration of topics, brokers, clients | `kafka-configs.sh` |
| Offsets by time or position | `kafka-get-offsets.sh` |
| KRaft controller quorum health | `kafka-metadata-quorum.sh` |
| Feature versions and upgrades | `kafka-features.sh` |
| Look inside segment files | `kafka-dump-log.sh` |
| Load testing | `kafka-producer-perf-test.sh`, `kafka-consumer-perf-test.sh` |

## Topics with kafka-topics.sh

Create a topic for order events with three partitions:

```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 1
```

```
Created topic orders.
```

In scripts, add `--if-not-exists` so a second run does not fail. List and describe:

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --list
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
```

```
Topic: orders	TopicId: Qm2v9cPpRWeT1x3c8bYfQw	PartitionCount: 3	ReplicationFactor: 1	Configs:
	Topic: orders	Partition: 0	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
	Topic: orders	Partition: 1	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
	Topic: orders	Partition: 2	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
```

Read the describe output column by column: `Leader` is the broker that serves reads and writes for that partition, `Replicas` are all brokers holding a copy, and `Isr` is the subset currently in sync. `Elr` lists eligible leader replicas, a newer safety mechanism covered in the [replication page](../2-kafka-topics-and-storage/2-kafka-replication.mdx). On a healthy cluster `Replicas` and `Isr` match. On a real cluster the most useful describe variants are filters:

```bash
# Partitions whose ISR is smaller than the replica list: something is lagging or down
kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions

# Partitions with no leader at all: producers and consumers are blocked on these
kafka-topics.sh --bootstrap-server localhost:9092 --describe --unavailable-partitions
```

You can increase the partition count later with `--alter --partitions 6`, but never decrease it, and adding partitions changes which partition each key maps to. Deleting a topic (`--delete --topic orders`) is immediate and permanent; there is no recycle bin.

## Producing and Consuming from the Terminal

The console producer reads lines from standard input and sends each one as a record. Plain values are fine for a smoke test, but real topics are keyed, so learn the keyed form straight away:

```bash
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --reader-property parse.key=true --reader-property key.separator=:
```

```
>cust-42:{"orderId":"o-1001","amount":25.00}
>cust-7:{"orderId":"o-1002","amount":9.50}
>cust-42:{"orderId":"o-1003","amount":12.75}
```

Everything before the first `:` becomes the key. Press `Ctrl-D` to finish. To send a file of prepared records, redirect it: `kafka-console-producer.sh ... < orders.txt`.

The console consumer prints records as they arrive. By default it starts at the end of the topic, so add `--from-beginning` to see what is already there, and ask the formatter to show the metadata that matters:

```bash
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning \
  --formatter-property print.key=true \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true
```

```
Partition:1	Offset:0	cust-42	{"orderId":"o-1001","amount":25.00}
Partition:1	Offset:1	cust-42	{"orderId":"o-1003","amount":12.75}
Partition:2	Offset:0	cust-7	{"orderId":"o-1002","amount":9.50}
```

Both `cust-42` orders landed in the same partition, in the order they were sent. That is the key-based ordering guarantee you will rely on throughout this tutorial. Records from different partitions may be printed interleaved in any order.

Without `--group`, the console consumer joins a throwaway group with a random name and does not leave useful committed offsets behind. With `--group order-audit`, it behaves exactly like an application consumer: it commits offsets, and a second run resumes where the first stopped. Add `--max-messages 10` to exit after a fixed number of records, which is handy in scripts.

## Consumer Groups and Lag

`kafka-consumer-groups.sh` answers the question you will ask most often in production: is my consumer keeping up?

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-audit
```

```
GROUP        TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID                      HOST         CLIENT-ID
order-audit  orders  0          0               0               0    console-consumer-1c7b...  /172.18.0.1  console-consumer
order-audit  orders  1          2               2               0    console-consumer-1c7b...  /172.18.0.1  console-consumer
order-audit  orders  2          1               1               0    console-consumer-1c7b...  /172.18.0.1  console-consumer
```

`CURRENT-OFFSET` is the group's last committed position, `LOG-END-OFFSET` is where the partition currently ends, and `LAG` is the difference: records written but not yet processed. A lag that rises and falls is normal; a lag that only rises means the consumers are too slow, stuck, or gone. Add `--members` to see which instance owns which partitions, or `--state` to see whether the group is `Stable` or rebalancing. The [consumer lag page](../10-kafka-operations/2-kafka-consumer-lag.mdx) goes deeper.

The same tool can move a group's offsets, for example to reprocess yesterday's orders after a bug fix. This is the most dangerous everyday command, so it is built to be safe: without `--execute` it only prints the plan.

```bash
# 1. Dry run (the default): show where each partition would move
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group order-audit \
  --topic orders --reset-offsets --to-datetime 2026-10-16T00:00:00.000

# 2. Apply it; the group must have no active members
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group order-audit \
  --topic orders --reset-offsets --to-datetime 2026-10-16T00:00:00.000 --execute
```

Other targets are `--to-earliest`, `--to-latest`, `--to-offset 500`, `--shift-by -100` and `--by-duration PT2H`. Kafka refuses the reset while consumers in the group are running, because they would overwrite the new offsets with their own commits a moment later. Stop the application first.

`kafka-groups.sh --list` shows every kind of group the cluster knows about, including classic consumer groups, groups using the newer rebalance protocol, share groups and Kafka Streams groups.

## Configuration and Offsets

`kafka-configs.sh` changes settings without restarting anything. Topic overrides are the common case:

```bash
# Keep order events for 30 days instead of the 7-day default
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name orders \
  --alter --add-config retention.ms=2592000000

# Show only the overrides on this topic
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name orders --describe
```

```
Completed updating config for topic orders.
Dynamic configs for topic orders are:
  retention.ms=2592000000 sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=2592000000}
```

Add `--all` to `--describe` to see every effective value with its source. `--delete-config retention.ms` removes the override so the topic falls back to the broker default. The same tool manages broker settings (`--entity-type brokers`), client quotas and SCRAM users; the [configuration page](./4-kafka-configuration-basics.mdx) explains which broker settings can change at runtime.

`kafka-get-offsets.sh` reports partition offsets without joining a group:

```bash
kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic orders --time latest
```

```
orders:0:0
orders:1:2
orders:2:1
```

`--time earliest` gives the first offset still retained, and a millisecond timestamp gives the first offset at or after that moment, which is how you check what a time-based reset would do.

## Connecting to a Secured Cluster

Real clusters require TLS and authentication. Put the client settings in a file once and pass it to any tool with `--command-config`:

```properties
# client.properties
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-512
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="ops-alice" password="change-me";
ssl.truststore.location=/etc/kafka/certs/truststore.p12
ssl.truststore.password=change-me
```

```bash
kafka-topics.sh --bootstrap-server kafka-1.prod.internal:9093 \
  --command-config client.properties --list
```

The console producer and consumer take the same file through `--command-config`. Keep that file out of version control and readable only by you; it holds a password. The [security section](../11-kafka-security/0-kafka-security-overview.mdx) covers the mechanisms themselves.

:::warning
Commands that change state (`--delete`, `--alter`, `--reset-offsets --execute`, `kafka-delete-records.sh`, `kafka-configs.sh --alter`) take effect immediately and cluster-wide. On production, run the read-only form first, paste the output into your change ticket, and only then run the mutating form.
:::

## KRaft Health with kafka-metadata-quorum.sh

Kafka 4.x has no ZooKeeper to inspect. Instead, the controllers form a Raft quorum, and this tool shows its state:

```bash
kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

```
ClusterId:              MkU3OEVBNTcwNTJENDM2Qk
LeaderId:               1
LeaderEpoch:            1
HighWatermark:          1874
MaxFollowerLag:         0
MaxFollowerLagTimeMs:   0
CurrentVoters:          [{"id": 1, "directoryId": "...", "endpoints": ["CONTROLLER://kafka:29093"]}]
CurrentObservers:       []
```

`LeaderId` is the active controller. `describe --replication` lists every voter and observer with how far behind the leader's log it is; a controller or broker whose lag keeps growing has a problem. Run this first whenever brokers cannot register or topic creation hangs.

## Worked Scenario: The Payments Consumer Has Stopped

A payment service reads `payments.authorized` and writes ledger entries. At 09:10 the dashboard shows the ledger is twenty minutes behind. The on-call engineer has SSH access to a bastion host with the Kafka binaries, and no UI. The CLI was chosen over a web console for this runbook because it works through the bastion, leaves an exact command history in the ticket, and needs no extra service to be up.

1. `kafka-consumer-groups.sh --describe --group ledger-writer` shows lag of 180,000 on partition 4 and near zero everywhere else. One partition, not the whole group, so the problem is a specific record or a specific instance.
2. `--describe --members` shows partition 4 assigned to `ledger-writer-7`. Its application logs show a deserialization exception repeating on the same offset: a poison record.
3. `kafka-console-consumer.sh --partition 4 --offset 9182231 --max-messages 1` prints the record. It has an amount field encoded as a string by a producer deployed that morning.
4. The team fixes the consumer to tolerate the format, deploys, and the lag drains. They chose not to skip the record with `--reset-offsets --shift-by 1`, because this is money and skipping it would leave a hole in the ledger.

Each step was read-only until the deploy. That is the habit worth building.

## Common Mistakes

- Copying commands with `--zookeeper` or `--broker-list` from old tutorials. Use `--bootstrap-server`; the old flags no longer exist in 4.x.
- Running the console consumer without `--from-beginning` and concluding the topic is empty.
- Testing with unkeyed console records and then being surprised that ordering differs from production, where records have keys.
- Resetting offsets while the application is still running. The reset is rejected, or the running consumers overwrite it.
- Forgetting `--execute` and believing a reset happened. The default is a dry run.
- Passing the bootstrap address of the wrong listener, for example `kafka:19092` from your host. The tool connects, fetches metadata, then times out against unreachable advertised addresses.
- Treating `--alter --partitions` as harmless. It is irreversible and remaps keys to partitions.

## Summary

- Every script in `bin/` is a thin wrapper around a Java class; they share `--bootstrap-server`, `--command-config` and `--help`.
- `kafka-topics.sh` creates and inspects topics; `--under-replicated-partitions` and `--unavailable-partitions` are the health checks.
- The console producer and consumer are for smoke tests and debugging; use keys and print partition and offset to see what is really happening.
- `kafka-consumer-groups.sh --describe` shows lag; `--reset-offsets` is a dry run until you add `--execute`, and needs the group stopped.
- `kafka-configs.sh` changes topic and broker settings live; `kafka-metadata-quorum.sh` replaces the ZooKeeper checks of older versions.
- On production, run the read-only form of a command before the mutating one.
