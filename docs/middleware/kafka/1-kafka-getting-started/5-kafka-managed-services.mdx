# Managed Kafka: Confluent Cloud, Amazon MSK, Azure Event Hubs and Redpanda

## Introduction

Running Kafka yourself means owning brokers, controllers, disks, upgrades, certificates, monitoring and the pager. Many teams decide that is not where they want to spend their engineering time, and pay a provider to do it. The market is crowded, and the services differ more than their marketing suggests: some run Apache Kafka itself, some reimplement its protocol on a different engine, and each draws the line between "managed" and "your problem" in a different place.

This page explains what each major option actually is, how a client connects to it, which Kafka features you might lose, and how the pricing models push your design in different directions. By the end you should be able to shortlist one or two services for a given workload and know which questions to ask before committing.

The four covered in depth are Confluent Cloud, Amazon MSK, Azure Event Hubs and Redpanda Cloud. Aiven for Apache Kafka and Google Cloud's Managed Service for Apache Kafka are credible alternatives that sit close to MSK in the comparison below. Prices and quotas change often, so treat the specifics here as a map and check the provider's current documentation for numbers.

## What "Managed" Really Covers

Every managed service takes away the same core chores: provisioning machines, replacing failed brokers, patching and upgrading Kafka, and keeping the metadata quorum healthy. Beyond that, responsibilities diverge.

| Concern | Self-managed | Provisioned managed (MSK Standard, Aiven) | Serverless or fully managed (Confluent Cloud, MSK Serverless, Event Hubs) |
|---|---|---|---|
| Broker count and instance size | You | You choose, provider runs | Provider |
| Disk sizing | You | You, or auto-expanding storage | Provider |
| Kafka upgrades | You | You trigger, provider executes | Provider |
| Partition rebalancing across brokers | You | Usually you | Provider |
| Broker configuration | Full control | Most settings | A small allowed subset |
| Topic design, partition counts, keys | You | You | You |
| Client tuning, consumer lag, schemas | You | You | You |

The last two rows are the important ones. No provider designs your topics, picks your partition keys or fixes a slow consumer. Managed Kafka removes the infrastructure work, not the application work, so everything else in this tutorial still applies.

## Confluent Cloud

Confluent was founded by Kafka's original creators, and Confluent Cloud is its fully managed service on AWS, Azure and Google Cloud. Under the hood it runs Kora, Confluent's cloud-native engine that speaks the Kafka protocol and separates compute from storage. You do not see brokers at all; you choose a cluster type.

| Cluster type | Intended use |
|---|---|
| Basic | Development, testing and small workloads |
| Standard | Production workloads on public networking |
| Enterprise | Production workloads that need private networking, with elastic scaling |
| Dedicated | Single-tenant capacity sized in CKUs, for high throughput or special networking |
| Freight | Very high throughput where relaxed latency is acceptable; no idempotent producer or transactions |

Its strength is the ecosystem around the brokers: a managed Schema Registry with governance features, a large catalogue of fully managed connectors, managed Apache Flink for stream processing, and cluster linking for replication between clusters and regions. If you would otherwise assemble those pieces yourself, Confluent Cloud is often the cheapest option in total cost even when its per-gigabyte price is not.

Clients connect over TLS with an API key and secret:

```properties
bootstrap.servers=pkc-12345.us-east-1.aws.confluent.cloud:9092
security.protocol=SASL_SSL
sasl.mechanism=PLAIN
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required \
  username="API_KEY" password="API_SECRET";
# Recommended by Confluent for cloud clusters: tolerate transient network blips
client.dns.lookup=use_all_dns_ips
```

`PLAIN` here is safe because it runs inside TLS; the name refers to how credentials are sent, not to a lack of encryption. Confluent Cloud also supports OAuth through your identity provider.

Watch for: per-partition and per-connection limits on the smaller cluster types, network egress charges for consumers in another cloud or region, and the fact that some broker settings you might tune on your own cluster are not exposed.

## Amazon MSK

Amazon Managed Streaming for Apache Kafka runs real Apache Kafka brokers inside your AWS account's VPC. It comes in three shapes:

- **MSK Provisioned with Standard brokers.** You choose instance types and broker count, and storage is EBS volumes you size (with optional auto-expansion and tiered storage). Closest to running Kafka yourself, with AWS handling the machines and patching. Most broker settings can be customised.
- **MSK Provisioned with Express brokers.** Same model, but storage is fully managed and pay-as-you-go, and AWS claims up to three times the throughput per broker and much faster scaling and recovery. Fewer settings are tunable, and three-way replication is the default.
- **MSK Serverless.** No brokers to size; you pay for throughput and partitions. Authentication must use IAM, Kafka ACLs are not supported, and quotas on partitions and throughput per cluster apply.

MSK's case is integration with the rest of AWS: IAM for authentication, PrivateLink, CloudWatch metrics, MSK Connect for Kafka Connect workers, Lambda triggers and the Glue Schema Registry. Data never leaves your VPC unless you route it out. MSK supports Kafka 4.x on its newer offerings; check the version table, because MSK adds new Kafka releases weeks to months after the Apache release.

With IAM authentication, clients add the open-source `aws-msk-iam-auth` library to their classpath and use the dedicated IAM port:

```properties
bootstrap.servers=b-1.orders.abc123.c2.kafka.eu-west-1.amazonaws.com:9098
security.protocol=SASL_SSL
sasl.mechanism=AWS_MSK_IAM
sasl.jaas.config=software.amazon.msk.auth.iam.IAMLoginModule required;
sasl.client.callback.handler.class=software.amazon.msk.auth.iam.IAMClientCallbackHandler
```

The client then signs requests with whatever AWS credentials the process has (an instance role, an EKS service account), so there are no Kafka passwords to rotate. Provisioned clusters also support SCRAM, mutual TLS and, if you insist, unauthenticated access inside the VPC.

Watch for: with Standard brokers you still own capacity planning, partition reassignment after scaling, and the choice of when to upgrade. Cross-AZ data transfer between your clients and brokers can be a noticeable line on the bill.

## Azure Event Hubs

Azure Event Hubs is not Kafka. It is Microsoft's own event streaming service, which also exposes a Kafka-protocol endpoint. Existing Kafka clients can connect by changing only configuration, and the concepts map closely: a namespace is a cluster, an event hub is a topic, and partitions, consumer groups and offsets mean what you expect.

```properties
bootstrap.servers=shop-events.servicebus.windows.net:9093
security.protocol=SASL_SSL
sasl.mechanism=PLAIN
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required \
  username="$ConnectionString" \
  password="Endpoint=sb://shop-events.servicebus.windows.net/;SharedAccessKeyName=app;SharedAccessKey=...";
```

The username is the literal string `$ConnectionString`. For production, Microsoft recommends Entra ID with `OAUTHBEARER` instead of shared access keys.

The Kafka endpoint is available in the Standard, Premium and Dedicated tiers, not Basic. Because the engine is different, feature coverage varies by tier: at the time of writing, Kafka transactions and Kafka Streams are in public preview on Premium and Dedicated only, compression is limited to gzip on those same tiers, and broker-side features such as Kafka's own ACLs and broker configs do not exist (Azure RBAC replaces ACLs). Check the current feature table before relying on anything beyond plain produce and consume.

Event Hubs is a strong fit when you are already on Azure and mostly need durable, high-volume ingestion: telemetry, logs, clickstreams, with Azure Stream Analytics, Functions or Capture to Blob Storage downstream. It is a weak fit when your design depends on exactly-once processing, compacted topics or the wider Kafka ecosystem behaving exactly as it does on Apache Kafka.

## Redpanda Cloud

Redpanda is a separate streaming engine written in C++ that implements the Kafka protocol. There is no JVM and no separate controller process; each node uses a thread-per-core design and its own Raft implementation. Clients, Kafka Connect and Kafka Streams applications generally work unchanged, and Redpanda's tooling (`rpk`, Redpanda Console) works against Apache Kafka too.

Redpanda Cloud comes in three deployment models:

| Model | Where it runs |
|---|---|
| Serverless | Multi-tenant, in Redpanda's cloud account; pay per use; no Kafka Connect |
| Dedicated | Single-tenant, in Redpanda's cloud account on AWS, Azure or GCP |
| BYOC | Single-tenant data plane in your own cloud account, operated by Redpanda |

Redpanda's pitch is lower and more predictable tail latency and fewer, smaller nodes for the same throughput. BYOC is attractive when data must stay in your account but you do not want to operate the cluster. Clients usually connect with `SASL_SSL` and `SCRAM-SHA-256`. The self-hosted Community Edition is source-available under the Business Source License rather than Apache 2.0, which matters if you plan to move off the cloud service later.

Watch for: features that are newer in Apache Kafka can arrive later, or work differently, in a reimplementation. Test the specific features you depend on, such as transactions, the KIP-848 consumer protocol or share groups.

## Choosing Between Them

| Question | Leans towards |
|---|---|
| Are you all-in on AWS and want data inside your VPC? | Amazon MSK (Express or Serverless for less operations) |
| Do you need managed connectors, Schema Registry and Flink in one place, or multi-cloud? | Confluent Cloud |
| Are you on Azure, mainly ingesting telemetry or logs into Azure services? | Azure Event Hubs |
| Must data stay in your account, but you want someone else to operate it? | Redpanda BYOC, Confluent BYOC options, or MSK |
| Is latency at the 99.9th percentile the main concern? | Benchmark Redpanda and Confluent with your own workload |
| Is the workload small, spiky or experimental? | A serverless tier: Confluent Basic or Standard, MSK Serverless, Redpanda Serverless |
| Do you need full control over broker configs and Kafka versions? | Self-managed, or MSK and Aiven with Standard brokers |

Pricing models shape design. Throughput-billed services make chatty, uncompressed producers expensive, so batching and compression pay off directly. Partition-billed tiers punish the "just create 200 partitions to be safe" habit. Egress-billed services reward placing consumers in the same region and cloud as the cluster. Always model the bill with your real ingress, egress, retention and partition count; the headline price per hour is rarely what dominates.

:::tip
Keep your application portable by putting every connection setting (bootstrap servers, security protocol, mechanism, credentials) in configuration, never in code. Then switching providers, or running against the local Docker broker in development, is a configuration change. The [development workflow page](./6-kafka-development-workflow.mdx) shows this pattern.
:::

## Worked Scenario: A Startup's Clickstream Pipeline

A startup with eight engineers is building product analytics. Their web and mobile clients send about 20 MB/s of click events at peak and almost nothing at night. Events must reach a data warehouse within a minute, and the team wants to add a fraud-signal service later. Everything else they run is on AWS.

They compared four options:

- **Self-managed on EC2.** Cheapest on paper, but nobody on the team has run Kafka, and on-call for a stateful cluster was the one thing they were determined to avoid.
- **MSK Provisioned (Standard).** Fits AWS well, but they would still size brokers and disks for the daytime peak and pay for idle capacity at night.
- **MSK Serverless.** Scales with traffic, IAM authentication fits their existing roles, data stays in their VPC. Partition and throughput quotas were well above their needs.
- **Confluent Cloud.** Attractive managed connector for their warehouse, but cross-cloud networking and a second vendor contract were extra work for a team this size.

They chose MSK Serverless, with the warehouse fed by a small consumer service on ECS. The written decision noted the conditions for revisiting it: sustained throughput high enough that Express brokers become cheaper, or a need for managed connectors at which point Confluent Cloud becomes the stronger candidate. Because all connection settings live in environment variables and local development uses the Docker broker, both moves would be configuration changes, not rewrites.

## Common Mistakes

- Assuming "Kafka-compatible" means identical. Test transactions, compaction, consumer protocols and admin operations on the actual service.
- Comparing only the hourly price and ignoring egress, cross-AZ traffic, partition charges and retention storage.
- Forgetting that managed services still need monitoring of your own consumer lag, error rates and producer retries.
- Hard-coding cloud credentials or endpoints in application code, which locks you in and leaks secrets.
- Over-partitioning on a service that bills or limits by partition.
- Placing consumers in a different region from the cluster and paying for every byte twice, in latency and in egress.
- Choosing a provider before deciding whether you need the surrounding pieces (schemas, connectors, stream processing), which often decides the total cost.

## Summary

- Managed services remove broker operations, not application design; topics, keys, schemas and consumer health are still yours.
- Confluent Cloud is fully managed with the richest surrounding ecosystem, on all three major clouds.
- Amazon MSK runs Apache Kafka in your VPC with AWS integration; Standard brokers give control, Express and Serverless give less operations.
- Azure Event Hubs is a different engine with a Kafka endpoint; check tier-specific feature support before relying on transactions or Streams.
- Redpanda reimplements the Kafka protocol in C++ and offers serverless, dedicated and bring-your-own-cloud deployments.
- Choose by cloud, data residency, ecosystem needs and pricing model, and keep connection settings in configuration so the choice stays reversible.
