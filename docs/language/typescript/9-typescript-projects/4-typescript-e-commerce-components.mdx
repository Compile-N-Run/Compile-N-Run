# TypeScript E-commerce Components

## Introduction

Shopping carts look simple, but checkout code is full of traps: prices that drift by a cent, coupons that discount more than the order is worth, orders that jump from "delivered" back to "pending", and payment data in three different shapes. TypeScript can turn most of these bugs into compile-time errors.

In this project we'll build a set of small, framework-neutral e-commerce components in plain TypeScript. You'll learn how to:

- Model products, cart items and orders with interfaces and union types
- Represent payment methods as a discriminated union with exhaustive checks
- Store money as integer cents and format it with `Intl.NumberFormat`
- Validate coupons coming from JSON using type guards
- Use generics for a reusable `Result` type and a typed lookup helper
- Write a typed `Cart` class and render a plain-text receipt

Everything runs on Node.js with `tsc`, so you can later plug these pieces into any frontend framework or a backend API.

## Step 1: Money as Integer Cents

Before writing any types, let's settle how we store money. JavaScript numbers are binary floating-point values, and most decimal fractions cannot be represented exactly:

```typescript
console.log(0.1 + 0.2);
console.log(1.15 * 100);
console.log(Math.round(1.005 * 100));
```

```text
0.30000000000000004
114.99999999999999
100
```

The last line should be `101`, but `1.005` is actually stored as `1.00499999...`, so it rounds down. In a shop, these tiny errors add up across thousands of orders and cause totals that don't match the payment provider or the accounting system.

The standard fix is to store every amount as an **integer number of the smallest currency unit** (cents for USD). Integer addition and multiplication are exact, and we only convert to a decimal string when displaying a price.

We'll use a **branded type** so that a plain `number` can't accidentally be used where cents are expected:

```typescript title="src/money.ts"
// A branded type: a number that has been checked to be whole cents
export type Cents = number & { readonly __brand: "Cents" };

export function cents(value: number): Cents {
  if (!Number.isSafeInteger(value)) throw new Error(`Not whole cents: ${value}`);
  return value as Cents;
}

// Parse "12.99" without ever going through floating-point math
export function parseDollars(input: string): Cents {
  const match = /^(\d+)(?:\.(\d{1,2}))?$/.exec(input.trim());
  if (!match) throw new Error(`Invalid amount: "${input}"`);
  const fraction = (match[2] ?? "").padEnd(2, "0");
  return cents(Number(match[1]) * 100 + Number(fraction));
}

export const addCents = (...amounts: Cents[]): Cents =>
  cents(amounts.reduce((sum, a) => sum + a, 0));

// The single place where rounding happens (percentages, tax)
export const multiplyCents = (amount: Cents, factor: number): Cents =>
  cents(Math.round(amount * factor));

export function formatPrice(amount: Cents, currency = "USD", locale = "en-US"): string {
  const formatter = new Intl.NumberFormat(locale, { style: "currency", currency });
  // USD and EUR have 2 minor digits, JPY has 0: ask Intl instead of hardcoding 100
  const digits = formatter.resolvedOptions().maximumFractionDigits ?? 2;
  return formatter.format(amount / 10 ** digits);
}
```

A few design decisions are worth pointing out:

- `Cents` is a `number` at runtime, but the `__brand` property exists only in the type system. The only way to create one is through `cents()`, which checks that the value is a safe integer.
- `parseDollars` parses user input like `"12.99"` with a regular expression and integer math, so we never multiply a float by 100.
- `multiplyCents` is the one place where rounding happens, for percentages and tax. Keeping rounding in one function makes the rounding rule easy to change.
- `Intl.NumberFormat` handles currency symbols, separators and decimals per locale. Creating one is relatively expensive, so cache formatters in a `Map` in hot paths.

The brand catches mistakes at compile time: `const shipping: Cents = 499` fails with "Type 'number' is not assignable to type 'Cents'", while `cents(499)` compiles.

Let's try the formatter with a few locales:

```typescript title="src/money-demo.ts"
import { cents, parseDollars, formatPrice } from "./money.js";

console.log(parseDollars("19.99"), parseDollars("0.5"));

const price = cents(123450);
console.log(formatPrice(price));
console.log(formatPrice(price, "EUR", "de-DE"));
console.log(formatPrice(price, "GBP", "en-GB"));
console.log(formatPrice(cents(1500), "JPY", "ja-JP"));
```

```text
1999 50
$1,234.50
1.234,50 €
£1,234.50
￥1,500
```

Notice that the yen has no minor unit, so `1500` means 1,500 yen. That's why `formatPrice` asks `Intl` for `maximumFractionDigits` instead of always dividing by 100.

## Step 2: Product, Cart and Order Types

Next we describe the shape of our domain. String literal unions keep categories and statuses to a fixed set of values, and a discriminated union models payment methods that each carry different data:

```typescript title="src/types.ts"
import type { Cents } from "./money.js";

export type Category = "books" | "electronics" | "clothing";
export type OrderStatus = "pending" | "paid" | "shipped" | "delivered" | "cancelled";

export interface Product {
  readonly id: string;
  name: string;
  priceCents: Cents;
  category: Category;
  stock: number;
}

export interface CartItem {
  readonly product: Product;
  quantity: number;
}

export interface CartTotals {
  subtotal: Cents;
  discount: Cents;
  tax: Cents;
  total: Cents;
}

export type PaymentMethod =
  | { kind: "card"; brand: "visa" | "mastercard" | "amex"; last4: string }
  | { kind: "paypal"; email: string }
  | { kind: "bankTransfer"; iban: string }

export interface Order {
  readonly id: string;
  readonly items: readonly CartItem[];
  readonly totals: CartTotals;
  readonly payment: PaymentMethod;
  readonly status: OrderStatus;
}
```

The `kind` field is the **discriminant**. When you check `payment.kind === "card"`, TypeScript narrows `payment` to the card variant, so `payment.last4` is available but `payment.email` is not. This is much safer than one big interface with lots of optional fields.

We can use that narrowing in a helper that describes a payment for receipts:

```typescript title="src/payment.ts"
import type { PaymentMethod } from "./types.js";

export function describePayment(payment: PaymentMethod): string {
  switch (payment.kind) {
    case "card":
      return `${payment.brand.toUpperCase()} ending in ${payment.last4}`;
    case "paypal":
      return `PayPal (${payment.email})`;
    case "bankTransfer":
      return `Bank transfer from ${payment.iban.slice(0, 4)}...${payment.iban.slice(-4)}`;
    default: {
      // If a new payment kind is added and not handled, this line fails to compile
      const unhandled: never = payment;
      throw new Error(`Unknown payment method: ${JSON.stringify(unhandled)}`);
    }
  }
}
```

The `never` assignment is an **exhaustiveness check**. If someone later adds `| { kind: "giftCard"; code: string }` to `PaymentMethod` and forgets to update this switch, the compiler reports:

```text
src/payment.ts(13,13): error TS2322: Type '{ kind: "giftCard"; code: string; }' is not assignable to type 'never'.
```

## Step 3: A Generic Result Type

Many shop operations can fail for ordinary business reasons: a product is out of stock, a coupon has expired, an order can't be cancelled. Throwing exceptions for these makes them easy to forget. Instead, we return a `Result` that the caller must inspect:

```typescript title="src/result.ts"
export type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E };

export const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
export const err = <E>(error: E): Result<never, E> => ({ ok: false, error });
```

`Result` is generic in both the success type `T` and the error type `E`. Because `ok` is the discriminant, checking `if (result.ok)` narrows to the branch that has `value`, and the `else` branch has `error`. Later, `main.ts` pairs it with a constrained generic, `findById<T extends { readonly id: string }>`, that can look up products, orders or customers and returns a `Result<T>` of the right type.

## Step 4: Coupons with Type Guards

Coupons are another discriminated union. They usually come from an admin panel or an API as JSON, so TypeScript can't trust their shape. A **type guard**, a function returning `value is Coupon`, validates the data at runtime and tells the compiler what it found:

```typescript title="src/discounts.ts"
import { type Cents, cents, multiplyCents, formatPrice } from "./money.js";
import { type Result, ok, err } from "./result.js";
import type { CartItem, Category } from "./types.js";

export type Coupon =
  | { type: "percentage"; code: string; percent: number }
  | { type: "fixed"; code: string; amount: Cents; minSubtotal: Cents }
  | { type: "category"; code: string; category: Category; percent: number };

const CATEGORIES: readonly unknown[] = ["books", "electronics", "clothing"];

const isPercent = (v: unknown): v is number =>
  typeof v === "number" && v > 0 && v <= 100;
const isCents = (v: unknown): v is Cents =>
  typeof v === "number" && Number.isSafeInteger(v) && v >= 0;

// Coupons arrive as JSON from an API or admin panel, so validate them at runtime
export function isCoupon(value: unknown): value is Coupon {
  if (typeof value !== "object" || value === null) return false;
  const c = value as Record<string, unknown>;
  if (typeof c.code !== "string") return false;
  switch (c.type) {
    case "percentage": return isPercent(c.percent);
    case "fixed": return isCents(c.amount) && isCents(c.minSubtotal);
    case "category": return CATEGORIES.includes(c.category) && isPercent(c.percent);
    default: return false;
  }
}

export function calculateDiscount(
  coupon: Coupon,
  items: readonly CartItem[],
  subtotal: Cents
): Result<Cents> {
  switch (coupon.type) {
    case "percentage":
      return ok(multiplyCents(subtotal, coupon.percent / 100));
    case "fixed":
      if (subtotal < coupon.minSubtotal) {
        return err(`${coupon.code} needs a subtotal of ${formatPrice(coupon.minSubtotal)}`);
      }
      return ok(cents(Math.min(coupon.amount, subtotal))); // never below zero
    case "category": {
      const eligible = items
        .filter((item) => item.product.category === coupon.category)
        .reduce((sum, item) => sum + item.product.priceCents * item.quantity, 0);
      if (eligible === 0) return err(`${coupon.code} only applies to ${coupon.category}`);
      return ok(multiplyCents(cents(eligible), coupon.percent / 100));
    }
  }
}
```

Key points:

- Inside `isCoupon`, the parameter starts as `unknown`, so TypeScript forces us to check every field before we use it.
- `calculateDiscount` returns `Result<Cents>`, so a coupon that doesn't apply is a normal outcome, not an exception.
- The fixed coupon is capped with `Math.min`, so a 50 dollar coupon on a 30 dollar cart can never produce a negative total.
- The switch has no `default` branch, yet TypeScript knows every path returns, because all three `type` values are handled.

## Step 5: The Cart Class

Now we combine everything into a `Cart` class:

```typescript title="src/cart.ts"
import { type Cents, cents, addCents, multiplyCents } from "./money.js";
import { type Result, ok, err } from "./result.js";
import { type Coupon, calculateDiscount } from "./discounts.js";
import type { CartItem, CartTotals, Product } from "./types.js";

export class Cart {
  private readonly items = new Map<string, CartItem>();
  private coupon: Coupon | null = null;

  // Tax rate in basis points: 825 = 8.25%, so the rate itself is an integer too
  constructor(private readonly taxRateBps: number) {}

  add(product: Product, quantity = 1): Result<CartItem> {
    const current = this.items.get(product.id)?.quantity ?? 0;
    return this.setLine(product, current + quantity);
  }

  setQuantity(productId: string, quantity: number): Result<CartItem | null> {
    const existing = this.items.get(productId);
    if (!existing) return err(`Product "${productId}" is not in the cart`);
    if (quantity <= 0) {
      this.remove(productId);
      return ok(null);
    }
    return this.setLine(existing.product, quantity);
  }

  remove(productId: string): boolean {
    return this.items.delete(productId);
  }

  private setLine(product: Product, quantity: number): Result<CartItem> {
    if (!Number.isInteger(quantity) || quantity <= 0) {
      return err(`Quantity must be a positive integer, got ${quantity}`);
    }
    if (quantity > product.stock) {
      return err(`Only ${product.stock} of "${product.name}" in stock`);
    }
    const item: CartItem = { product, quantity };
    this.items.set(product.id, item);
    return ok(item);
  }

  applyCoupon(coupon: Coupon): Result<Cents> {
    const result = calculateDiscount(coupon, this.getItems(), this.subtotal());
    if (result.ok) this.coupon = coupon;
    return result;
  }

  getItems(): readonly CartItem[] {
    return [...this.items.values()];
  }

  itemCount(): number {
    return this.getItems().reduce((count, item) => count + item.quantity, 0);
  }

  subtotal(): Cents {
    return addCents(...this.getItems().map((i) => cents(i.product.priceCents * i.quantity)));
  }

  totals(): CartTotals {
    const subtotal = this.subtotal();
    // Re-check the coupon: the cart may have changed since it was applied
    const result = this.coupon && calculateDiscount(this.coupon, this.getItems(), subtotal);
    const discount = result?.ok ? result.value : cents(0);
    const taxable = cents(subtotal - discount);
    const tax = multiplyCents(taxable, this.taxRateBps / 10_000);
    return { subtotal, discount, tax, total: addCents(taxable, tax) };
  }
}
```

The cart stores items in a `Map` keyed by product ID, so adding the same product twice increases its quantity instead of creating a duplicate line. Both `add` and `setQuantity` go through the private `setLine` method, so the quantity and stock rules live in one place. `getItems()` returns a `readonly CartItem[]`, so callers can't push items into the cart behind its back.

The tax rate is stored in **basis points** (hundredths of a percent). Like cents, this keeps the configuration an integer, and `multiplyCents` does the single rounding step. Note that the discount is recalculated in `totals()`: if a customer removes all their books, a books-only coupon quietly stops applying.

## Step 6: Orders and Status Transitions

When the customer checks out, we freeze the cart into an `Order`. Order statuses follow a simple state machine, which we can describe with a `Record` typed by the `OrderStatus` union:

```typescript title="src/orders.ts"
import type { Cart } from "./cart.js";
import { type Result, ok, err } from "./result.js";
import type { Order, OrderStatus, PaymentMethod } from "./types.js";

const allowedTransitions: Record<OrderStatus, readonly OrderStatus[]> = {
  pending: ["paid", "cancelled"],
  paid: ["shipped", "cancelled"],
  shipped: ["delivered"],
  delivered: [],
  cancelled: [],
};

let nextOrderNumber = 1001;

export function checkout(cart: Cart, payment: PaymentMethod): Result<Order> {
  if (cart.itemCount() === 0) return err("Cannot check out an empty cart");
  return ok({
    id: `ORD-${nextOrderNumber++}`,
    items: cart.getItems().map((item) => ({ ...item })),
    totals: cart.totals(),
    payment,
    status: "pending",
  });
}

export function transition(order: Order, next: OrderStatus): Result<Order> {
  if (!allowedTransitions[order.status].includes(next)) {
    return err(`Cannot move order ${order.id} from "${order.status}" to "${next}"`);
  }
  return ok({ ...order, status: next });
}
```

Because the table is `Record<OrderStatus, readonly OrderStatus[]>`, adding a new status like `"refunded"` to the union makes the compiler demand a new entry. `transition` returns a new order object instead of mutating the old one, which makes order history easy to keep.

## Step 7: Rendering a Receipt

Finally, a small framework-agnostic rendering function turns an order into text. The same idea works for HTML strings, emails or a React component, because it only depends on our types:

```typescript title="src/render.ts"
import { cents, formatPrice } from "./money.js";
import { describePayment } from "./payment.js";
import type { Order } from "./types.js";

export function renderReceipt(order: Order, width = 40): string {
  const row = (left: string, right: string) => left + right.padStart(width - left.length);
  const line = "-".repeat(width);
  const { subtotal, discount, tax, total } = order.totals;

  return [
    `Order ${order.id} (${order.status})`,
    line,
    ...order.items.map(({ product, quantity }) =>
      row(`${quantity} x ${product.name}`, formatPrice(cents(product.priceCents * quantity)))),
    line,
    row("Subtotal", formatPrice(subtotal)),
    ...(discount > 0 ? [row("Discount", `-${formatPrice(discount)}`)] : []),
    row("Tax", formatPrice(tax)),
    row("Total", formatPrice(total)),
    line,
    `Paid with: ${describePayment(order.payment)}`,
  ].join("\n");
}
```

## Putting It All Together

Here is a script that uses every component:

```typescript title="src/main.ts"
import { Cart } from "./cart.js";
import { isCoupon } from "./discounts.js";
import { cents, formatPrice } from "./money.js";
import { checkout, transition } from "./orders.js";
import { renderReceipt } from "./render.js";
import { type Result, ok, err } from "./result.js";
import type { Product } from "./types.js";

// Works for products, orders, customers: anything with a string id
function findById<T extends { readonly id: string }>(items: readonly T[], id: string): Result<T> {
  const found = items.find((item) => item.id === id);
  return found ? ok(found) : err(`No item with id "${id}"`);
}

const catalog: Product[] = [
  { id: "p1", name: "TypeScript Book", priceCents: cents(3999), category: "books", stock: 10 },
  { id: "p2", name: "USB-C Cable", priceCents: cents(1299), category: "electronics", stock: 3 },
  { id: "p3", name: "Dev Hoodie", priceCents: cents(4950), category: "clothing", stock: 5 },
];

const cart = new Cart(825); // 8.25% sales tax
const lines: [string, number][] = [["p1", 1], ["p2", 2], ["p3", 1], ["p9", 1]];

for (const [id, qty] of lines) {
  const found = findById(catalog, id);
  if (!found.ok) { console.log(`Skipped: ${found.error}`); continue; }
  const added = cart.add(found.value, qty);
  console.log(added.ok ? `Added ${qty} x ${found.value.name}` : `Error: ${added.error}`);
}

const tooMany = cart.setQuantity("p2", 5);
if (!tooMany.ok) console.log(`Error: ${tooMany.error}`);
console.log(`Items: ${cart.itemCount()}, subtotal: ${formatPrice(cart.subtotal())}`);

// Coupons as they might arrive from an API
const incoming: unknown[] = [
  { type: "fixed", code: "BIG50", amount: 5000, minSubtotal: 20000 },
  { type: "percent", code: "TYPO", percent: 10 },
  { type: "category", code: "READMORE", category: "books", percent: 25 },
];

for (const raw of incoming) {
  if (!isCoupon(raw)) { console.log(`Rejected: ${JSON.stringify(raw)}`); continue; }
  const result = cart.applyCoupon(raw);
  console.log(result.ok ? `Applied ${raw.code}: -${formatPrice(result.value)}` : `Not applied: ${result.error}`);
}

const placed = checkout(cart, { kind: "card", brand: "visa", last4: "4242" });
const paid = placed.ok ? transition(placed.value, "paid") : placed;
if (!paid.ok) throw new Error(paid.error);
console.log(`\n${renderReceipt(paid.value)}\n`);

const backwards = transition(paid.value, "pending");
console.log(backwards.ok ? "Moved back to pending" : `Error: ${backwards.error}`);
```

```bash
node dist/main.js
```

## Real-World Scenario

Imagine a small team running a store that sells books and accessories. Their original JavaScript checkout stored prices as floats like `19.99`, coupons as loosely shaped objects, and order status as free-form strings. They regularly saw totals that differed from the payment provider by a cent, a coupon that once produced a negative order total, and a support ticket where an order had a status of `"shiped"`.

**Why these components help:** integer cents remove the rounding drift, the `Coupon` union plus `isCoupon` reject malformed coupon data at the boundary, `OrderStatus` makes typos impossible, and the transition table blocks invalid status changes. The `Result` type makes every "out of stock" or "coupon not valid" case visible in the function signature, so the UI can show a friendly message instead of crashing.

**When to use this approach:** it pays off as soon as money, discounts or order states are involved, whether in a storefront frontend, a Node.js checkout API, or a shared package used by both. Because the components are framework-neutral, the same `Cart` and `calculateDiscount` can run in the browser for instant feedback and on the server for the final, trusted calculation.

**Trade-offs to keep in mind:**

- Type guards and TypeScript types disappear at runtime. For larger APIs, a schema library such as Zod can generate both the validator and the type from one definition.
- Integer cents are safe up to `Number.MAX_SAFE_INTEGER` (about 90 trillion dollars), which is plenty for carts. For currency conversion or very precise financial math, consider `bigint` or a decimal library.
- Rounding rules for tax are set by law and differ by country (per line versus per order, half-up versus banker's rounding). Keeping rounding in `multiplyCents` makes it easy to change, but you must confirm the right rule.
- Never trust prices sent from the browser. The client-side cart is for display; the server should look up prices and recompute totals before charging.

## Summary

In this project we built a set of typed e-commerce components:

1. **Money** stored as branded integer `Cents`, formatted with `Intl.NumberFormat`
2. **Types** for products, cart items and orders, using string literal unions for categories and statuses
3. **Payment methods** as a discriminated union with a `never` exhaustiveness check
4. **A generic `Result` type** for expected failures, plus a constrained generic `findById` helper
5. **Coupons** validated from `unknown` input with type guards
6. **A `Cart` class** with add, quantity updates, removal, coupons and totals
7. **Orders** with a typed status state machine and a plain-text receipt renderer

## Exercises

1. **Free shipping:** add a `{ type: "freeShipping"; minSubtotal: Cents }` coupon and a shipping fee to `CartTotals`. Follow the compiler errors to update every switch.
2. **Stacking rules:** allow up to two coupons at once, but never more than one percentage coupon. Return a descriptive `Result` error otherwise.
3. **Gift cards:** add a `giftCard` payment method and fix the exhaustiveness error in `describePayment`.
4. **HTML rendering:** write a `renderCartHtml(cart: Cart): string` function that escapes product names before inserting them into markup.
