# HTML Project: Community Workshop Website

Combine the course's techniques into a small, usable website. The finished project has a workshop home page, a practice interest form, and a request-preview page. It uses native HTML, a small stylesheet, and no JavaScript or external media.

**Prerequisites:** Complete the [HTML forms](../4-html-forms/index.mdx) and [quality checks](./index.mdx) sections. The exercise is about structure and behavior; you can deepen the styling later in the [CSS course](/docs/language/css).

## Run the complete example

[Open the finished workshop website](/examples/html/index.html). Its form submits a GET request to a static preview page. It does not store information, send email, or reserve a place. Use invented practice values; they appear in the URL.

In the repository, the complete source is in `static/examples/html/`. Copy that whole directory to a working folder, keeping these files together:

```text
workshop-site/
  index.html
  interest.html
  preview.html
  styles.css
```

Without a repository checkout, save the HTML source of each linked page using your browser's View Source facility: [home](/examples/html/index.html), [interest form](/examples/html/interest.html), and [preview](/examples/html/preview.html). Save the [stylesheet](/examples/html/styles.css) as `styles.css` beside them. Preserve the filenames; browser “Save complete page” commands may rewrite paths into additional folders.

Open a terminal in `workshop-site` and run:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

Visit `http://127.0.0.1:8000/`. On Windows, use `py` instead of `python3` if that is your Python launcher. No installation beyond an available Python 3 runtime is needed for this server.

## Understand the design

Each page has its own title and one main heading. Shared navigation uses relative paths, with `aria-current` only on the matching page. A visible skip link reaches the main region. The home page includes a schedule with column and row headers and a native disclosure for an optional question.

The form asks for a fictional display name, one session, and a small seat quantity. Labels match unique IDs. Radio choices share a name and sit inside a fieldset. Native constraints help catch omissions and out-of-range values.

The important submission relationship is:

```html
<form action="preview.html" method="get">
```

The browser serializes named controls into a query string and navigates to the preview resource. The static preview explains that it has not processed or stored a registration. It deliberately does not pretend to personalize a response from values it never reads.

## Build your variation

Add a third workshop to the home page's schedule and the form's radio group. Give it a distinct value such as `gardening`, a unique ID, and a descriptive visible label. Add preparation advice under a heading on the home page, with a fragment link from the corresponding form description if useful.

Use this acceptance checklist:

- Every navigation link works from its actual page, including nested deployment paths.
- Heading levels describe the content hierarchy, and IDs are unique per document.
- The third workshop appears in both schedule and form with consistent wording.
- Empty required fields and a seat count of 5 block ordinary form submission.
- Valid invented values produce a query string on `preview.html`, with no booking claim.
- Keyboard navigation, zoom, and HTML conformance checks reveal no unresolved failures.

A successful solution updates both the visible choice and its submitted identifier. Changing only the table leaves users unable to choose the new session; changing only the form creates an option the schedule never explains.

For a production registration system, the next project would add a real server endpoint with validation, persistence, and a truthful confirmation response. That is a separate application feature, not a hidden capability of HTML.
