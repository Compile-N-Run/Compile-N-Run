# HTML Accessibility Checks

Accessibility is part of building each element, and a final review helps catch mistakes introduced when those elements are combined. No single automated score can tell you whether every person can complete a task.

**Prerequisites:** Complete the [semantic structure](../2-html-semantic-structure/index.mdx), [media](../3-html-images-and-media/index.mdx), and [forms](../4-html-forms/index.mdx) sections. Review a real page from your project rather than an isolated fragment.

## Choose a task to test

For the workshop project, the task is: find a session, identify its location, and complete the demonstration form. Start at the home page, because context and navigation matter. Record observations as concrete steps, such as “Tab reaches the session link but focus is not visible.”

Use the keyboard without the mouse. Check that you can reach and activate links, open disclosures, choose form options, and submit. Confirm the skip link bypasses repeated navigation. A visually obvious control may still be missing a usable name or normal keyboard behavior.

## Inspect structure and names

Read the heading outline without the paragraphs. It should describe the content in a sensible hierarchy. Check that there is one visible main region and that multiple navigation regions have useful names.

For every form field, identify the visible label and confirm that its `for` matches the control's ID. Instructions should remain available after typing. For every image, ask what information would be lost if it were unavailable and check whether the alternative and surrounding text cover that information.

This fragment has a visible instruction but no proper control label:

```html
<p>Email address</p>
<input id="email" name="email" type="email">
```

Repair the relationship explicitly:

```html
<label for="email">Email address</label>
<input id="email" name="email" type="email">
```

Do not try to repair all accessibility problems with ARIA. Native semantic elements and explicit labels often solve the underlying issue more directly. An ARIA name also does not create keyboard behavior on a generic element.

## Change the viewing conditions

Increase browser zoom and narrow the window. Check for clipped text, overlapping controls, and horizontal scrolling caused by oversized images. Tables and code samples sometimes need special handling, but ordinary paragraphs should not require constant side-to-side movement.

If you add CSS, check text contrast and visible focus in addition to HTML structure. If possible, try a screen reader and inspect the browser's accessibility tree. Learn the tool's navigation commands before treating unexpected behavior as a page defect.

Automated accessibility tools can detect some problems, such as missing names, but cannot reliably judge whether alternative text is accurate or an instruction makes sense. Use their findings alongside manual task testing.

## Practice and check

Audit your form twice: once with the keyboard and once at 200% zoom. Write three observations, fix any failures, and repeat the exact task. A passing result lets you understand every field, reach each control, correct an invalid value, and see the result without losing essential content. Treat this as an initial review, not a claim of complete standards conformance.
