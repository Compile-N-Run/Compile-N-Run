# HTML Accessible Navigation

A navigation system should work when a reader uses a keyboard, zooms the page, or encounters a link outside its original visual context. Native links already supply much of this behavior if you preserve it.

**Prerequisites:** [Links and paths](../1-html-text-and-links/2-html-links-and-paths.mdx) and [page landmarks](./0-html-landmarks.mdx).

## Build a simple navigation pattern

Place a skip link near the beginning of the body, followed by site navigation and the main content:

```html
<a href="#main-content">Skip to main content</a>
<header>
  <nav aria-label="Main">
    <ul>
      <li><a href="index.html" aria-current="page">Home</a></li>
      <li><a href="about.html">About</a></li>
    </ul>
  </nav>
</header>
<main id="main-content" tabindex="-1">
  <h1>Community Workshop</h1>
  <p>Choose a session and learn with a neighbor.</p>
</main>
```

The skip link lets people bypass repeated navigation. Keep it visible while learning; a later CSS enhancement can reveal it on focus if implemented carefully. `tabindex="-1"` lets the main region receive focus without adding it to the normal Tab sequence, helping the fragment target behave predictably.

`aria-current="page"` identifies the current page in the navigation. On `about.html`, move that attribute to the About link. It does not automatically add a visual style, so later use CSS to make the current item apparent visually as well.

## Preserve native behavior

An anchor with a real `href` participates in keyboard navigation. Users can activate it, copy the URL, or open it in another tab using their browser's commands. A clickable `span` does not acquire those behaviors simply because it looks like a link.

Do not give ordinary site navigation `role="menu"`. Application menus have additional keyboard conventions that a list of page links does not implement. A `nav` containing a list of anchors is sufficient here.

Avoid positive `tabindex` values such as `1` or `2` to force a custom order. They can make focus jump around the document as you add controls. Keep the source order logical, then let the browser's normal navigation follow it.

## Test from the keyboard

Reload the page and use Tab to move through links, Shift+Tab to go backward, and Enter to activate a focused link. On some systems, browser or operating-system keyboard settings affect which controls Tab reaches; check those settings before assuming markup is broken.

You should always be able to tell which element has focus. Do not remove a focus outline merely because it clashes with a design. Test the skip link and then verify that subsequent keyboard navigation continues sensibly through the main content.

## Practice and check

Add the same navigation to two pages and mark the appropriate current link on each. Add a skip target to each page.

The solution should have a unique `main-content` ID per document, working document-relative paths, and exactly one current-page indicator in that navigation. Inspect the source after visiting both pages; copying a header without updating `aria-current` is an easy mistake.
