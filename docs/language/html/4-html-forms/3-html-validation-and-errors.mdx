# HTML Form Validation and Errors

Native validation catches some mistakes before a request is sent. It helps people complete a form, but a server must still treat incoming data as untrusted because requests can bypass the browser's controls.

**Prerequisites:** [Form submission](./2-html-form-submission.mdx). Keep the local `preview.html` demonstration destination and use invented values.

## Express the actual requirements

```html
<form action="preview.html" method="get">
  <p>
    <label for="email">Email address (required)</label>
    <input id="email" name="email" type="email" required>
  </p>
  <p>
    <label for="seats">Seats (1 to 4)</label>
    <input id="seats" name="seats" type="number"
           min="1" max="4" step="1" required>
  </p>
  <p>
    <label for="reference">Reference code (three uppercase letters)</label>
    <input id="reference" name="reference" pattern="[A-Z]{3}"
           aria-describedby="reference-help" required>
  </p>
  <p id="reference-help">Practice example: ABC. Use exactly three letters.</p>
  <button type="submit">Preview request</button>
</form>
```

Submitting empty required fields should block normal submission and show browser feedback. An email value such as `hello` should fail the type constraint. A seat quantity of 5 should fail the maximum; 1.5 should fail the step constraint. The pattern applies to the whole reference value, so `ABCD` does not match three letters.

The browser's messages, styling, and timing vary. Do not write a test that assumes every browser displays the exact same sentence. Test the user-observable outcome: invalid data is identified and normal submission does not proceed until corrected.

## Make constraints understandable before errors

Visible labels and instructions explain requirements in advance. `required` exposes a constraint programmatically; adding “required” in visible text makes the rule apparent to other readers too. Do not communicate a requirement only with color or an unexplained asterisk.

Use constraints that match the real data. A strict pattern for personal names can exclude valid names. An email input checks a format, not deliverability. `maxlength` can limit appropriate text fields, but a server must enforce its own bounds even if a browser has already limited typing.

## Know the limits

Native validation runs for ordinary validated submissions, but can be disabled or bypassed. A person can modify markup, use another HTTP client, or send a direct request. A production server must check values, permissions, inventory, and business rules independently.

If a server rejects a submission, return clear messages near the relevant fields and preserve safe entered values so the person can recover. Associate field-specific messages with controls, and indicate invalid state after an actual error. A full dynamic error-summary implementation needs behavior beyond this HTML-only exercise.

Avoid a reset button on ordinary registration forms: it can erase work accidentally. A normal submit button should state the actual result, such as “Preview request” in this local demo.

## Practice and check

Test four cases: empty form, malformed email, five seats, and valid invented data with code `ABC`. The first three should stop normal submission. The valid case should navigate to the static preview with a query string and still make no booking. Then explain why a backend cannot trust that browser check as proof of validity.
