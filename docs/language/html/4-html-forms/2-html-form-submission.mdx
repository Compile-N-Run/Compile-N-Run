# HTML Form Submission and Server Boundaries

A form tells the browser where and how to send data. A server decides what that data means, whether it is valid, and whether anything should be stored. HTML supplies the interface and request configuration, not the server's application logic.

**Prerequisites:** [Labels](./0-html-form-labels-and-controls.mdx), [choice controls](./1-html-grouping-and-choices.mdx), and a [local HTTP server](../0-html-foundations/1-html-setup.mdx).

## Observe a GET request

Save a basic document as `preview.html` beside `register.html`. Its body should clearly describe the demonstration:

```html
<h1>Form request preview</h1>
<p>The browser sent a query string. This static page has not saved a booking.</p>
<p>Inspect the address bar to see the submitted demonstration values.</p>
<a href="register.html">Return to the practice form</a>
```

Use this form in `register.html`:

```html
<form action="preview.html" method="get">
  <label for="topic">Topic</label>
  <input id="topic" name="topic" value="bicycle repair">
  <button type="submit">Preview request</button>
</form>
```

Open the form through HTTP and submit it. The URL should end with a query similar to `preview.html?topic=bicycle+repair`. Spaces and reserved characters are URL-encoded. The exact displayed representation may vary, but the name and value remain identifiable.

The static server returns `preview.html`; it does not turn the query into a registration. The page's text is the same regardless of the submitted topic. You can inspect the request in Developer Tools to separate browser behavior from server behavior.

## Which values are included?

A named text input contributes its current value. Disabled controls are omitted. Unchecked checkboxes and radio buttons are omitted. A selected option contributes its value. The activated submit button can also contribute a name/value pair if you give it a name.

`id` associates labels and fragment targets; it does not substitute for `name`. A read-only field is different from a disabled field: where supported, read-only controls can still contribute values.

## Choose the method for the operation

GET suits retrieval such as search or filtering. Its data appears in the URL, which can enter history, logs, and shared links. Do not put secrets or sensitive practice data in it.

POST sends form data in the request body and is appropriate for operations such as creating a registration. Changing the method to POST does not make a static file process it. Python's basic development server will not implement your registration endpoint. You need backend code or a configured form service.

POST is not encryption. Real applications use HTTPS, server-side validation, appropriate access controls, and other protections. File uploads typically require POST with `enctype="multipart/form-data"` and a server that handles uploaded files safely.

## Practice and solution

Add a named `level` select to the GET form and a disabled named input. Submit and inspect the URL. You should find the topic and selected level, but not the disabled field. Remove the topic input's name and submit again: its value should disappear from the request even though the field remains visible.
