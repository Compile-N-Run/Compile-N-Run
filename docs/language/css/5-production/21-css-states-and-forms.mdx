# Interactive States and Accessible Form Styling

An interface is more than its default appearance. A keyboard user needs to see focus. A checked option needs a visible state. An error needs understandable text, not just a red border. CSS expresses these states, while semantic HTML supplies much of the underlying behavior.

Use a link for navigation and a button for an action. Making a `div` look like a button does not give it keyboard activation or an accessible name. Start with the appropriate native element, then style it.

## Style a small preference form

Use a fresh practice document with this form and stylesheet. The reset button works locally; this exercise does not save data:

```html
<form class="preferences">
  <fieldset>
    <legend>Study preferences</legend>
    <div class="field">
      <label for="study-name">Notebook name</label>
      <input id="study-name" name="name" value="My notebook"
             required aria-describedby="name-help">
      <p id="name-help">A name is required. This practice form does not save changes.</p>
    </div>
    <label class="check">
      <input type="checkbox" name="reminders" checked>
      Show study reminders
    </label>
    <button type="reset">Restore defaults</button>
  </fieldset>
</form>
```

```css
* { box-sizing: border-box; }
body { padding: 1rem; font: 1rem/1.6 system-ui, sans-serif; color: #172033; }
.preferences { max-width: 30rem; }
fieldset { min-inline-size: 0; border: 1px solid #64748b; padding: 1rem; }
legend { font-weight: 700; }
.field { display: grid; gap: 0.4rem; }
input, button { font: inherit; }
input:not([type="checkbox"]) {
  width: 100%;
  min-width: 0;
  padding: 0.6em;
  border: 2px solid #64748b;
  border-radius: 0.25rem;
}
.check { display: flex; align-items: baseline; gap: 0.5rem; margin-block: 1rem; }
input[type="checkbox"] { accent-color: #234e9b; }
button {
  padding: 0.65em 1em;
  border: 2px solid #234e9b;
  border-radius: 0.3rem;
  background: #234e9b;
  color: white;
  cursor: pointer;
}
button:hover { background: #17376d; }
:focus-visible { outline: 3px solid #9f1239; outline-offset: 3px; }
input:invalid { border-color: #9f1239; }
```

Tab through the controls, change the name and checkbox, then activate Restore defaults. The native reset action restores the original value and checked state. Emptying the required field changes its border, while the visible help text explains the requirement.

## Design beyond hover

`:focus-visible` lets the browser determine when an explicit focus indicator is appropriate, including typical keyboard interaction. Do not remove all outlines globally. Keep a fallback browser indicator, and check that your custom outline remains visible against each surface and is not clipped by overflow.

`:focus-within` matches a container when it or a descendant has focus; it can highlight a group without replacing each control's focus indicator. `:checked` styles selected checkbox or radio states. `:disabled` matches truly disabled native controls. A disabled-looking class alone does not prevent activation, while `aria-disabled` communicates a state but still requires behavior management.

`:invalid` can match before a person interacts. In a production form, consider when errors should appear and provide associated error text. CSS cannot implement complete validation feedback or server validation by itself. `:user-invalid` can offer interaction-aware styling where supported, but the form must remain understandable without that enhancement.

## Exercise and checks

Add a second button with the `disabled` attribute and style it distinctly:

```css
button:disabled {
  background: #e2e8f0;
  color: #475569;
  border-color: #94a3b8;
  cursor: not-allowed;
}
```

Place this rule after the hover rule. Verify the disabled button cannot activate and is skipped in ordinary Tab navigation. Remove the attribute and observe that appearance and behavior both change. Finally, zoom to 200% and ensure labels, helper text, and focus rings remain visible.
