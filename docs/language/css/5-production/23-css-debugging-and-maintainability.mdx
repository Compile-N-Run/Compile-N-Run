# Debugging and Maintaining CSS

A useful CSS debugging process follows the browser's decisions. First establish whether the stylesheet loaded, then whether the selector matched, then which declaration won, then how the winning value participates in layout. Skipping straight to `!important` often changes the symptom while hiding the cause.

## Work through a real failure

In a fresh practice page, use this deliberately broken example:

```html
<div class="layout">
  <article class="card">
    <h1>Export</h1>
    <p class="filename">export01234567890123456789012345678901234567890123456789.json</p>
  </article>
</div>
```

```css
.layout { display: flex; width: 18rem; max-width: 100%; }
.card { flex: 1; padding: 1rem; border: 2px solid #234e9b; }
.filename { color: navy; }
p { color: green; }
```

At a narrow width, the card can overflow because its automatic minimum size is influenced by the unbroken filename. The filename is navy because its class selector beats the later type selector. These are separate failures to reason about, even if they appear in the same screenshot.

Inspect the paragraph in developer tools. The Styles panel shows matching declarations and crossed-out overrides. The Computed panel shows resolved property values, and the box-model diagram shows dimensions, padding, and borders. A flex overlay helps identify the parent layout and its available space.

Apply this targeted fix:

```css
.card { min-inline-size: 0; }
.filename { overflow-wrap: anywhere; }
```

The item can shrink, and its content has a wrapping policy. Neither rule needs importance. If you intended the paragraph to be green, edit the component's color declaration or its token instead of escalating selector strength.

## Use a repeatable investigation order

1. Check the Network panel for the stylesheet and confirm its path, response, and contents.
2. Inspect the exact element and verify the selector matches its real classes and relationships.
3. Check invalid values, active conditions, layers, specificity, and source order.
4. Inspect the winning computed value and the parent layout mode.
5. Check box dimensions, content minimums, overflow, containing blocks, and stacking contexts as relevant.
6. Disable one suspected declaration, observe the result, and copy the smallest successful correction into the source file.

Developer-tools edits are experiments, not saved source changes. Reload after saving to verify the fix survives.

## Organize for change

For a modest project, one stylesheet with a clear order is enough: design tokens, reset and base elements, layouts, components, utilities, then contextual adaptations near the relevant component. Cascade layers can make this ordering explicit, but remember that normal unlayered rules outrank layered ones.

Use component names that describe a role. A `.course-card` can move from a dashboard to a search page; `.left-blue-box` encodes details likely to change. Keep variants local and document the reason for non-obvious constraints, such as `min-inline-size: 0` on a shrinking content region.

Remove obsolete rules once a fix is understood. Appending another override every time eventually creates a stylesheet where no declaration can be evaluated in isolation.

## Exercise and review criteria

Repair the example without changing its HTML, without hiding page overflow, and without importance. Then add a second long filename and increase text size. Both should remain readable inside the card.

Before shipping a page, check narrow and wide widths, keyboard focus, zoom, longer content, color preferences, and reduced motion. Use an additional browser engine when available. Automated checks help, but they do not replace reading the page and operating its controls.
