# Container Queries for Reusable Components

A viewport query can tell you whether the page is wide, but not whether a card sits in a narrow sidebar. A container query lets descendants adapt to an eligible ancestor's size. That makes one component useful in several layouts without assigning a separate class for every location.

Start with a good compact component that works without the query. Then enhance its internal arrangement when its container has enough space.

## Query a wrapper, style its descendant

Place this markup in a fresh starter document and use the stylesheet below:

```html
<div class="examples">
  <div class="course-slot">
    <article class="course-card">
      <div class="course-icon" aria-hidden="true">CSS</div>
      <div><h2>Layout practice</h2><p>Build a flexible course card.</p></div>
    </article>
  </div>
  <div class="course-slot course-slot--narrow">
    <article class="course-card">
      <div class="course-icon" aria-hidden="true">CSS</div>
      <div><h2>Layout practice</h2><p>The same card in a narrow slot.</p></div>
    </article>
  </div>
</div>
```

```css
* { box-sizing: border-box; }
body { margin: 0; padding: 1rem; font: 1rem/1.6 system-ui; }
.examples { display: grid; gap: 1rem; }
.course-slot { container: course / inline-size; }
.course-slot--narrow { max-inline-size: 18rem; }
.course-card {
  display: grid;
  gap: 1rem;
  padding: 1rem;
  border: 1px solid #94a3b8;
}
.course-card h2 { margin: 0; }
.course-icon {
  display: grid;
  place-items: center;
  min-block-size: 4rem;
  background: #dbeafe;
  color: #172033;
  font-weight: 700;
}
@container course (min-width: 26rem) {
  .course-card {
    grid-template-columns: 5rem minmax(0, 1fr);
    align-items: center;
  }
}
```

On a wide page, the first card becomes a horizontal icon-and-text layout. The narrow card stays stacked even though it shares the same viewport. The query evaluates the nearest eligible ancestor named `course` for each card.

## Why the wrapper matters

The container establishes the queryable size, and the rule styles descendants. A size query does not use an element's own container declaration to style that same element based on its own resulting size. Separating `.course-slot` from `.course-card` avoids that circular relationship.

`inline-size` containment is useful because it makes the inline size queryable while allowing the block dimension to grow with content. It also changes intrinsic sizing behavior: make sure the wrapper receives a meaningful width from its parent layout. A shrink-to-fit container without a suitable size can produce surprising results.

Naming the container is optional, but useful in nested layouts. It makes the intended ancestor relationship explicit instead of accidentally querying a nearer unrelated container.

## Progressive enhancement and testing

If a browser does not apply the container query, this card remains a readable stacked component. That fallback is already defined outside the conditional rule. Avoid placing essential content or the only usable layout inside a query.

Test by changing the wrapper width while keeping the viewport fixed. This distinguishes a genuine component adaptation from a viewport-based effect. Developer tools can help identify which ancestor is the active query container.

## Exercise and solution

Add a third slot limited to `30rem` and put it inside a wide page. It should become horizontal when its actual inline size crosses `26rem`, while the `18rem` slot remains stacked.

```css
.course-slot--medium { max-inline-size: 30rem; }
```

Use a longer title and verify the second column wraps rather than overflowing. The `minmax(0, 1fr)` track allows shrinkage; `overflow-wrap: anywhere` can be added for truly unbreakable content. Next, give these cards reusable [design tokens](./20-css-custom-properties.mdx).
