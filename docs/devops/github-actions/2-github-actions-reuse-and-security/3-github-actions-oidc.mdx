# GitHub Actions OIDC and Cloud Identity

OpenID Connect lets a workflow prove aspects of its execution identity to an external service. A configured cloud provider can exchange that proof for short-lived credentials instead of requiring a long-lived cloud key stored in the repository.

**Prerequisites:** [Permissions and secrets](./1-github-actions-permissions-and-secrets.mdx) and [fork safety](./2-github-actions-fork-safety.mdx). This lesson describes configuration boundaries; it does not deploy resources or create cloud trust automatically.

## Follow the identity exchange

GitHub's identity token contains claims about the run. A provider verifies the issuer, audience, signature, and relevant claims, then decides whether to issue credentials and which permissions they should have.

The critical decision is the provider's trust policy. It should restrict the intended repository and approved branch, tag, or environment context. A policy that trusts every token from GitHub ignores the distinction between your reviewed workflow and someone else's repository.

A deployment job may need this shape:

```yaml
permissions:
  contents: read
jobs:
  deployment-plan:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - name: Explain configuration boundary
        run: printf '%s\n' 'Provider trust and a provider login action are required.'
```

This is a job fragment, not a working cloud deployment. It deliberately contains no provider login or resource-changing command. `id-token: write` allows a job to request an OIDC token; it does not by itself grant permission to modify cloud resources.

## Constrain both sides

On GitHub, use a trusted event, a protected environment where appropriate, and minimal job permissions. On the cloud side, constrain the identity claims and grant a narrowly scoped role. A workflow `if` condition helps express intent, but the provider's policy must independently enforce the identity it accepts.

Environment-based identity subjects differ from branch-based subjects. If a job starts referencing an environment, revisit the provider's expected claims instead of assuming the previous branch condition still matches the subject format.

Use the provider's official integration instructions for audience values, role identifiers, and the login action. These details differ among providers and cannot be replaced safely by one universal copy-and-paste credential block.

## Keep the execution chain trusted

Short-lived credentials reduce the lifetime of a leaked credential, but code running during that lifetime can still use its authority. Do not check out an unreviewed pull-request revision in an OIDC-enabled deployment job. Review third-party action pins and any downloaded executable artifacts in that job too.

Never print identity tokens into logs to debug a trust mismatch. Inspect nonsecret configuration, documented claim formats, and provider error messages instead.

## Practice and solution

List the controls needed before turning the fragment into deployment: a real environment and protection rules, a provider trust policy restricted to the expected identity, a least-privilege cloud role, and a reviewed provider login implementation. The correct answer separates permission to request a token from permission to act on a cloud resource.
