# GitHub Actions Fork and Pull Request Safety

A pull request can change executable code: tests, package scripts, build configuration, and workflow-related inputs. Treat that contribution as untrusted until the repository's review and merge process establishes otherwise.

**Prerequisites:** [Events](../0-github-actions-foundations/2-github-actions-events.mdx) and [permissions](./1-github-actions-permissions-and-secrets.mdx).

## Keep contribution testing unprivileged

A normal test workflow should use `pull_request`, read-only permissions, and no deployment secrets. GitHub restricts secrets and token capabilities for ordinary fork pull requests, subject to repository policies and settings. Do not design tests that require production credentials to evaluate a proposed change.

```yaml
name: Contribution tests
on:
  pull_request:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: '22'
          package-manager-cache: false
      - run: npm ci --ignore-scripts
      - run: npm test
```

Even with install scripts disabled, `npm test` executes code supplied by the pull request. The useful boundary is that this job has no sensitive deployment authority, not that its commands are inherently safe.

## Understand the privileged trigger

`pull_request_target` runs in the base-repository context and is intended for carefully designed trusted operations such as metadata handling. Do not switch a test workflow to it simply to obtain secrets or write permissions, then check out and execute the pull request's head code.

That pattern gives untrusted code a privileged execution environment. The danger also includes indirect execution: package installation, build scripts, local actions, and downloaded artifacts can all carry attacker-controlled behavior. Keeping the workflow YAML on the base branch does not make checked-out contribution code trusted.

## Keep external text out of shell source

Pull-request titles, branch names, and other event fields can contain special characters. Pass them as data through environment variables rather than interpolating expressions into the body of `run`:

```yaml
- name: Show pull request title
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: printf '%s\n' "$PR_TITLE"
```

The fixed printf format and quoted argument preserve the value as text. Do not later evaluate that text as a command or use it as an unchecked executable argument.

## Protect other trust boundaries

Do not execute an untrusted artifact in a privileged follow-up workflow just because the producing workflow completed. Self-hosted runners need special care because a contribution may reach persistent files, credentials, or internal networks.

## Practice and check

Review a workflow that uses `pull_request_target`, checks out `github.event.pull_request.head.sha`, and runs tests with a cloud secret. A correct review rejects that trust arrangement and moves contribution tests to an unprivileged pull-request workflow. It does not attempt to fix the design merely by hiding the secret from log output.
