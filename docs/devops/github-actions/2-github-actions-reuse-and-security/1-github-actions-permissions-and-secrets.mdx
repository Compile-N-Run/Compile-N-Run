# GitHub Actions Permissions and Secrets

A workflow can execute repository code and third-party actions. Its permissions and secrets determine what that code can reach. A test job should not receive release or deployment authority merely because another job needs it.

**Prerequisites:** [Runners and contexts](../0-github-actions-foundations/3-github-actions-runners-and-expressions.mdx). No secret is needed for the course's CI capstone.

## Start with a small token scope

For read-only checkout and tests, declare:

```yaml
permissions:
  contents: read
```

The `GITHUB_TOKEN` is provided for workflow authentication, subject to repository, event, and organization policy. Explicit permission configuration avoids relying on a broad default. When you specify permissions, unspecified scopes are generally set to none, apart from platform-defined exceptions described in the reference.

Grant additional permissions only to the job that needs them. A job that creates a release might require a write scope, but that is a different responsibility from a job testing untrusted contributions.

Disabling checkout's persistent credentials reduces later Git access through its checkout configuration. It does not revoke all token availability to actions, and it is not a substitute for least-privilege job permissions.

## Treat secrets as authority, not ordinary configuration

Repository or environment secrets can hold credentials. Reference a secret only where required, typically through a step-level environment variable consumed by a fixed trusted command. Do not print it, embed it in a URL that enters logs, or upload a workspace containing a generated credential file.

GitHub masks many registered secret values in logs, but masking is not a complete data-loss prevention system. Transformed values, structured data, or accidental artifacts can still reveal information. Avoid producing the sensitive output in the first place.

Public settings such as a runtime version belong in normal variables or workflow configuration. Putting every nonsecret value in the secret store makes configuration harder to inspect without adding meaningful protection.

## Review who controls executed code

An action receives the job environment and can execute with its available authority. Pin actions to reviewed full commit SHAs when you need an immutable dependency reference, and maintain those pins as fixes are released. A verified owner or popular repository is useful evidence, not a guarantee that every future tag points to identical code.

Installation scripts and test scripts from the checked-out project also execute code. Keeping a secret out of one explicit step is insufficient if a prior untrusted step can alter scripts that later run with elevated credentials on the same runner.

## Practice and solution

Review a hypothetical workflow where a top-level `contents: write` exists only because one release job needs it. Move the write permission to the release job and give the test job read-only contents. Then remove any deployment secrets from the test job's environment. Explain which code can access each credential after the change.
