# GitHub Actions Reusable Workflows

A reusable workflow lets several callers share complete job behavior. It is useful when installation, testing, and permissions should follow the same reviewed contract across repositories or workflow entry points.

**Prerequisites:** [Node CI](../1-github-actions-continuous-integration/0-github-actions-node-ci.mdx). The called file must live directly in `.github/workflows` in the practice repository.

## Define the called workflow

Save `.github/workflows/node-check.yml`:

```yaml
name: Reusable Node check
on:
  workflow_call:
    inputs:
      node-version:
        required: false
        type: string
        default: '22'
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ inputs.node-version }}
          package-manager-cache: false
      - run: npm ci --ignore-scripts
      - run: npm test
```

A second file can call it:

```yaml
name: Pull request checks
on:
  pull_request:
permissions:
  contents: read
jobs:
  checks:
    uses: ./.github/workflows/node-check.yml
    with:
      node-version: '22'
```

The reusable workflow is invoked at job level, not as a step. The caller does not also attach ordinary `runs-on` and `steps` to that calling job. The called workflow supplies its own jobs.

## Design a narrow interface

Inputs should represent deliberate variation, such as the runtime version. Avoid accepting an arbitrary shell command as an input merely to make the workflow “flexible.” That turns a shared implementation into a general execution surface and makes its security contract difficult to review.

Use declared secrets when the workflow genuinely needs them. Passing secrets explicitly shows what authority crosses the boundary. `secrets: inherit` can be convenient in supported arrangements but broadens implicit coupling; a simple test workflow should need no secrets at all.

A called workflow cannot use this mechanism to elevate its token permissions beyond what its caller permits. Keep permissions minimal in both definitions and inspect the whole call chain when diagnosing access failures.

## Choose the appropriate reuse level

Reusable workflows share jobs. A composite action shares a collection of steps within a caller's job. A normal script shares application logic and can also run locally. Prefer a script for a check that should not depend on Actions-specific execution.

For a workflow in another repository, use the documented repository/path/ref syntax and pin an audited immutable commit when stability matters. A local relative call follows the caller's repository revision, which makes changes reviewable together.

## Practice and check

Create two caller jobs that choose Node 22 and Node 24. Predict that each invokes the same test implementation with a different input. Confirm the interface contains no secret or command-string parameter because the tests do not require them. Locally validate file paths and YAML, while recognizing that hosted invocation requires an actual Actions run.
