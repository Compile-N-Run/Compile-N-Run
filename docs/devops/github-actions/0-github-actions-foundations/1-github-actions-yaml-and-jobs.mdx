# GitHub Actions YAML, Jobs, and Steps

Workflow YAML is a structured document. Indentation determines which settings belong to the workflow, a job, or a step. A syntactically valid YAML file can still be an invalid Actions workflow if keys appear at the wrong level.

**Prerequisites:** [Actions Introduction](./0-github-actions-introduction.mdx). Use a practice repository with a Node package and test script, or use the course capstone files later.

## Read the hierarchy

```yaml
name: Node checks
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: Check out source
        uses: actions/checkout@v7
        with:
          persist-credentials: false
      - name: Select Node
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          package-manager-cache: false
      - name: Run tests
        run: npm test
```

`jobs` is a mapping whose `test` key identifies a job. `steps` is a sequence, indicated by hyphens. `with` passes inputs to an action; `run` supplies shell source. Do not put `run` and `uses` in the same step to try to extend an action. Add another step.

The official action repositories advertised version 7 for checkout and setup-node when these examples were checked in October 2026. Major tags are readable learning references but can move; a security-conscious production workflow should pin an audited full commit SHA and maintain it. Consult each action's runner compatibility requirements, particularly for self-hosted machines.

## Files are not present automatically

A hosted runner is not automatically your repository checkout. The checkout action makes source available in its workspace. The setup action selects the project's Node version; that is separate from the JavaScript runtime used internally to execute the action itself.

This example assumes the package has no third-party dependencies. For a dependency-bearing package, install from its lockfile before testing, as described in the [CI lesson](../1-github-actions-continuous-integration/0-github-actions-node-ci.mdx).

## Use readable scalar values

Quote version strings so values such as `22` or `1.10` are treated as intended rather than relying on YAML numeric interpretation. Use spaces for indentation. A multiline shell script uses `run: |`, followed by more-indented command lines.

Do not confuse YAML validation with shell validation. A workflow can parse correctly but fail because its shell command is malformed, its working directory is wrong, or an executable is missing.

## Practice and solution

Add a step named “Show runtime” after setup-node with `run: node --version`. It should print a Node 22 version before tests run. If you put the step before setup-node, the runner's preinstalled runtime might be used instead, which does not verify your selected version.

Then explain why moving `timeout-minutes` under `with` would change its meaning: it would become an action input, not the job timeout you intended.
