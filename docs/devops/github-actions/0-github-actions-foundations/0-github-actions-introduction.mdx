# GitHub Actions Introduction

GitHub Actions runs repository automation in response to events. A common use is continuous integration: check out a proposed change, install the expected runtime, and run the same tests a developer runs locally.

**Prerequisites:** Basic Git commits and branches, a GitHub repository you control, and familiarity with terminal commands. The [Git course](/docs/devops/git) and [Node.js course](/docs/framework/nodejs) provide useful background. You can read and validate the supplied examples locally without enabling any hosted workflow.

## Follow one run from event to result

A workflow is a YAML file describing when work starts and which jobs run. A job runs on a runner, which is the machine executing the work. Steps within a normal job execute in sequence. Jobs can run independently unless you declare dependencies between them.

An action is reusable automation referenced by a `uses` step. A `run` step executes commands in a shell. Neither is inherently harmless: both can execute code with the job's available permissions and credentials.

Create this file as `.github/workflows/hello.yml` only in your own practice repository when you intend to enable it:

```yaml
name: Hello workflow
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  hello:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Print a greeting
        run: printf '%s\n' 'Hello from a runner'
```

This workflow has a manual trigger and no checkout. It prints a constant message, so it does not need repository files. After committing it to the repository's default branch with Actions enabled, an authorized user can start it from the Actions interface. The log should contain `Hello from a runner`.

## Separate configuration from activation

The website's supplied workflows live under `static/examples/github-actions/`; they are downloadable teaching files, not active workflows for this website. Saving a YAML example in an arbitrary directory does not make GitHub run it. A live workflow belongs directly under `.github/workflows` in the target repository.

Local YAML validation can catch syntax mistakes but does not prove the hosted runner can access an action or that your repository's policies permit execution. This course identifies those boundaries rather than claiming a live run occurred from a local check.

## Understand costs and authority

Runner availability, usage limits, and billing depend on the account, repository, and runner type. Check your own settings before enabling expensive matrices or frequent schedules. Start with a small job and a timeout.

A passing run means its configured commands succeeded for that run's source and environment. It is not proof that every application behavior was tested or that deployment is safe.

## Practice and solution

Rename the workflow and greeting step, leaving their functions unchanged. Explain which name appears for the entire automation and which identifies one operation in the job log. Add a second constant print step and predict its order: it should run after the first succeeds.
