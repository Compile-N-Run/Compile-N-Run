# GitHub Actions Events and Filters

An event determines when a workflow is considered for execution and what context it receives. Choose it based on the work's purpose and trust boundary, then add filters carefully.

**Prerequisites:** [Workflow structure](./1-github-actions-yaml-and-jobs.mdx). The following fragment replaces the top-level `on` block of a practice CI workflow.

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
```

This checks pushes to main and pull requests targeting main, plus manual requests. For pull requests, the branch filter refers to the base branch, not the contributor's feature branch. A pull request from `feature/forms` into `main` matches.

## Know which revision is checked

For ordinary `pull_request` workflows, checkout commonly tests GitHub's pull-request merge ref. This helps detect integration failures with the base branch. If you intentionally check the head commit instead, document why and understand the event's context rather than assuming every `github.sha` is the contributor's latest commit.

The default pull-request activity set includes opening, reopening, and synchronizing changes. Additional activity types can be configured when needed. Do not add every type merely because it exists; unnecessary runs consume attention and resources.

Fork pull requests have restrictions on secrets and token permissions. Those restrictions are useful boundaries, not inconveniences to bypass by switching to a more privileged trigger. The [fork-safety lesson](../2-github-actions-reuse-and-security/2-github-actions-fork-safety.mdx) covers that distinction.

## Apply path filters with care

For a non-required specialized check, you might use:

```yaml
on:
  pull_request:
    paths:
      - 'src/**'
      - 'test/**'
      - 'package*.json'
      - '.github/workflows/**'
```

If both branch and path filters are present, both conditions must match. Include files that influence the job, such as workflow configuration and lockfiles, not only application code.

A workflow skipped by filters can leave an expected required check pending and block merging. For a mandatory check, often it is better to run the workflow consistently and make internal job decisions carefully. Test the behavior with your repository's actual branch rules before relying on it.

## Schedules are not precise clocks

A schedule uses cron syntax and UTC by default; current GitHub documentation also supports an optional IANA `timezone` setting. Review daylight-saving behavior when using a local timezone. Scheduled runs can be delayed and are not a hard real-time service. Scheduled workflows operate under default-branch rules documented by GitHub; changing a schedule in an unmerged feature branch does not make it an independent scheduler.

Avoid scheduling a learning job every few minutes. A manual trigger is easier to inspect while you are developing the workflow.
