# GitHub Actions Runners, Contexts, and Expressions

GitHub evaluates workflow expressions to configure a run; a runner later executes shell commands. These are different evaluation layers, and confusing them can create both bugs and injection risks.

**Prerequisites:** [Events](./2-github-actions-events.mdx). The example below is a step inside a job running on `ubuntu-latest`.

```yaml
- name: Describe the run
  env:
    EVENT_NAME: ${{ github.event_name }}
    REF_NAME: ${{ github.ref_name }}
  run: |
    printf 'Event: %s\n' "$EVENT_NAME"
    printf 'Ref: %s\n' "$REF_NAME"
```

The expressions fill environment values. The shell expands the quoted variables when the step executes. Passing potentially external text as an environment variable avoids inserting it directly into shell source. Still use the value safely: do not feed it into `eval` or treat it as a command later.

## Understand runner isolation

GitHub-hosted jobs normally receive fresh environments. Files and exported shell variables from one job are not automatically available in another. Steps within a job share its workspace, but each `run` step starts a separate shell process.

A plain `export MODE=test` inside one step does not persist to the next shell. Use workflow or job `env` for fixed configuration, or documented environment files when computing values for later steps.

Runner labels choose an environment; `ubuntu-latest` tracks an evolving image rather than an immutable machine snapshot. For reproducibility, explicitly select language runtimes and dependencies, then record actual versions in logs when troubleshooting.

Self-hosted runners have different cleanup, network, and persistence considerations. Do not run untrusted fork code on a machine with valuable credentials or internal network access merely because it has a matching label.

## Use conditions and outputs explicitly

A job or step can have an `if` condition:

```yaml
- name: Main branch message
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  run: printf '%s\n' 'This is a push to main'
```

This controls whether a step runs; it is not an authorization policy for a cloud account. More privileged operations need scoped credentials and external trust rules too.

For a computed value needed by a later step, write a named output to the file identified by `GITHUB_OUTPUT`, then read it through the producing step's ID. Avoid the obsolete `::set-output` command. Use the documented multiline format for multiline values rather than assuming a newline-free string.

## Practice and solution

Add two steps. In the first, set a shell variable normally. In the second, try to read it, then fix the example by defining it at job-level `env`. The fixed value should be available to both steps. Explain why a file created in the workspace may survive between those steps while a shell-local variable does not.
