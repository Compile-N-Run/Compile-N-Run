# GitHub Actions Dependency Caching

A cache stores reusable intermediate data to avoid downloading or computing it repeatedly. It is an optimization: the workflow must remain correct when the cache is absent, stale, or unavailable.

**Prerequisites:** [Node CI](./0-github-actions-node-ci.mdx) and a committed lockfile. The dependency-free capstone does not need caching; use this pattern when a real dependency tree makes it worthwhile.

## Cache npm's download data

Replace the setup-node step with:

```yaml
- uses: actions/setup-node@v7
  with:
    node-version: '22'
    cache: npm
    cache-dependency-path: package-lock.json
- run: npm ci --ignore-scripts
- run: npm test
```

The action's npm cache support caches package-manager data, not the installed `node_modules` directory. You still run `npm ci` to create the correct installation from the lockfile. A cache hit is not evidence that the workspace already has valid dependencies.

The dependency path tells the action which lockfile influences its cache key. If the package lives in a subdirectory, point to that lockfile and set the installation step's working directory appropriately. Merely changing one of those paths leaves the workflow looking in inconsistent locations.

## Treat a miss as normal

The first eligible run often has no cache. Installation should still succeed by obtaining dependencies normally. Later runs may reuse cached package data. Do not make application correctness depend on a successful restore or on one particular cache-hit message.

Lockfile changes should naturally produce different dependency keys. Cache scopes and restore rules determine which branches and events can access entries; review GitHub's documented behavior before sharing a cache across trust boundaries.

Some setup-node configurations can enable automatic package-manager caching based on package metadata. This course sets `package-manager-cache: false` in its basic no-cache examples so the intended behavior is explicit. When caching is useful, configure it deliberately rather than inheriting it unknowingly.

## Keep sensitive data out

Do not cache credentials, environment files containing secrets, private signing keys, or arbitrary workspace snapshots. Pull-request and branch cache access rules can make cache contents available in contexts you did not intend.

A cache is also not a release artifact. You should be able to recreate build output from reviewed source and locked dependencies. Downloading a cache and deploying its unverified contents bypasses that relationship.

If an installation only succeeds after restoring `node_modules`, investigate missing setup steps or undeclared dependencies. Clearing a cache may expose a real reproducibility problem rather than causing one.

## Practice and check

Write down the behavior you expect on a cache miss and a cache hit. Both should install from the same lockfile and run the same tests; only download or computation time should differ. For a package in `app/`, a correct setup uses `cache-dependency-path: app/package-lock.json` and runs npm commands with `working-directory: app`.
