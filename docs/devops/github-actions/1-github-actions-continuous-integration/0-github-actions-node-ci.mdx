# GitHub Actions Node.js CI

A reliable CI job repeats the project's documented local checks in a clean environment. It should fail on a broken test or an inconsistent dependency manifest rather than making the build appear successful.

**Prerequisites:** [Workflow structure](../0-github-actions-foundations/1-github-actions-yaml-and-jobs.mdx). Your repository root must contain `package.json`, a matching `package-lock.json`, and a working `test` script. The [capstone project](../3-github-actions-operations-and-project/3-github-actions-ci-project.mdx) supplies all three.

## Assemble the complete workflow

```yaml
name: Node CI
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: '22'
          package-manager-cache: false
      - name: Install locked dependencies
        run: npm ci --ignore-scripts
      - name: Run behavioral tests
        run: npm test
```

Store it as `.github/workflows/ci.yml` in your practice repository when you intend to activate CI. These action majors were checked against their official repositories in October 2026. Use reviewed full-SHA references when adopting a stricter production dependency policy.

## Understand every operation

Checkout places the selected revision in the workspace. Disabling persistent Git credentials avoids leaving checkout's authentication configured for later Git commands; it does not make all other job credentials disappear.

Setup-node selects the application runtime. `npm ci` installs from the committed lockfile and fails if it is inconsistent with the manifest. The supplied project needs no install scripts, so `--ignore-scripts` reduces unnecessary execution. Real packages may require lifecycle steps; review those needs rather than removing the flag reflexively.

The test command must return a nonzero exit code when a test fails. Do not append `|| true` or apply `continue-on-error` to required checks just to get a green badge. That changes the meaning of success.

## Reproduce locally first

In a clean copy of the project, run the same installation and test commands. If the local command already fails, investigate that before debugging Actions YAML. If it succeeds locally but fails remotely, compare runtime versions, filesystem case sensitivity, environment configuration, and generated files.

Do not rely on an uncommitted fixture or a globally installed tool. The runner only receives what checkout and subsequent setup steps provide. A lockfile belongs in version control; `node_modules` does not replace it.

## Practice and solution

Change one assertion in a practice branch so a test fails, then restore it. Locally, the test command should change from success to failure and back. If you enable the workflow in your own repository, verify the same transition in the run log. A local check alone does not prove that a hosted run actually happened.
