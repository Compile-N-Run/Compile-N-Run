# GitHub Actions Matrix Testing

A matrix expands one job definition into multiple jobs with different inputs. It is useful when your package claims support for several runtime versions or operating systems, but every extra combination should have a reason.

**Prerequisites:** [A working Node CI job](./0-github-actions-node-ci.mdx). Replace its test job with this example while retaining the top-level event and permissions configuration.

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    timeout-minutes: 10
    strategy:
      fail-fast: false
      max-parallel: 2
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: ['22', '24']
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          package-manager-cache: false
      - run: npm ci --ignore-scripts
      - run: npm test
```

The two operating systems and two Node versions create four jobs. `max-parallel: 2` limits this matrix's simultaneous jobs, while account-level concurrency limits may impose additional constraints. `fail-fast: false` allows the other combinations to finish when one fails, which helps compare compatibility problems.

## Test the support policy

At the course's verification date, Node 22 and 24 are supported LTS lines. Testing both is useful if the package claims compatibility with them. It does not establish compatibility with every older runtime or with the newest Current release.

A Windows job can reveal hardcoded path separators or shell-specific assumptions. Use cross-platform application commands when possible. If a step needs Bash explicitly, specify the shell and confirm that the runner provides it rather than assuming every runner uses the same default shell.

## Keep matrices affordable and readable

A third dimension multiplies the job count. Two operating systems, two Node versions, and three database versions would create twelve combinations. Start with the smallest set that tests meaningful differences.

Use `exclude` to remove combinations you intentionally do not support, and `include` for targeted additional configurations. Document the reason for exceptions. Excluding the one combination that fails without adjusting your support policy hides a defect.

Artifacts uploaded by matrix jobs need distinct names, such as a name containing both operating system and runtime. Otherwise different jobs may collide while uploading results.

## Practice and solution

Add macOS to the operating-system list. Predict the new job count before running: six. Then restrict the matrix to Ubuntu on both Node versions plus Windows on Node 24 using appropriate `exclude` entries for macOS combinations and Windows on Node 22. The intended result is three combinations.

Explain why `fail-fast: false` is not the same as accepting failures: unsuccessful jobs still fail the workflow; they simply do not cancel their matrix siblings early. Keep experimental allowed failures separate and explicit if your project actually needs them.
