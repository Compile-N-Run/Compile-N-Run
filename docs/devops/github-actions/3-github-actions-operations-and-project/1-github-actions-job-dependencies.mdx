# GitHub Actions Job Dependencies and Concurrency

Jobs run independently unless you define their relationships. A dependency graph makes prerequisites explicit, while concurrency settings control overlapping runs that would otherwise compete for resources.

**Prerequisites:** [Workflow structure](../0-github-actions-foundations/1-github-actions-yaml-and-jobs.mdx) and [artifacts](../1-github-actions-continuous-integration/3-github-actions-artifacts.mdx).

## Express a prerequisite with needs

```yaml
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - run: printf '%s\n' 'Replace this demonstration with unit tests.'
  integration:
    needs: unit
    runs-on: ubuntu-latest
    steps:
      - run: printf '%s\n' 'The prerequisite job succeeded.'
```

This job fragment demonstrates ordering only; the constant messages are not actual tests. The integration job waits for the unit job and ordinarily does not run if its prerequisite fails. Do not create a chain merely to make independent checks look ordered: parallel checks can finish sooner and provide more useful feedback.

`needs` does not transfer the first job's filesystem. If the next job requires a generated bundle, publish and download a deliberately named artifact using compatible action versions. If it requires only a small string, use a declared job output connected to a step output.

## Define a useful concurrency group

For CI where a newer run supersedes an older run for the same workflow and reference, add this top-level setting:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

Including the workflow name avoids unintentionally grouping unrelated workflows that share a branch. Different pull-request refs normally get distinct groups. Review your chosen event's ref semantics rather than assuming every event identifies a branch in the same way.

Canceling obsolete tests can reduce wasted runner time. It also means those runs may not produce final reports, so artifact steps should account for cancellation appropriately.

## Cancellation is not a transaction

For deployments, cancellation can interrupt an operation after some external changes have occurred. Do not copy a CI cancellation policy into production deployment without considering recovery and rollback.

A concurrency group is not a durable first-in-first-out queue guaranteeing every deployment runs. GitHub's pending-run replacement and ordering behavior must be considered when every requested release matters. An external release coordinator or explicit deployment policy may be needed for stronger guarantees.

## Practice and solution

Draw the intended job graph for linting and unit tests that can run independently, followed by packaging that requires both. The packaging job should declare `needs: [lint, unit]`; lint and unit should not depend on each other.

Then decide whether an old packaging run may be canceled when a newer commit arrives. For ordinary PR feedback the answer is often yes, but for an already-started external release it requires a separate safety decision. Explain the difference in terms of side effects rather than job names alone.
