# GitHub Actions Troubleshooting and Local Validation

A failed automation can result from invalid configuration, the wrong event, unavailable resources, or a real application defect. Identify which layer failed before changing permissions or rerunning repeatedly.

**Prerequisites:** [Node CI](../1-github-actions-continuous-integration/0-github-actions-node-ci.mdx) and [permissions](../2-github-actions-reuse-and-security/1-github-actions-permissions-and-secrets.mdx).

## Start with whether the run exists

If no run appears, inspect the workflow path, event configuration, branch and path filters, default-branch requirements for the trigger, and repository Actions policy. A command cannot fail on a runner that was never scheduled.

If the workflow is rejected before jobs start, read the configuration diagnostic and validate YAML structure. Keys can be valid YAML while appearing at an invalid Actions level. Duplicate mapping keys should be treated as defects, not as a clever override mechanism.

## Find the first useful failure

Open the failed job and expand the first failing step. Record the source revision, runtime version, working directory, exact command, and exit status. Later failures may be consequences: an upload step missing a report does not explain why runtime setup failed earlier.

For the Node capstone, reproduce the commands locally:

```bash
node --version
npm ci --ignore-scripts
npm test
```

If the failure only occurs on the runner, compare case-sensitive paths, line endings, platform-specific shell syntax, environment configuration, and absent untracked files. Do not solve an undeclared dependency by adding a global installation with an unspecified version.

## Treat permission errors as policy evidence

A 403 can mean the operation exceeds the token's scope or is restricted by the event. A fork test job missing a deployment secret may be functioning exactly as intended. Do not automatically increase top-level permissions or change to `pull_request_target` to make the error disappear.

Likewise, a self-hosted runner stuck waiting may have a label, connectivity, or compatibility issue. The major version of a JavaScript action can require a newer runner; selecting an application Node version with setup-node does not upgrade the runner service itself.

## Use local checks honestly

A YAML parser checks structure. A workflow-aware linter can catch additional expression or schema mistakes. Running shell commands locally checks some program behavior. None reproduces all hosted event contexts, repository policies, secret availability, action downloads, or artifact services.

Avoid printing an entire context object or environment while debugging; it can contain sensitive material. Add narrowly targeted diagnostics and remove unnecessary debug output when the issue is resolved.

## Practice and solution

Diagnose these cases: `npm ci` reports a manifest mismatch; checkout is denied by policy; tests cannot find `Sample.json` although the repository contains `sample.json`.

The appropriate fixes are to reconcile and commit the manifest and lockfile, inspect the configured action/token policy, and correct the filename's case. None requires ignoring test failures. Rerun only after a change or a credible transient cause gives the retry a purpose.
