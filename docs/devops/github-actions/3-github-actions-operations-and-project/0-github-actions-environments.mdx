# GitHub Actions Environments and Approvals

An environment names a deployment target such as staging or production. It can associate protection rules and configuration with the job that targets it. A test passing and a deployment being authorized are different decisions.

**Prerequisites:** [OIDC and cloud identity](../2-github-actions-reuse-and-security/3-github-actions-oidc.mdx). This lesson uses a nondeploying demonstration. It does not create a real environment or change an external service.

## Reference an environment deliberately

This complete manual workflow shows the job-level relationship:

```yaml
name: Environment demonstration
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  explain:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    environment: training
    steps:
      - run: printf '%s\n' 'This job demonstrates an environment gate only.'
```

Before enabling it in a practice repository, inspect or create the `training` environment in repository settings and configure the desired protection rules. Merely writing `environment: training` does not prove required reviewers or branch restrictions are already configured.

Availability of environment features and protection rules depends on repository visibility and plan. Check your own repository settings and current GitHub documentation instead of assuming every account exposes identical controls.

## Put the gate before sensitive work

When a job requires environment approval, the gate applies before that job's protected execution and access to environment secrets. Keep deployment credentials at the appropriate environment or job boundary; do not expose them to an earlier unprivileged test job simply because deployment comes later.

A reviewer should know what source revision and artifact are being approved. A vague “approve production” prompt without a traceable commit or build result makes it difficult to assess the actual change.

Configure who can approve, whether self-review is permitted, which branches or tags may deploy, and whether administrators can bypass rules according to your policy. These are repository settings, not implied by a green CI check.

## Combine controls without confusing them

Branch protection governs how changes reach a protected branch. Environment protection governs jobs targeting a deployment environment. Cloud trust and permissions govern external operations after authentication. Each can reinforce the others, but none automatically creates all the others.

For example, an environment label does not grant cloud access. An OIDC role does not guarantee that a human approved the intended artifact. A successful test suite does not prove a database migration can be rolled back safely.

Keep the course capstone focused on CI; adding deployment is a separate feature requiring concrete targets, credentials, and rollback expectations.

## Practice and check

Review the demonstration workflow and name the configuration it cannot establish by itself. A correct answer includes reviewer requirements, branch restrictions, and environment-secret values. If you run the harmless demo in your own repository, compare behavior before and after a protection-rule change. Do not infer that a gate worked merely because the job mentioned an environment name in its logs.
