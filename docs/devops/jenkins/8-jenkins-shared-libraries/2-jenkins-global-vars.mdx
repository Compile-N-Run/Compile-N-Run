# Custom Steps with vars

## Introduction

The `vars/` directory is where most shared library work happens. Each file there becomes a **custom step** that reads just like a built-in step such as `sh` or `junit`. A well-designed custom step hides twenty lines of boilerplate behind one readable line:

```groovy
buildMaven(goals: 'clean verify', jdk: '21')
```

A custom step is like a keyboard shortcut. The full sequence of actions still happens, but you trigger it with one keystroke, and everyone on the team uses the same shortcut.

This page shows how to write custom steps that are pleasant to use and hard to misuse:

- the `call` method and how Jenkins finds it
- positional arguments versus a map of named arguments
- defaults and input validation
- steps that take a block (a closure), like `withCredentials`
- global objects with several methods
- how custom steps fit into Declarative Pipeline
- what *not* to do in `vars/`

You should already know the [library layout](./1-jenkins-library-structure.mdx).

## How a vars Step Works

When a pipeline calls `buildMaven(...)`, Jenkins looks for a global variable named `buildMaven`. It finds `vars/buildMaven.groovy`, creates an object from that script, and calls its `call` method with the arguments.

```mermaid
flowchart LR
    A["Jenkinsfile: buildMaven(goals: 'verify')"] --> B["Find vars/buildMaven.groovy"]
    B --> C["Create script object"]
    C --> D["Invoke call(Map config)"]
    D --> E["Run sh, junit, archiveArtifacts"]
```

Inside a `vars` file you are in the same environment as a Scripted Pipeline. You can call `sh`, `echo`, `env`, `params`, `currentBuild` and every step from your installed plugins.

## Step 1: The Simplest Step

```groovy
// vars/printBuildInfo.groovy
def call() {
    echo "Job: ${env.JOB_NAME}"
    echo "Build: ${env.BUILD_NUMBER}"
    echo "Branch: ${env.BRANCH_NAME ?: 'not a multibranch job'}"
}
```

```groovy
// Jenkinsfile
@Library('acme-pipeline-lib@v1') _

pipeline {
    agent any
    stages {
        stage('Info') {
            steps {
                printBuildInfo()
            }
        }
    }
}
```

Example output:

```text
[Pipeline] echo
Job: payments/main
[Pipeline] echo
Build: 42
[Pipeline] echo
Branch: main
```

## Step 2: Positional Arguments

For one or two obvious arguments, positional parameters are fine:

```groovy
// vars/sayHello.groovy
def call(String name = 'human') {
    echo "Hello, ${name}."
}
```

Groovy lets callers drop the parentheses, so both `sayHello('Ana')` and `sayHello 'Ana'` work.

Positional arguments get confusing quickly. What does `deploy('prod', true, false, 3)` mean? Once a step has more than two parameters, switch to named arguments.

## Step 3: Named Arguments with a Map

Accept a single `Map` and read options from it. Groovy turns `step(key: value, ...)` into a map automatically.

```groovy
// vars/buildMaven.groovy
def call(Map config = [:]) {
    def goals    = config.goals ?: 'clean verify'
    def jdk      = config.jdk ?: '21'
    def reports  = config.containsKey('publishTests') ? config.publishTests : true
    def settings = config.settingsId

    def image = "maven:3.9-eclipse-temurin-${jdk}"
    echo "Building with ${image}: mvn ${goals}"

    docker.image(image).inside {
        if (settings) {
            configFileProvider([configFile(fileId: settings, variable: 'MAVEN_SETTINGS')]) {
                sh "mvn -B -s \"\$MAVEN_SETTINGS\" ${goals}"
            }
        } else {
            sh "mvn -B ${goals}"
        }
    }

    if (reports) {
        junit testResults: '**/target/surefire-reports/*.xml', allowEmptyResults: true
    }
}
```

Callers use whichever options they need:

```groovy
buildMaven()
buildMaven(jdk: '17')
buildMaven(goals: 'clean package -DskipTests', publishTests: false)
```

A few details in this example are worth copying:

- `config = [:]` makes the whole map optional.
- `config.publishTests` would be `null` when absent, and `false ?: true` would wrongly become `true`. That is why boolean options use `containsKey`.
- Note the escaped `\$MAVEN_SETTINGS`. Inside a Groovy double-quoted string, `$` starts interpolation. Escaping it passes the literal text to the shell, which then reads the environment variable. This keeps the secret file path out of the Groovy string.

The step uses `docker.image(...).inside` from the Docker Pipeline plugin (`docker-workflow`) and `configFileProvider` from the Config File Provider plugin. If your agents are Kubernetes pods instead, see [Kubernetes Pod Agents](../6-jenkins-agents/4-jenkins-kubernetes-agents.mdx).

## Step 4: Validate Input Early

A typo in an option name silently does nothing: `buildMaven(jkd: '17')` builds with JDK 21. Fail fast instead:

```groovy
// vars/deployService.groovy
def call(Map config = [:]) {
    def allowed  = ['service', 'environment', 'imageTag', 'replicas', 'namespace']
    def required = ['service', 'environment', 'imageTag']

    def unknown = config.keySet() - allowed
    if (unknown) {
        error "deployService: unknown option(s) ${unknown}. Allowed: ${allowed}"
    }
    def missing = required.findAll { !config[it] }
    if (missing) {
        error "deployService: missing required option(s) ${missing}"
    }
    if (!(config.environment in ['dev', 'staging', 'prod'])) {
        error "deployService: environment must be dev, staging or prod, got '${config.environment}'"
    }

    def namespace = config.namespace ?: "${config.service}-${config.environment}"
    def replicas  = config.replicas ?: 2

    echo "Deploying ${config.service}:${config.imageTag} to ${namespace} with ${replicas} replicas"
    sh """
        kubectl -n ${namespace} set image deployment/${config.service} \
            ${config.service}=registry.example.com/${config.service}:${config.imageTag}
        kubectl -n ${namespace} scale deployment/${config.service} --replicas=${replicas}
        kubectl -n ${namespace} rollout status deployment/${config.service} --timeout=5m
    """
}
```

A call with a typo now fails immediately with a clear message:

```groovy
deployService(service: 'billing', enviroment: 'prod', imageTag: '1.4.2')
```

Example output:

```text
[Pipeline] error
ERROR: deployService: unknown option(s) [enviroment]. Allowed: [service, environment, imageTag, replicas, namespace]
Finished: FAILURE
```

The `error` step stops the build and marks it failed. It is the right way to report bad input from a library step.

:::caution
Values interpolated into `sh` scripts come from callers. If a value can come from a build parameter or a branch name, validate it (for example with a regular expression) before passing it to the shell, or a crafted value could inject commands. Never interpolate secrets into Groovy strings; see [Credentials Management](../11-jenkins-security/3-jenkins-credentials.mdx).
:::

## Step 5: Steps That Take a Block

Built-in steps like `withCredentials`, `timeout` and `dir` take a block of code. Your steps can too. Make the last parameter a `Closure` and call it:

```groovy
// vars/withStageTimer.groovy
def call(String label, Closure body) {
    def start = System.currentTimeMillis()
    try {
        body()
    } finally {
        def seconds = (System.currentTimeMillis() - start) / 1000
        echo "${label} took ${seconds} s"
    }
}
```

```groovy
// Jenkinsfile, in a steps block
withStageTimer('Unit tests') {
    sh './gradlew test'
}
```

Example output:

```text
[Pipeline] sh
+ ./gradlew test
BUILD SUCCESSFUL in 41s
[Pipeline] echo
Unit tests took 42.317 s
```

A more useful example wraps a block with standard credentials and environment for a cloud CLI:

```groovy
// vars/withAwsDeployRole.groovy
def call(String environment, Closure body) {
    def credentialId = "aws-deploy-${environment}"
    withCredentials([
        string(credentialsId: "${credentialId}-key-id", variable: 'AWS_ACCESS_KEY_ID'),
        string(credentialsId: "${credentialId}-secret", variable: 'AWS_SECRET_ACCESS_KEY')
    ]) {
        withEnv(["AWS_REGION=eu-west-1", "DEPLOY_ENV=${environment}"]) {
            body()
        }
    }
}
```

```groovy
withAwsDeployRole('staging') {
    sh 'aws sts get-caller-identity'
    sh './scripts/deploy.sh'
}
```

Now every team uses the same credential naming scheme, and nobody copies the `withCredentials` block by hand. `withCredentials` comes from the Credentials Binding plugin (`credentials-binding`). Many teams replace static keys like these with short-lived credentials; see [External Secrets with Vault and Cloud Secret Managers](../11-jenkins-security/4-jenkins-external-secrets.mdx).

### Combining a Map and a Closure

Groovy lets you pass named arguments and a trailing block together:

```groovy
// vars/inBuildContainer.groovy
def call(Map config = [:], Closure body) {
    def image = config.image ?: 'alpine:3.20'
    def args  = config.args ?: ''
    docker.image(image).inside(args) {
        body()
    }
}
```

```groovy
inBuildContainer(image: 'node:22-alpine', args: '-v npm-cache:/root/.npm') {
    sh 'npm ci'
    sh 'npm test'
}
```

## Step 6: Global Objects with Several Methods

A `vars` file does not need a `call` method. You can define several named methods and use the file as a namespace:

```groovy
// vars/git.groovy is a bad name: it would clash with the git step.
// vars/gitInfo.groovy
def shortCommit() {
    return sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
}

def authorEmail() {
    return sh(script: "git log -1 --format='%ae'", returnStdout: true).trim()
}

def changedFiles(String base = 'origin/main') {
    def out = sh(script: "git diff --name-only ${base}...HEAD", returnStdout: true).trim()
    return out ? out.split('\n') as List : []
}
```

```groovy
// Jenkinsfile
steps {
    script {
        def commit = gitInfo.shortCommit()
        def files  = gitInfo.changedFiles()
        echo "Commit ${commit} changed ${files.size()} file(s)"
    }
}
```

Example output:

```text
[Pipeline] sh
+ git rev-parse --short HEAD
[Pipeline] sh
+ git diff --name-only origin/main...HEAD
[Pipeline] echo
Commit 9b1e4c2 changed 3 file(s)
```

Notice the `script` block. Declarative Pipeline does not allow `object.method()` calls directly in `steps`; plain step calls such as `buildMaven(...)` are fine. Notice too that the work happens in `sh` on the agent, and Groovy only trims the result. That keeps the controller light.

## Using Custom Steps in Declarative Pipelines

| What you call | Directly in `steps` | Needs `script` |
| --- | --- | --- |
| `myStep()` / `myStep(a: 1)` | Yes | No |
| `myStep(a: 1) { sh '...' }` | Yes | No |
| `myObject.method()` | No | Yes |
| Return value assigned to a variable | No | Yes |
| Class from `src/` | No | Yes |

Custom steps can be used in `post` conditions too:

```groovy
post {
    failure {
        notifySlack('#payments', "Failed: ${env.BUILD_URL}")
    }
}
```

A `vars` step can even define a **whole** Declarative pipeline. That is the foundation of [Pipeline Templates for Many Teams](./7-jenkins-pipeline-templates.mdx).

## Real-World Scenario

Your team runs a SaaS helpdesk product with 18 services. Every `Jenkinsfile` ends with about 30 lines of notification logic: post to the team's Slack channel on failure, post again when the build is fixed, and email the commit author on production failures. Three variations exist, and one of them pings the wrong channel.

You write one step:

```groovy
// vars/notifyBuild.groovy
def call(Map config = [:]) {
    def channel = config.channel ?: error('notifyBuild: channel is required')
    def result  = currentBuild.currentResult
    def prev    = currentBuild.previousBuild?.result

    if (result == 'SUCCESS' && prev && prev != 'SUCCESS') {
        slackSend(channel: channel, color: 'good',
                  message: "Fixed: ${env.JOB_NAME} #${env.BUILD_NUMBER}")
    } else if (result == 'FAILURE') {
        slackSend(channel: channel, color: 'danger',
                  message: "Failed: ${env.JOB_NAME} #${env.BUILD_NUMBER} ${env.BUILD_URL}")
        if (config.emailOnFailure) {
            emailext(subject: "Build failed: ${env.JOB_NAME}",
                     body: "See ${env.BUILD_URL}",
                     recipientProviders: [culprits()])
        }
    }
}
```

Each service then uses:

```groovy
post {
    always {
        notifyBuild(channel: '#helpdesk-api', emailOnFailure: env.BRANCH_NAME == 'main')
    }
}
```

### Why this approach

Notifications are pure policy: identical everywhere except for the channel. A custom step with named arguments is the smallest abstraction that removes the duplication. It also gives you one place to switch from Slack to Microsoft Teams later. `slackSend` and `emailext` come from the Slack Notification and Email Extension plugins; see [Notifications](../12-jenkins-administration/6-jenkins-notifications.mdx).

### When to use it and when not to

Write a custom step when the same 5 or more lines appear in many pipelines and differ only in a few values. Do not write one to wrap a single built-in step with no added logic. `myEcho('x')` that only calls `echo` adds indirection without value.

### Alternatives and trade-offs

| Approach | Pros | Cons | Best for |
| --- | --- | --- | --- |
| `vars` step with map arguments | Readable, flexible, easy to extend | Runtime resolution, typos caught only by validation or tests | Most reusable pipeline logic |
| `vars` step with positional arguments | Short calls | Unclear meaning beyond two arguments | One or two obvious parameters |
| Class in `src/` | Testable, typed, good for complex logic | Needs `script` blocks and a steps reference | Logic with state or many helpers |
| Shell script in `resources/` | Runs on the agent, testable outside Jenkins | Harder to pass structured data back | Heavy processing, file manipulation |
| Inline in `Jenkinsfile` | Visible right where it is used | Duplicated across repos | Truly one-off logic |

## Common Mistakes

**Shadowing built-in steps.** Naming a file `vars/git.groovy`, `vars/docker.groovy` or `vars/sh.groovy` replaces the real step or global for every pipeline that loads the library.

**Storing state in script fields.** A variable defined at the top of a `vars` file looks like a field, but it is not reliable across controller restarts. Return values from methods instead.

**Doing heavy work in Groovy.** Parsing big files with `JsonSlurper` or looping over thousands of items runs on the controller. Use `sh` with `jq` or a script on the agent, as the Jenkins best practices guide recommends.

**Forgetting `returnStdout` and `trim()`.** `sh 'git rev-parse HEAD'` returns nothing useful. Use `sh(script: '...', returnStdout: true).trim()`.

**Interpolating secrets.** `sh "curl -u admin:${PASSWORD} ..."` puts the secret into the Groovy string and may log it. Use single quotes so the shell expands the variable: `sh 'curl -u "admin:$PASSWORD" ...'`.

**No validation.** A step with ten optional settings and no unknown-key check turns typos into silent misconfiguration.

## Summary

- A file in `vars/` becomes a step; its `call` method runs when the step is used.
- Use positional arguments for one or two values, and a `Map` with defaults for anything more.
- Validate options and fail with `error` and a clear message.
- Accept a trailing `Closure` to build block steps like `withAwsDeployRole { ... }`.
- `vars` files without `call` act as namespaces with several methods, which Declarative needs to call inside `script`.
- Keep Groovy as glue and do heavy work on the agent with `sh`.
