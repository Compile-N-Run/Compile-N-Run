# Multi-Head Attention

## Introduction

The self-attention layer from the [previous pages](./2-llm-self-attention-from-scratch.mdx) computes one set of attention weights per token. Each token gets **one** weighted average of the other tokens' values. That is a real limitation: to understand "it" in "The trophy didn't fit in the suitcase because it was too big", a model may want to look at "trophy" to resolve the reference, at "was" for grammar and at the previous token for local context, all at once and with different weights.

**Multi-head attention** (Vaswani et al., 2017) runs several attention operations side by side. Each **head** has its own small query, key and value projections and computes its own attention pattern. Their outputs are concatenated and mixed by an output projection. Remarkably, this costs the same number of parameters and FLOPs as one big head.

On this page you will:

- Derive multi-head attention and show why its cost does not depend on the number of heads.
- Implement head splitting with `view` and `transpose`, and see the classic reshape bug.
- Build a full multi-head layer and verify it against `torch.nn.MultiheadAttention`.
- Read the head-related fields of real config.json files, including models where `head_dim` is not `hidden_size / num_attention_heads`.
- Review what research has found individual heads to do.

## Why One Head Is Not Enough

A single attention head mixes value vectors with **one** set of weights per query. Whatever the weights are, every feature of the output is the same weighted average. If a token needs syntactic information from one position and semantic information from another, a single head must compromise: put weight on both and get a blend of both values.

Multiple heads remove the compromise. Head 1 can attend to position 3 and head 2 to position 7, and the output projection can then route head 1's result into some features and head 2's into others. Vaswani et al. described this as letting the model jointly attend to information from different representation subspaces at different positions.

There is also an argument from the shape of the score function. In head $i$ the score between tokens $a$ and $b$ is

$$
s^{(i)}_{ab} = \frac{x_a^\top W_Q^{(i)} \left(W_K^{(i)}\right)^\top x_b}{\sqrt{d_h}}
$$

The matrix $W_Q^{(i)} (W_K^{(i)})^\top$ is $d_{\text{model}} \times d_{\text{model}}$ but has rank at most $d_h$, the head dimension. Each head therefore compares tokens through its own low-rank "lens". Several heads give several independent lenses, each with its own softmax, which a single head of the same total size cannot imitate because there is only one softmax.

## The Math of Multi-Head Attention

Let $h$ be the number of heads and $d_h$ the dimension per head. In the original Transformer $d_h = d_{\text{model}} / h$ (base model: $d_{\text{model}} = 512$, $h = 8$, $d_h = 64$). For each head $i = 1, \dots, h$:

$$
\mathrm{head}_i = \mathrm{Attention}\!\left(X W_Q^{(i)},\ X W_K^{(i)},\ X W_V^{(i)}\right), \qquad W_Q^{(i)}, W_K^{(i)}, W_V^{(i)} \in \mathbb{R}^{d_{\text{model}} \times d_h}
$$

Each $\mathrm{head}_i$ is a $T \times d_h$ matrix. The heads are concatenated along the feature axis and projected back to the model width:

$$
\mathrm{MultiHead}(X) = \left[\mathrm{head}_1; \dots; \mathrm{head}_h\right] W_O, \qquad W_O \in \mathbb{R}^{h d_h \times d_{\text{model}}}
$$

### Same Cost as One Big Head

In code nobody stores $3h$ small matrices. Stack the per-head matrices side by side: $W_Q = [W_Q^{(1)}, \dots, W_Q^{(h)}] \in \mathbb{R}^{d_{\text{model}} \times h d_h}$, and the same for $W_K$ and $W_V$. One matrix multiplication $XW_Q$ then computes every head's queries at once; the heads are just consecutive slices of $d_h$ columns.

With $h d_h = d_{\text{model}}$ the parameter count is

$$
\underbrace{3 \cdot d_{\text{model}} \cdot d_{\text{model}}}_{W_Q, W_K, W_V} + \underbrace{d_{\text{model}} \cdot d_{\text{model}}}_{W_O} = 4 d_{\text{model}}^2
$$

(plus $4 d_{\text{model}}$ if the projections have biases). It does not depend on $h$. Neither do the FLOPs: the score computation is $h$ heads times $T^2 d_h$ multiply-adds, which is $T^2 d_{\text{model}}$ regardless of how the width is split. The only thing $h$ changes is how many separate softmax distributions there are, and how many $T \times T$ weight matrices exist (one per head), which matters for memory in the naive implementation.

### The Output Projection as a Sum Over Heads

Split $W_O$ into $h$ row blocks $W_O^{(i)} \in \mathbb{R}^{d_h \times d_{\text{model}}}$, one per head. Block matrix multiplication gives

$$
\left[\mathrm{head}_1; \dots; \mathrm{head}_h\right] W_O = \sum_{i=1}^{h} \mathrm{head}_i\, W_O^{(i)}
$$

So multi-head attention is a **sum of $h$ independent attention layers**, each writing its own contribution into the residual stream. This view, emphasized by Elhage et al. (2021) in "A Mathematical Framework for Transformer Circuits", is the starting point for interpretability work: each head has a "QK circuit" $W_Q^{(i)} (W_K^{(i)})^\top$ that decides where to look and an "OV circuit" $W_V^{(i)} W_O^{(i)}$ that decides what to write. A quick check of the identity (with PyTorch's `x @ W.T` convention, so the column blocks of the stored weight play the role of the row blocks above):

```python
import torch

torch.manual_seed(0)
T, d_model, h = 5, 12, 3
hd = d_model // h
heads = [torch.randn(T, hd) for _ in range(h)]        # per-head outputs o_i: (T, hd)
W_o = torch.randn(d_model, d_model)                    # out = concat(o) @ W_o.T

concat_then_project = torch.cat(heads, dim=-1) @ W_o.T
# Column block i of W_o only ever multiplies head i.
sum_of_heads = sum(o @ W_o[:, i * hd:(i + 1) * hd].T for i, o in enumerate(heads))
print(torch.allclose(concat_then_project, sum_of_heads, atol=1e-5))
```

```text
True
```

## Splitting Heads: Reshape and Transpose

The implementation hinges on two tensor operations. After the projection, `q = W_q(x)` has shape `(B, T, h * d_h)`. We want `(B, h, T, d_h)`, so that the attention function treats `(B, h)` as batch dimensions and computes one `(T, T)` score matrix per head.

1. `view(B, T, h, d_h)`: split the last axis into heads. This is free, it only reinterprets memory. Because each head's columns are consecutive, features `0 .. d_h-1` become head 0, the next $d_h$ become head 1, and so on.
2. `transpose(1, 2)`: swap the token and head axes to get `(B, h, T, d_h)`.

Merging is the reverse: `transpose(1, 2)` back to `(B, T, h, d_h)`, then `reshape(B, T, h * d_h)`. After a transpose the tensor is no longer contiguous in memory, so use `.reshape` or `.contiguous().view(...)`.

The tempting shortcut `q.view(B, h, T, d_h)` has the right shape and the wrong content. The next example labels every feature with its origin (token $t$, head $j$, dimension $i$ becomes the number $100t + 10j + i$) so you can see where each value lands:

```python
import torch

B, T, h, hd = 1, 3, 2, 2
# Make each feature value tell us where it came from: token t, head j, dim i -> 100t + 10j + i
x = torch.tensor([[[100 * t + 10 * j + i for j in range(h) for i in range(hd)]
                   for t in range(T)]], dtype=torch.float32)       # (B, T, h*hd)

right = x.view(B, T, h, hd).transpose(1, 2)    # (B, h, T, hd)
wrong = x.view(B, h, T, hd)                    # same shape, different meaning

print("right, head 1:\n", right[0, 1])
print("wrong, head 1:\n", wrong[0, 1])
```

```text
right, head 1:
 tensor([[ 10.,  11.],
        [110., 111.],
        [210., 211.]])
wrong, head 1:
 tensor([[110., 111.],
        [200., 201.],
        [210., 211.]])
```

The correct version gives head 1 the features $10, 11$ of tokens 0, 1 and 2. The wrong one mixes features from different heads and tokens into one "head": row 0 belongs to token 1's head 0, and row 1 to token 2's head 0. Nothing crashes, the shapes are fine, and the model trains, just worse. Labeling tensors like this is a cheap way to unit-test any reshape logic.

## A Complete Multi-Head Attention Layer

Here is the full layer, verified against PyTorch's built-in `nn.MultiheadAttention`. The built-in module stores $W_Q$, $W_K$, $W_V$ stacked into one `in_proj_weight` of shape `(3 * d_model, d_model)`, so we copy our weights into it.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

torch.manual_seed(0)


class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_heads, bias=True):
        super().__init__()
        assert d_model % n_heads == 0
        self.n_heads, self.head_dim = n_heads, d_model // n_heads
        self.W_q = nn.Linear(d_model, d_model, bias=bias)
        self.W_k = nn.Linear(d_model, d_model, bias=bias)
        self.W_v = nn.Linear(d_model, d_model, bias=bias)
        self.W_o = nn.Linear(d_model, d_model, bias=bias)

    def split_heads(self, x):
        B, T, _ = x.shape
        # (B, T, d_model) -> (B, T, n_heads, head_dim) -> (B, n_heads, T, head_dim)
        return x.view(B, T, self.n_heads, self.head_dim).transpose(1, 2)

    def forward(self, x, is_causal=False):
        B, T, C = x.shape                                     # (batch, seq_len, d_model)
        q = self.split_heads(self.W_q(x))                     # (B, h, T, head_dim)
        k = self.split_heads(self.W_k(x))
        v = self.split_heads(self.W_v(x))
        o = F.scaled_dot_product_attention(q, k, v, is_causal=is_causal)  # (B, h, T, head_dim)
        o = o.transpose(1, 2).contiguous().view(B, T, C)      # merge heads: (B, T, d_model)
        return self.W_o(o)


d_model, n_heads = 32, 4
ours = MultiHeadAttention(d_model, n_heads)
ref = nn.MultiheadAttention(d_model, n_heads, batch_first=True)

# Copy our weights into PyTorch's module. It stores W_q, W_k, W_v stacked in one matrix.
with torch.no_grad():
    ref.in_proj_weight.copy_(torch.cat([ours.W_q.weight, ours.W_k.weight, ours.W_v.weight]))
    ref.in_proj_bias.copy_(torch.cat([ours.W_q.bias, ours.W_k.bias, ours.W_v.bias]))
    ref.out_proj.weight.copy_(ours.W_o.weight)
    ref.out_proj.bias.copy_(ours.W_o.bias)

x = torch.randn(2, 7, d_model)
causal = torch.triu(torch.ones(7, 7, dtype=torch.bool), diagonal=1)  # nn.MHA: True = BLOCK
with torch.no_grad():
    a = ours(x, is_causal=True)
    b, _ = ref(x, x, x, attn_mask=causal, need_weights=False)
print("output shape:", tuple(a.shape))
print("matches nn.MultiheadAttention:", torch.allclose(a, b, atol=1e-6))
print("parameters:", sum(p.numel() for p in ours.parameters()),
      "= 4*d^2 + 4*d =", 4 * d_model**2 + 4 * d_model)
```

```text
output shape: (2, 7, 32)
matches nn.MultiheadAttention: True
parameters: 4224 = 4*d^2 + 4*d = 4224
```

Note the mask: `nn.MultiheadAttention` uses the **opposite** boolean convention from SDPA (`True` blocks a position), so the causal mask passed to it is the upper triangle above the diagonal. The shape flow through the layer:

| Step | Shape (B=2, T=7, d=32, h=4) |
| --- | --- |
| input `x` | `(2, 7, 32)` |
| `W_q(x)` | `(2, 7, 32)` |
| `view` to heads | `(2, 7, 4, 8)` |
| `transpose(1, 2)` | `(2, 4, 7, 8)` |
| scores inside SDPA | `(2, 4, 7, 7)` |
| attention output | `(2, 4, 7, 8)` |
| merge heads | `(2, 7, 32)` |
| `W_o` | `(2, 7, 32)` |

`nn.MultiheadAttention` is fine for experiments, but LLM implementations write their own layer like ours, because they need to insert RoPE between the projection and the attention, use grouped key-value heads and manage a KV cache. The layer above is what [Building a GPT from Scratch in PyTorch](../3-llm-transformer/5-llm-build-gpt-from-scratch.mdx) uses as its attention block.

## Heads in Real Models: Reading config.json

The relevant config.json fields are `hidden_size` ($d_{\text{model}}$), `num_attention_heads` ($h$), `head_dim` ($d_h$, sometimes omitted) and `num_key_value_heads` (explained on the [next page](./5-llm-mqa-gqa.mdx)). Values from the published configs and papers:

| Model | hidden_size | heads | head_dim | heads x head_dim |
| --- | --- | --- | --- | --- |
| Transformer base (2017) | 512 | 8 | 64 | 512 |
| GPT-2 small | 768 | 12 | 64 | 768 |
| GPT-3 175B | 12288 | 96 | 128 | 12288 |
| Llama 3.1 8B | 4096 | 32 | 128 | 4096 |
| Llama 3.1 70B | 8192 | 64 | 128 | 8192 |
| Qwen3-8B | 4096 | 32 | 128 | 4096 |
| Qwen3-32B | 5120 | 64 | 128 | **8192** |
| Gemma 3 27B | 5376 | 32 | 128 | **4096** |
| gpt-oss-120b | 2880 | 64 | 64 | **4096** |

Two patterns stand out:

- **Head dimension 128 is the de facto standard** for large models; 64 is common for small ones. Hardware kernels such as FlashAttention are tuned for these sizes, and RoPE needs enough dimension pairs for its range of frequencies. More heads at fixed width means a smaller $d_h$ and lower-rank lenses; fewer heads means fewer distinct patterns.
- **$h \cdot d_h$ need not equal `hidden_size`.** In Qwen3-32B the query projection maps 5,120 features to $64 \times 128 = 8{,}192$, and $W_O$ maps 8,192 back to 5,120. In gpt-oss-120b it goes 2,880 to 4,096. Nothing in the math requires the attention width to equal the residual width; it is a capacity choice. If you compute `hidden_size // num_attention_heads` instead of reading `head_dim`, you get the wrong shapes for these models. The parameter count becomes $2 d_{\text{model}} h d_h$ for $W_Q$ and $W_O$ together, rather than $2 d_{\text{model}}^2$.

## What Do Heads Learn?

Because each head produces its own attention pattern, researchers have studied what individual heads do. The findings are a mix of striking specializations and redundancy.

**Interpretable heads exist.** Clark et al. (2019, "What Does BERT Look At?") found heads in BERT that attend to delimiter tokens, to fixed relative offsets (the previous or next token) or broadly over the sentence, and heads that track syntax: some find the direct object of a verb or the determiner of a noun with more than 75% accuracy, and one performs coreference resolution reasonably well. None of this was supervised; it emerged from pretraining.

**Many heads are redundant.** Voita et al. (2019) classified heads in translation models as positional, syntactic or rare-word heads and pruned the rest with a learned gating method: on English-Russian, removing 38 of 48 encoder heads cost only 0.15 BLEU, and the specialized heads were the last ones to be pruned. Michel et al. (2019, "Are Sixteen Heads Really Better than One?") found that many layers can be reduced to a single head at test time with little loss. Heads seem to matter more for training (more paths to explore) than for the final function.

**Heads compose into circuits.** In decoder LLMs the best-understood mechanism is the **induction head** (Elhage et al., 2021; Olsson et al., 2022). A "previous-token head" in an early layer writes into each position which token came before it. An induction head in a later layer uses that information to find earlier occurrences of the **current** token and copies the token that followed it: having seen "Harry Potter" once, on seeing "Harry" again it predicts "Potter". Olsson et al. present evidence that induction heads are an important mechanism behind in-context learning. The details are in [Mechanistic Interpretability](../12-llm-evaluation/4-llm-interpretability.mdx).

**Some heads look at nothing in particular.** Many heads in trained LLMs put a large share of their weight on the first token regardless of content. Xiao et al. (2023) called this an **attention sink**: since softmax weights must sum to 1, a head that has nothing useful to read parks its weight on a fixed position. This matters for long-context inference, because evicting the first tokens from the KV cache breaks those heads (see [Sliding Window, Sparse and Linear Attention](../5-llm-flash-attention/5-llm-sparse-and-linear-attention.mdx)).

:::warning
An attention weight says how much a value contributed to a head's output, not why the model made a decision. Jain and Wallace (2019, "Attention is not Explanation") showed that quite different attention distributions can produce the same predictions. Treat attention maps as a starting point for analysis, not as an explanation.
:::

## Worked Scenario: The Attention Block of Qwen3-32B

Let us read the attention part of a real config and derive every weight shape, using Qwen3-32B: `hidden_size` 5120, `num_attention_heads` 64, `head_dim` 128, and (from the next page) `num_key_value_heads` 8.

1. **Queries.** $W_Q$ maps 5,120 to $64 \times 128 = 8{,}192$. Stored as `q_proj.weight` with shape `(8192, 5120)`: 41.9 million parameters.
2. **Keys and values.** With 8 KV heads each maps 5,120 to $8 \times 128 = 1{,}024$: `k_proj.weight` and `v_proj.weight` are `(1024, 5120)`, 5.2 million parameters each.
3. **Attention.** Per token the query is viewed as `(64, 128)`, keys and values as `(8, 128)`. Each group of 8 query heads shares one KV head.
4. **Output.** The 64 head outputs of size 128 are concatenated to 8,192 features and `o_proj.weight` of shape `(5120, 8192)` maps them back: another 41.9 million.

Total: about 94.4 million parameters per layer for attention, times 64 layers, about 6.0 billion of the model's roughly 32 billion. Compare with the textbook $4 d_{\text{model}}^2 = 105$ million per layer: the wider queries add parameters, the grouped keys and values remove more. Reading these four shapes from a config is a skill you will use constantly; [Counting Parameters, FLOPs and Memory](../3-llm-transformer/6-llm-parameter-and-flop-counting.mdx) extends it to the whole model.

## Common Mistakes

- **`view(B, h, T, d_h)` without the transpose.** Right shape, scrambled heads. Always `view(B, T, h, d_h).transpose(1, 2)`.
- **Calling `.view` after `transpose`** to merge heads. The tensor is not contiguous; use `.reshape` or `.contiguous().view`.
- **Computing `head_dim` as `hidden_size // num_attention_heads`** when the config gives `head_dim` explicitly (Qwen3, Gemma 3, gpt-oss).
- **Using SDPA's mask convention with `nn.MultiheadAttention`** or the other way around; their boolean masks are inverted.
- **Forgetting the output projection.** Without $W_O$ the heads cannot exchange information and the layer's output is just the concatenation.
- **Assuming more heads cost more.** At fixed $h \cdot d_h$, parameters and FLOPs are unchanged; only the number of softmaxes and the per-head rank change.
- **Reading attention maps as explanations** of model behavior.

## Summary

- Multi-head attention runs $h$ attention operations with separate $d_h$-dimensional projections, concatenates the results and mixes them with $W_O$.
- With $h d_h = d_{\text{model}}$, parameters ($4 d_{\text{model}}^2$) and FLOPs do not depend on $h$; heads add separate softmaxes and low-rank QK lenses for free.
- The output projection is a sum over heads, $\sum_i \mathrm{head}_i W_O^{(i)}$, so each head writes its own contribution to the residual stream.
- Split heads with `view(B, T, h, d_h).transpose(1, 2)` and merge with the reverse; the shortcut `view(B, h, T, d_h)` silently scrambles features.
- Head dimension 128 is standard in large models, and $h \cdot d_h$ can differ from `hidden_size` (Qwen3-32B, Gemma 3, gpt-oss).
- Some heads specialize (syntax, coreference, previous token, induction), many are redundant, and some act as attention sinks; attention weights are not explanations.
