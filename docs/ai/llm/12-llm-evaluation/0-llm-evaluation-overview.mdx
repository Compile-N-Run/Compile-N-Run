# Evaluating LLMs: Benchmarks and Their Limits

## Introduction

Every model release comes with a table of numbers: MMLU 85, GPQA 60, HumanEval 90, SWE-bench 70. Those numbers decide which model a team picks, which paper gets attention and which training run is called a success. Yet very few people who quote them know how they were produced. Was the answer chosen by the highest log-probability or by parsing generated text? Was the score averaged over five samples or one? How many questions were there, and how big is the error bar?

Those details are not trivia. The same model on the same benchmark can move by several points when you change the prompt template, the number of few-shot examples or the way you normalize answer length. A three-point gap on a 198-question benchmark is often noise. A benchmark whose questions leaked into the training data measures memory, not skill.

This page builds an evaluation from the ground up. You will learn:

- the three ways benchmarks score a model (log-likelihood, generated answer, executed code) and implement the first one with GPT-2;
- the unbiased pass@k estimator used for code benchmarks, with its derivation;
- what the main benchmarks (MMLU, GPQA, GSM8K, HumanEval, SWE-bench and others) actually contain;
- how to put a confidence interval on a score and compare two models properly;
- how to run the standard open-source harness, and why benchmarks saturate and stop being useful.

The later pages of this section go deeper: [perplexity](./1-llm-perplexity.mdx) for intrinsic quality, [LLM judges](./2-llm-llm-as-judge.mdx) for open-ended answers, [hallucination](./3-llm-hallucination.mdx), [interpretability](./4-llm-interpretability.mdx) and [contamination](./5-llm-contamination.mdx). For a fine-tuning-specific view see [Evaluating a Fine-Tuned Model](../9-llm-fine-tuning/5-llm-evaluating-fine-tunes.mdx), and for long context see [Needle Tests and RULER](../4-llm-positional-encoding/7-llm-long-context-evaluation.mdx).

## What a Benchmark Score Is Made Of

A benchmark is not just a dataset. A score comes from five choices stacked on top of each other:

1. **Items.** The questions and reference answers.
2. **Prompt format.** The instruction text, the few-shot examples, whether a chat template is applied, whether the model is asked to reason first.
3. **Decoding.** Greedy or sampled, temperature, maximum tokens, how many samples per item.
4. **Scoring rule.** How a model output becomes right or wrong: compare log-probabilities, extract a final answer with a regular expression, run unit tests, ask a judge model.
5. **Aggregation.** Mean accuracy, macro-average over subjects, pass@k, a rating from pairwise wins.

Change any layer and the number changes. When two papers report different MMLU scores for the same model, the difference usually lives in layers 2 to 4, not in the model.

```mermaid
flowchart LR
  A["Benchmark items"] --> B["Prompt template + few-shot"]
  B --> C["Model"]
  C --> D["Log-probs or generated text"]
  D --> E["Scoring rule"]
  E --> F["Per-item 0/1 or score"]
  F --> G["Aggregate + error bar"]
```

There are three families of scoring rule, and almost every benchmark uses one of them:

| Scoring family | How it works | Examples | Main weakness |
|---|---|---|---|
| Log-likelihood | Score each candidate answer by the model's probability; pick the most likely | MMLU (classic), HellaSwag, ARC, PIQA | Does not test generation; sensitive to length normalization |
| Generate and match | Let the model generate; extract the answer; compare to a reference | GSM8K, MATH, GPQA (generative form), SimpleQA | Answer extraction is brittle; formatting errors count as wrong |
| Execute | Run the generated code or agent actions against tests | HumanEval, MBPP, SWE-bench, LiveCodeBench | Tests can be incomplete; environment setup is costly |

A fourth family, preference judgments by humans or models, is the topic of [LLM-as-a-Judge](./2-llm-llm-as-judge.mdx).

## Log-Likelihood Scoring of Multiple Choice

Base models (before instruction tuning) often cannot follow "answer with A, B, C or D". So classic harnesses never ask them to. Instead they compute, for each candidate continuation $c_j$ of a context $x$, the log-probability the model assigns to it:

$$
\ell_j = \log p_\theta(c_j \mid x) = \sum_{t=1}^{\lvert c_j \rvert} \log p_\theta\!\left(c_{j,t} \mid x, c_{j,\lt t}\right)
$$

Here $c_{j,t}$ is the $t$-th token of candidate $j$ and $\lvert c_j \rvert$ its length in tokens. The prediction is $\hat{j} = \arg\max_j \ell_j$, and accuracy is the fraction of items where $\hat{j}$ is the correct index.

The sum has a built-in bias: every extra token adds another negative log-probability, so longer answers are penalized. Harnesses therefore report a second number, often called `acc_norm`, which divides by the length of the candidate in bytes (or characters):

$$
\ell^{\mathrm{norm}}_j = \frac{\ell_j}{\mathrm{bytes}(c_j)}
$$

Neither rule is "correct". The raw sum favours short answers; the normalized one can favour long, fluent distractors. Let us see both on GPT-2:

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

torch.manual_seed(0)
tok = AutoTokenizer.from_pretrained("openai-community/gpt2")
model = AutoModelForCausalLM.from_pretrained("openai-community/gpt2").eval()

def continuation_logprob(context: str, continuation: str) -> float:
    """Sum of log p(continuation tokens | context), the way lm-eval scores choices."""
    ctx = tok(context).input_ids
    cont = tok(continuation).input_ids
    ids = torch.tensor([ctx + cont])                         # (1, T)
    with torch.no_grad():
        logp = torch.log_softmax(model(ids).logits[0, :-1], -1)   # (T-1, vocab)
    targets = ids[0, 1:]
    lp = logp[torch.arange(len(targets)), targets]           # (T-1,)
    return lp[-len(cont):].sum().item()                      # only the continuation

question = "Question: What do bees make?\nAnswer:"
choices = [" honey", " cars", " a sweet, sticky golden food called honey", " milk"]
for c in choices:
    lp = continuation_logprob(question, c)
    n_bytes = len(c.encode("utf-8"))
    print(f"{c!r:46s} sum={lp:7.2f}  per_byte={lp / n_bytes:6.3f}")
```

```text
' honey'                                       sum=  -7.75  per_byte=-1.291
' cars'                                        sum= -17.00  per_byte=-3.401
' a sweet, sticky golden food called honey'    sum= -39.60  per_byte=-0.966
' milk'                                        sum= -12.98  per_byte=-2.596
```

With the raw sum, " honey" wins (-7.75). With per-byte normalization, the long paraphrase wins (-0.966 per byte), because once the model has read "a sweet, sticky golden food called", the word "honey" is almost free. On a real benchmark both answers might be marked correct or not, depending on how the item was written. The point is that the scoring rule, not the model, decided which answer was "chosen".

Two more details matter in practice:

- **Tokenization at the boundary.** Notice the leading space in `" honey"`. GPT-2 style tokenizers encode a word with its preceding space, so the context must end without a space and the continuation must start with one. Get this wrong and every candidate starts with an unusual token.
- **Letter versus content scoring.** MMLU can be scored by the probability of the content of each option, or by putting all four options in the prompt and scoring only the letters " A", " B", " C", " D". Instruction-tuned models do much better with the letter form; small base models often do better with the content form. Papers rarely use the same one.

## Generated Answers, Exact Match and pass@k

For math and question answering, the model generates a full response, and a parser extracts the final answer. GSM8K references end with a line like `#### 72`; harnesses usually ask the model to end with "The answer is 72" and apply a regular expression. MATH answers are LaTeX expressions, so graders normalize them (strip spaces, convert `\frac12` to `\frac{1}{2}`) or check symbolic equivalence. A model that computes the right number but writes "seventy-two" scores zero. When you see a jump of 10 points after "fixing the answer extraction", it was the parser, not the model.

Code benchmarks execute the output. HumanEval (Chen et al., 2021, "Evaluating Large Language Models Trained on Code") has 164 hand-written Python problems, each with a function signature, a docstring and hidden unit tests. A sample passes if all tests pass.

Because sampling is random, code results are reported as **pass@k**: the probability that at least one of $k$ samples passes. The naive way to estimate it is to draw exactly $k$ samples per problem and check. That is high-variance. Chen et al. instead draw $n \ge k$ samples, count the $c$ that pass, and compute the probability that a random subset of size $k$ contains at least one passing sample:

$$
\mathrm{pass@}k = \mathbb{E}_{\mathrm{problems}}\left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

The derivation is one line of counting. There are $\binom{n}{k}$ ways to pick $k$ samples out of $n$. The subsets that contain no passing sample are those drawn entirely from the $n-c$ failures: $\binom{n-c}{k}$ of them. So the fraction of subsets with at least one pass is one minus the ratio. Since every subset of the $n$ samples is equally likely to be the $k$ you "would have" drawn, this is an unbiased estimate of the true pass@k.

Why not plug the per-sample success rate $\hat{p} = c/n$ into $1-(1-\hat{p})^k$? Because that function is concave in $\hat{p}$, so by Jensen's inequality its expectation is below the true value: it is biased low. The code below checks both claims:

```python
import numpy as np
from math import comb

def pass_at_k(n: int, c: int, k: int) -> float:
    """Unbiased pass@k from n samples of which c passed (Chen et al., 2021)."""
    if n - c < k:                       # every size-k subset contains a correct sample
        return 1.0
    # 1 - C(n-c, k) / C(n, k), computed as a stable product
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

n, c = 10, 3
for k in (1, 2, 5):
    exact = 1 - comb(n - c, k) / comb(n, k)
    print(f"n={n} c={c} k={k}: pass@k={pass_at_k(n, c, k):.4f}  (comb form {exact:.4f})")

# why not just "1 - (1 - c/n)**k"?  it is biased; compare with simulation
rng = np.random.default_rng(0)
p_true, k = 0.3, 5
naive, unbiased = [], []
for _ in range(20000):
    s = rng.random(10) < p_true          # 10 samples, each correct with prob 0.3
    c = int(s.sum())
    naive.append(1 - (1 - c / 10) ** k)
    unbiased.append(pass_at_k(10, c, k))
print(f"true pass@5 = {1 - (1 - p_true) ** k:.4f}")
print(f"mean naive estimate    = {np.mean(naive):.4f}")
print(f"mean unbiased estimate = {np.mean(unbiased):.4f}")
```

```text
n=10 c=3 k=1: pass@k=0.3000  (comb form 0.3000)
n=10 c=3 k=2: pass@k=0.5333  (comb form 0.5333)
n=10 c=3 k=5: pass@k=0.9167  (comb form 0.9167)
true pass@5 = 0.8319
mean naive estimate    = 0.7599
mean unbiased estimate = 0.8321
```

Check the $k=2$ line by hand: $\binom{7}{2} = 21$, $\binom{10}{2} = 45$, so $1 - 21/45 = 0.5333$. The simulation shows the naive formula under-reports pass@5 by about seven points, while the combinatorial estimator is on target. The product form in the code avoids huge binomial coefficients when $n$ is 200, which is the sample count Chen et al. used.

:::note
pass@1 with $n$ samples is simply the mean success rate $c/n$. Reporting pass@1 averaged over several samples is far more stable than one greedy run, which is why many recent model cards state "pass@1, averaged over 4 or 16 samples".
:::

## The Benchmark Landscape

Here is what the most quoted benchmarks contain. Sizes and dates come from the original papers.

| Benchmark | Introduced by | What it tests | Size | Scoring |
|---|---|---|---|---|
| HellaSwag | Zellers et al., 2019 | Commonsense sentence completion, adversarially filtered | about 10k validation items | Log-likelihood, 4 endings |
| MMLU | Hendrycks et al., 2020 | Knowledge across 57 subjects, high school to professional | about 14k test questions | 4-way multiple choice |
| GSM8K | Cobbe et al., 2021 | Grade-school math word problems | 8.5k problems, 1,319 test | Exact match on final number |
| MATH | Hendrycks et al., 2021 | Competition mathematics | 12.5k problems | Normalized answer match |
| HumanEval | Chen et al., 2021 | Python functions from docstrings | 164 problems | Unit tests, pass@k |
| TruthfulQA | Lin et al., 2021 | Imitating common misconceptions | 817 questions, 38 categories | Judge model or multiple choice |
| GPQA | Rein et al., 2023 | "Google-proof" graduate biology, physics, chemistry | 448 questions, Diamond subset 198 | 4-way multiple choice |
| SWE-bench | Jimenez et al., 2023 | Fix real GitHub issues in 12 Python repos | 2,294 tasks; Verified subset 500 | Repository tests must pass |
| IFEval | Zhou et al., 2023 | Verifiable formatting instructions ("use no commas") | about 500 prompts | Programmatic checks |
| MMLU-Pro | Wang et al., 2024 | Harder, reasoning-heavy MMLU successor, 10 options | about 12k questions | 10-way multiple choice |
| Humanity's Last Exam | Phan et al., 2025 | Expert-written frontier questions | 2,500 questions | Exact match or multiple choice |

A few notes that change how you read these:

- **Human baselines matter.** In the GPQA paper, domain experts reached 65% while skilled non-experts with unrestricted web access and more than 30 minutes per question reached 34%. A model at 60% is therefore near expert level on that set, not "failing".
- **Benchmarks get repaired.** SWE-bench Verified was released by OpenAI with the SWE-bench authors in August 2024 after human annotators found that many original tasks had underspecified issues or unfair tests. MMLU-Redux (Gema et al., 2024) re-annotated MMLU questions and estimated that about 57% of the analysed Virology questions had errors. A benchmark with a few percent wrong labels has a ceiling below 100%.
- **Harder successors appear when old ones saturate.** MMLU-Pro raised the number of options from 4 to 10 and added reasoning questions; the authors report accuracy drops of 16 to 33 points relative to MMLU and lower sensitivity to the prompt (about 2% variation across 24 prompt styles versus 4 to 5% on MMLU).

Static benchmarks age. Once a benchmark is famous, its questions appear in blog posts, forums and training sets. That problem has its own page: [Benchmark Contamination](./5-llm-contamination.mdx).

## Error Bars and Comparing Two Models

A benchmark score is an average of $n$ per-item outcomes $y_i \in \lbrace 0, 1 \rbrace$. If we treat items as a random sample from some larger population of possible questions, the accuracy $\hat{p}$ has standard error

$$
\mathrm{SE}(\hat{p}) = \sqrt{\frac{\hat{p}(1-\hat{p})}{n}}
$$

and a 95% interval is roughly $\hat{p} \pm 1.96\,\mathrm{SE}$. Plug in some numbers. On GPQA Diamond ($n = 198$) at $\hat{p} = 0.6$: $\mathrm{SE} = \sqrt{0.24/198} = 0.035$, so the interval is about plus or minus 7 points. On HumanEval ($n = 164$) it is similar. On MMLU ($n \approx 14{,}000$) at 0.8 it shrinks to about plus or minus 0.7 points. Small benchmarks are noisy benchmarks.

When you compare two models on the same items, do not compare their two intervals. The models tend to fail on the same hard questions, so their errors are correlated, and the paired difference has much less variance than either score. The right tool is a **paired** test: resample questions with replacement, and for each resample compute the difference of the two models on the same questions.

```python
import numpy as np

rng = np.random.default_rng(0)
n = 198                                      # e.g. the size of GPQA Diamond
# simulate per-question correctness for two models; B is truly about 3 points better,
# with correlated errors (both find the same questions hard)
difficulty = rng.random(n)
a = (difficulty < 0.60).astype(int) ^ (rng.random(n) < 0.08)
b = (difficulty < 0.63).astype(int) ^ (rng.random(n) < 0.08)
pa, pb = a.mean(), b.mean()
se = np.sqrt(pa * (1 - pa) / n)
print(f"model A: {pa:.3f} +/- {1.96 * se:.3f} (95% normal CI)")
print(f"model B: {pb:.3f}")

# paired bootstrap on the difference: resample questions, keep pairs together
idx = rng.integers(0, n, size=(10000, n))
diff = b[idx].mean(1) - a[idx].mean(1)
lo, hi = np.percentile(diff, [2.5, 97.5])
print(f"B - A = {pb - pa:+.3f}, 95% paired bootstrap CI [{lo:+.3f}, {hi:+.3f}]")
print(f"share of resamples where B wins: {(diff > 0).mean():.2f}")
```

```text
model A: 0.571 +/- 0.069 (95% normal CI)
model B: 0.576
B - A = +0.005, 95% paired bootstrap CI [-0.045, +0.061]
share of resamples where B wins: 0.54
```

Model B is better by construction, yet on this draw of 198 questions it wins by half a point and the interval spans zero comfortably. A leaderboard would still sort B above A. Two habits fix most of this: report an interval with every number, and when the interval includes zero, say "no detectable difference" instead of ranking.

There is a second, less visible source of variance: the **prompt**. Changing the few-shot examples, their order or the answer delimiter can move small models by several points. A robust evaluation reports the mean over a few prompt variants or at least fixes the template and publishes it.

## Running a Standard Harness

You rarely need to write the scoring loop yourself. The EleutherAI **lm-evaluation-harness** (`lm_eval`) implements hundreds of tasks with fixed templates, and it is the backend of many public leaderboards. Install it with the Hugging Face backend:

```bash
pip install "lm_eval[hf]"
```

Recent versions organize the CLI into subcommands (`lm-eval run`, `lm-eval ls tasks`, `lm-eval validate`); the old form `lm_eval --model hf ...` still works and is treated as `run`. A quick CPU smoke test on GPT-2, with `--limit` so that only 200 items per task are scored:

```bash
lm-eval run --model hf \
  --model_args pretrained=openai-community/gpt2 \
  --tasks arc_easy,hellaswag \
  --limit 200 --batch_size 16 --device cpu \
  --output_path results/
```

```text
hf ({'pretrained': 'openai-community/gpt2'}), gen_kwargs: ({}), limit: 200.0, num_fewshot: None, batch_size: 16
|  Tasks  |Version|Filter|n-shot| Metric |   |Value|   |Stderr|
|---------|------:|------|-----:|--------|---|----:|---|-----:|
|arc_easy |      1|none  |     0|acc     |↑  |0.405|±  |0.0348|
|         |       |none  |     0|acc_norm|↑  |0.375|±  |0.0343|
|hellaswag|      1|none  |     0|acc     |↑  |0.370|±  |0.0342|
|         |       |none  |     0|acc_norm|↑  |0.440|±  |0.0352|
```

Read the table the way the harness intends. `acc` is the raw log-likelihood rule from earlier; `acc_norm` is the length-normalized one. On HellaSwag, where endings differ a lot in length, normalization helps; on ARC-Easy it can hurt. The `Stderr` column is the standard error formula above (with $n-1$ in the denominator: $\sqrt{0.405 \cdot 0.595 / 199} = 0.0348$). With `--limit 200` it is about 3.5 points, so even the 7-point HellaSwag gap between `acc` and `acc_norm` is only two standard errors wide, which is why `--limit` is for debugging only: publish full-set numbers.

Other flags you will use: `--num_fewshot 5` for few-shot prompts, `--apply_chat_template` to wrap prompts in the model's chat template (essential for instruction-tuned models on generative tasks), `--log_samples` to save every prompt and response so you can inspect failures, and `--model vllm` for a much faster backend on a GPU. Other suites follow the same idea: Stanford's HELM (Liang et al., 2022) emphasizes many metrics per scenario beyond accuracy, and Hugging Face `lighteval` and OpenAI's `simple-evals` are common alternatives.

## Why Benchmarks Stop Working

Benchmarks have a life cycle. They start hard, a few labs make progress, the community adopts them, and within a few years the top models cluster near the ceiling. Four forces drive this:

- **Saturation.** When the top scores sit within a couple of points of the label-noise ceiling, the benchmark cannot separate models any more. HellaSwag, GSM8K and the original HumanEval are in this state for frontier models.
- **Goodhart's law.** "When a measure becomes a target, it ceases to be a good measure." Labs tune data mixtures, prompts and decoding for the benchmarks they will report. The model gets better at the benchmark faster than at the skill.
- **Contamination.** Test items leak into pretraining data. Models then score well by recall. GSM1k (Zhang et al., 2024), a fresh set written to mirror GSM8K, found that some model families scored several points lower on the new questions.
- **Distribution mismatch.** Your users do not ask MMLU questions. A model that leads on knowledge benchmarks can still be worse at following your output format, at your language or at refusing the right requests.

The field's response has been to make benchmarks dynamic (LiveBench and LiveCodeBench refresh questions after model release dates), harder (GPQA, HLE), more realistic (SWE-bench, agentic tasks) or preference-based (Chatbot Arena, covered in the [judge page](./2-llm-llm-as-judge.mdx)). None of these removes the need for your own evaluation.

## Worked Scenario: Choosing a Model for a Support Assistant

Suppose you must pick between two open-weight 8B models for an internal IT-support assistant. Model X scores 2 points higher on MMLU-Pro; model Y scores higher on IFEval. Which one?

Neither benchmark answers the question. A sound process looks like this:

1. **Write 150 to 300 real tasks.** Pull anonymized tickets, write the reference resolution for each, and tag them by type (password reset, VPN, hardware, out-of-scope).
2. **Decide the scoring rule per type.** Tasks with a single correct action (which form to file) get exact match after normalization. Open-ended explanations get a rubric scored by a judge model, validated against your own labels on 50 items (see [LLM-as-a-Judge](./2-llm-llm-as-judge.mdx)). Out-of-scope tasks score 1 only for a polite refusal.
3. **Freeze the prompt and decoding.** Use the system prompt you will ship, temperature 0 or the production temperature with several samples.
4. **Run both models, save every output** (the equivalent of `--log_samples`), and compute per-type accuracy with paired bootstrap intervals.
5. **Read failures.** Twenty minutes of reading outputs usually tells you more than the aggregate: one model may ignore the JSON format, another may invent ticket numbers.

With 200 items, a 5-point paired difference is usually detectable; a 2-point one usually is not. If the interval includes zero, pick on cost, latency or license. Keep the set private and add to it whenever production reveals a new failure. This private set is the most valuable evaluation asset you will own.

## Common Mistakes

- Comparing scores from different papers without checking that the prompt template, few-shot count and scoring rule (`acc` versus `acc_norm`, letter versus content) are the same.
- Ranking models by differences smaller than the confidence interval, especially on benchmarks with fewer than 500 items.
- Comparing two models with unpaired intervals instead of a paired bootstrap on the same items.
- Estimating pass@k with $1-(1-c/n)^k$, which is biased low; use the combinatorial estimator.
- Evaluating an instruction-tuned model without its chat template, or a base model with one, and blaming the model for the result.
- Trusting answer extraction blindly. Inspect a sample of "wrong" generations; many are formatting failures.
- Publishing numbers computed with `--limit`, or choosing the prompt variant that gives the best score on the test set.
- Treating a saturated or contaminated benchmark as evidence of progress.

## Summary

- A benchmark score is the product of items, prompt, decoding, scoring rule and aggregation; change any of them and the number moves.
- Log-likelihood scoring picks the most probable candidate; raw sums favour short answers and length-normalized scores (`acc_norm`) can favour long ones.
- Generative benchmarks depend on answer extraction; code benchmarks execute tests and report pass@k with the unbiased estimator $1 - \binom{n-c}{k}/\binom{n}{k}$.
- Small benchmarks have wide error bars: about plus or minus 7 points at 60% on 198 items. Compare models with paired tests.
- The lm-evaluation-harness gives reproducible scores with standard errors; always state the task version, few-shot count and template.
- Benchmarks saturate, get gamed and leak into training data; build a private, task-specific evaluation for any real decision.
