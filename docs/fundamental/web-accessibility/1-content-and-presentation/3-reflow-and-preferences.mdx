# Reflow, Text Resizing, and User Preferences

A usable layout adapts when readers enlarge text, narrow the viewport, or apply their own presentation preferences. Fixed heights and hidden overflow often conceal problems until a reader changes the default settings.

**Prerequisites:** CSS box sizing and normal flow. Use a fresh page containing a main region with a heading, paragraphs, and a native button. Apply the stylesheet below independently from earlier experiments.

## Build a flexible baseline

```css
* { box-sizing: border-box; }
body { margin: 0; font: 1rem/1.6 system-ui, sans-serif; }
main { width: min(100% - 2rem, 65ch); margin-inline: auto; }
h1 { font-size: clamp(1.75rem, 1rem + 3vw, 3rem); }
p, h1, button { overflow-wrap: anywhere; }
button {
  max-inline-size: 100%;
  padding: 0.75em 1em;
  font: inherit;
  white-space: normal;
}
```

The content has bounded measure and flexible side space. Text can create additional lines, and the button can grow vertically. There is no fixed card height that silently clips a longer translation or a larger font.

Test both browser zoom and text-size changes. They exercise related but different behavior. A layout that works at a wide viewport with large text may still fail at a narrow viewport, and vice versa. For common vertically scrolling content, WCAG reflow guidance uses a width equivalent to 320 CSS pixels, with exceptions for content that requires a two-dimensional layout. At 400% zoom, a 1280px-wide viewport commonly provides that effective width.

## Respect motion preferences without losing feedback

Make motion optional rather than essential to understanding an action:

```css
@media (prefers-reduced-motion: no-preference) {
  button { transition: background-color 160ms ease; }
}
```

The baseline remains still. Removing a transition should not remove success text, hide a loading state, or make a control stop working. Avoid an automatic animated demonstration that readers must endure just to inspect the example.

Do not confuse reduced motion with turning off all interaction. A disclosure should still open, and a form should still show errors; they simply need not animate those changes. If a page has ongoing movement or time-dependent content, assess its additional pause and timing requirements separately.

## Preserve user-selected colors

Forced-colors modes may replace your palette. Native controls, real borders, and outlines generally provide a better starting point than controls drawn entirely through shadows or background images.

```css
:focus-visible { outline: 3px solid currentColor; outline-offset: 4px; }
@media (forced-colors: active) {
  button { border: 2px solid ButtonText; }
}
```

Test the actual mode when possible. Do not globally apply `forced-color-adjust: none` to preserve branding: that can prevent the user's selected palette from doing its job. A browser's emulation is useful for finding issues, but it is not a substitute for testing the complete supported environment.

## Exercise and checks

Give the heading a much longer phrase, increase the root font size to 200% in developer tools, and narrow the viewport to 320 CSS pixels. Confirm that the page does not require horizontal scrolling for ordinary content and that the button's label remains visible.

Then test reduced motion and a forced-colors setting. A successful solution keeps the focus indicator, button boundary, text, and interaction results available. If a region grows beyond the viewport, inspect its intrinsic minimum width or unbroken text before hiding the overflow.
