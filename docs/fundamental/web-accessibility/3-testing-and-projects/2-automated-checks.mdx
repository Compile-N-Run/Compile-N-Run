# Automated Accessibility Checks with Playwright

Automation is useful for catching repeatable regressions. It cannot decide whether alternative text accurately describes an image, whether instructions are understandable, or whether every supported assistive-technology workflow is usable.

**Prerequisites:** Node.js with npm, basic JavaScript, and the [workshop project](./3-accessibility-capstone.mdx). Create a separate `a11y-checks` directory; do not install test dependencies into a published static-assets folder.

## Install the test tools

In the new directory, run:

```bash
npm init -y
npm install --save-dev @playwright/test @axe-core/playwright
npx playwright install chromium
```

Keep the generated lockfile with a real test project so collaborators can reproduce its dependency versions with `npm ci`. Browser installation may also require operating-system dependencies; follow Playwright's installation guidance for your environment instead of assuming every machine is already configured.

Serve a copy of the capstone files from a second terminal:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

Run that command from the directory containing the capstone's `index.html`. On Windows, use your installed Python launcher, such as `py`, when appropriate. Keep this terminal running while the tests execute.

## Test a meaningful state

Save this as `accessibility.spec.js` in `a11y-checks`:

```javascript
const { test, expect } = require('@playwright/test');
const AxeBuilder = require('@axe-core/playwright').default;

test('practice form exposes errors and a local result', async ({ page }) => {
  await page.goto('http://127.0.0.1:8000/');
  await page.getByRole('button', { name: 'Check practice details' }).click();
  await expect(page.locator('#error-summary')).toBeFocused();
  await expect(page.locator('#error-list li')).toHaveCount(2);

  const invalidState = await new AxeBuilder({ page }).analyze();
  expect(invalidState.violations).toEqual([]);

  await page.getByLabel('Practice name (required)').fill('Practice Learner');
  await page.getByLabel('Session (required)').selectOption('html');
  await page.getByRole('button', { name: 'Check practice details' }).click();
  await expect(page.getByRole('status')).toHaveText(
    'Practice details checked. Nothing was sent or saved.'
  );
  await expect(page.locator('#error-summary')).toBeHidden();
});
```

Run `npx playwright test accessibility.spec.js --workers=1`. The interaction assertions check behavior the rules engine does not infer: current errors, focus placement, successful correction, and truthful feedback. The rules scan runs on the invalid state rather than only the initial page.

## Interpret results carefully

Investigate reported violations before changing assertions. A rules engine may also return incomplete checks that need human judgment; zero reported violations is not a complete assessment. Inspect the output and test additional relevant states, including expanded content and validation success.

Do not silence a failing rule across the whole application because one component is inconvenient to repair. If a narrowly scoped exception is necessary, record the reason, the affected element, and the follow-up work. A permanent blanket exclusion can conceal unrelated future regressions.

## Exercise and checks

Add an assertion that activating the first error-summary link focuses the name field. Then add a scan of the initial page. A suitable focus assertion uses `toBeFocused()` on `#practice-name` after clicking its summary link.

Keep manual keyboard, resizing, and screen-reader checks in the test plan. An automated rules pass supports a specific set of checks at a specific state; it does not certify the full website or its complete user journeys.

Further reading: [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing) and [W3C evaluation tools overview](https://www.w3.org/WAI/test-evaluate/tools/).
