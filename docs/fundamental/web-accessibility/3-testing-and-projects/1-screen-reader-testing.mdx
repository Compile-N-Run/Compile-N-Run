# Screen-Reader Testing and Useful Evidence

A browser's accessibility tree helps explain exposed semantics. A screen reader shows how those semantics are used during navigation and interaction. Neither one replaces feedback from people who use assistive technology routinely.

**Prerequisites:** [The manual audit workflow](./0-manual-audit.mdx). Choose a screen reader supported by your operating system, such as NVDA on Windows or VoiceOver on macOS. Use the official guide to learn how to start and stop it and how to navigate headings, controls, and ordinary text.

## Learn the navigation model first

Reading commands and Tab navigation serve different purposes. A screen reader can navigate static headings and paragraphs even though those elements are not keyboard Tab stops. Some tools also switch between document-reading and form-interaction modes. If typing unexpectedly activates navigation commands, check the current mode before changing the page.

Do not copy keyboard shortcuts across tools and assume they have identical meanings. Record the actual screen reader, browser, operating system, versions, and relevant settings. A useful result is tied to that combination, not to a claim that every possible environment behaves identically.

## Follow the same task as other readers

Open the [workshop example](/examples/web-accessibility/index.html). Find the page's main heading and navigate to the practice form. Inspect each control's name, role, required state, and help text. Enter invented values, submit an invalid form, use the summary links, and correct the errors.

Ask concrete questions: Can you distinguish the two fields? Is the error explanation available when returning to its input? Does the successful check communicate a result while leaving the task understandable? A technically exposed description may still be too verbose or repeated in an unhelpful sequence.

When testing a live region, keep focus on the initiating control and listen for the update. Announcement timing can vary, especially while other content is being spoken. Do not treat a browser DOM mutation log as proof that a screen reader announced the intended message.

## Capture evidence without overgeneralizing

Write down the action and the information communicated. Exact speech can help diagnose a problem, but your acceptance criterion should usually focus on meaning: the field's identity, its state, and the correction needed. Different tools may announce these in different orders or use different words.

If the browser tree is correct but the experience is confusing, investigate both implementation and interaction design. If a problem occurs in only one combination, reproduce it with a minimal example and consult platform or pattern guidance. Avoid adding extra roles and labels blindly; that can create duplicate output elsewhere.

## Exercise and acceptance checks

Create a short test note for the initial form, one invalid submission, and a successful local check. Include the tested environment and any task you could not complete. If you do not have a screen reader available, mark this portion as not tested rather than inferring a pass from automated results.

A successful learning exercise distinguishes reading navigation from focus navigation, identifies the form's names and descriptions, and checks feedback after interaction. Where possible, invite an experienced assistive-technology user to review the workflow. Their observations can reveal usability issues that a beginner test misses even when the underlying markup is valid.
