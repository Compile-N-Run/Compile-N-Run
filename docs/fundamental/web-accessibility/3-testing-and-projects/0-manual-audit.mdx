# A Repeatable Manual Accessibility Audit

A useful audit produces evidence someone else can reproduce. Start with a real task and follow it through success and failure, rather than scanning the initial page for a list of attributes.

**Prerequisites:** The first three chapters. Use the [workshop practice project](/examples/web-accessibility/index.html), or a page you own with comparable controls. This is an introductory audit workflow, not a complete conformance evaluation.

## Define the environment and task

Record the browser, operating system, viewport, zoom level, and relevant input or presentation settings. Choose a task such as “Select a workshop and correct a missing-name error.” Include the starting URL and any setup needed to reproduce the state.

A compact test record might look like this:

```text
Task: correct an empty practice form
Start: workshop page, no fields completed
Input: keyboard only
Expected: error summary receives focus; links reach invalid fields
Observed: [record what actually happens]
Environment: [browser, OS, versions, zoom]
```

Do not fill in the observed result from what the code appears to do. Run the interaction. A correct-looking selector can still point at a hidden element or execute at the wrong time.

## Check several dimensions

First, inspect document structure: title, language, headings, regions, names, and instructions. Next, use only the keyboard. Check the skip link, forward and reverse navigation, visible focus, disclosure controls, field entry, errors, and completion.

Then test presentation changes. Enlarge text, zoom the page, narrow the viewport, and inspect user-preference modes that apply. Long text and translated labels are useful stress cases. Watch for clipped controls, off-screen messages, and overlays covering the focused element.

Finally, inspect content alternatives. Verify that image descriptions convey the actual information and that any recordings have appropriate alternatives. The presence of an `alt` attribute or caption track is not enough; the content must also serve its purpose.

## Write findings around barriers

A finding should identify the action, actual behavior, expected behavior, and likely impact. “Focus outline missing” is a start; “After Tab reaches Preview request, no visible indicator distinguishes it from the unfocused state” is easier to reproduce.

Separate the observed problem from your proposed fix. For example, the problem may be that an error message is not discoverable. One solution is an error summary with focus management; another design may solve the same barrier differently. This separation helps reviewers improve the implementation without losing the original requirement.

Prioritize issues that block a complete task, then those that make completion unreliable or unnecessarily difficult. Preserve exact steps and relevant screenshots or recordings, but do not collect private form values merely to demonstrate a problem.

## Exercise and acceptance checks

Audit the workshop example through three states: initial page, invalid form, and successful local check. Document at least one check for keyboard behavior and one for enlarged text in each relevant state.

For practice, temporarily remove the label association in your own copy, confirm the changed accessible name, then restore it. This gives you a known defect for evaluating your method. A successful report describes the observed change and the verification after repair, rather than simply saying that the page “passes accessibility.”

Continue with [screen-reader testing](./1-screen-reader-testing.mdx). Its findings complement keyboard and visual checks, because these approaches inspect different aspects of the experience.

Further reading: [W3C preliminary accessibility checks](https://www.w3.org/WAI/test-evaluate/preliminary/).
