# Native Widgets, Dialogs, and ARIA

ARIA describes roles, states, and relationships. It does not implement keyboard interaction, toggle visibility, or move focus for you. Start with a native element when it matches the behavior you need.

**Prerequisites:** [Keyboard and focus](../0-foundations/3-keyboard-and-focus.mdx) and basic JavaScript. Place these examples in fresh practice documents so IDs and event handlers do not collide with earlier lessons.

## Use a disclosure for optional information

```html
<details>
  <summary>What should I bring?</summary>
  <p>Bring a clean bicycle and a water bottle.</p>
</details>
```

A disclosure keeps the rest of the page available. Its summary is a native interactive control. Do not add a button inside the summary, duplicate an expanded state manually, or trap focus inside the revealed paragraph. Test opening and closing it with both pointer and keyboard input.

A custom disclosure would need its own control, expanded state, visibility behavior, and keyboard checks. Building that machinery is justified only when the native pattern cannot satisfy the actual requirement.

## Use a modal only when the task requires it

A modal temporarily makes the background unavailable. The native dialog element provides that behavior through `showModal()`:

```html
<button id="open-help" type="button">Open workshop help</button>
<dialog id="help" aria-labelledby="help-title">
  <h2 id="help-title">Workshop help</h2>
  <p>Ask the reception desk to help you find your session.</p>
  <form method="dialog">
    <button autofocus>Close help</button>
  </form>
</dialog>
<script>
  const opener = document.querySelector('#open-help');
  const dialog = document.querySelector('#help');
  opener.addEventListener('click', () => dialog.showModal());
</script>
```

Open the dialog, check the initial focus, and close it using the button and Escape. Verify that focus returns to the opening control. The native modal mechanism handles background interaction differently from a styled `div` with a high stacking order. Merely setting `open` on a dialog does not invoke the same modal behavior as `showModal()`.

Keep long dialog content scrollable and controls reachable at narrow widths and enlarged text. Avoid opening a modal on page load without a user need. For longer documents, choose an initial focus destination that supports understanding the content rather than blindly copying this short-dialog example.

## Treat ARIA patterns as complete contracts

Roles such as `tab`, `menuitem`, and `combobox` imply established interaction models. A site navigation list is not automatically an application menu. Adding `role="menu"` to ordinary links without implementing the expected model can make navigation harder.

When a custom widget is necessary, study its full pattern: names, states, relationships, keyboard commands, focus movement, disabled behavior, and how it closes. Test the whole interaction in supported browser and assistive-technology combinations. A role attribute passing an automated check does not establish that the pattern works.

## Exercise and checks

Decide whether preparation advice belongs in an always-visible section, a disclosure, or a modal. Explain the tradeoff before writing code. Then implement the simplest suitable choice.

A successful solution leaves critical instructions available, provides a meaningful control name, and has a predictable keyboard path. For the dialog experiment, confirm background controls cannot be operated while it is open and the close action returns focus appropriately. Do not claim a custom focus trap is complete after testing only one Tab press.
