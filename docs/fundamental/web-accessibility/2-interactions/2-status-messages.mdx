# Status Messages and Dynamic Updates

A visible change does not automatically become an announcement. If a result updates elsewhere on the page while focus stays on a control, some readers may miss it. A well-chosen status region can communicate the result without interrupting the task.

**Prerequisites:** Basic JavaScript event listeners and [accessible names](../0-foundations/2-accessible-names.mdx). Use the introduction's document shell. Put this fragment in the body and the script after it.

## Update an existing region

```html
<button id="add-item" type="button">Add one practice item</button>
<p id="item-status" role="status"></p>
<script>
  const button = document.querySelector('#add-item');
  const status = document.querySelector('#item-status');
  let count = 0;
  button.addEventListener('click', () => {
    count += 1;
    status.textContent = `${count} practice item${count === 1 ? '' : 's'} added.`;
  });
</script>
```

The status region exists before the first update. A status role has polite live-region behavior, suitable for many nonurgent results. The button retains focus, and the visible message changes to “1 practice item added,” then “2 practice items added.” Screen-reader announcement timing depends on the technology and what else is being spoken; test the resulting experience rather than promising exact wording or timing.

This example stores its count only in memory. Reloading resets it. The interface does not imply that anything was saved remotely.

## Choose the smallest useful message

Announce the outcome people need, such as “Three results found” or “Draft saved,” rather than repeating a long updated container. Do not make the entire main region live; minor content changes can then create a stream of irrelevant announcements.

A live region does not need to receive focus just to be announced. Moving focus to every search result count makes continued typing difficult. Reserve deliberate focus changes for situations such as navigating to an error summary or opening a modal dialog.

An urgent alert uses a different interruption model. It should not be the default for ordinary counts, background refreshes, or routine confirmations. Repeated assertive messages can make a page difficult to operate, even when each message is technically exposed to accessibility tools.

## Handle asynchronous work honestly

For a real request, announce success only after it succeeds. A failed request needs an error that explains a recovery action. If a result area is marked busy during updates, clear that state when work finishes, including failures. Keep a loading message accurate; never leave a permanent “Loading” state after rejecting a request.

Avoid placing sensitive data in global announcements unnecessarily. A short confirmation can identify the task without reading a full address or other private detail aloud. Keep the underlying content available for review through ordinary navigation.

## Exercise and solution

Add a reset button that sets the practice count to zero and updates the same status region. A suitable handler assigns `count = 0` and sets `status.textContent` to “Practice count reset.” It should not create a second region or force focus into the message.

Activate add, add, and reset with the keyboard. Verify the visible results first, then test announcements with a screen reader. Repeated identical text updates may not be announced consistently, so do not depend on a reset message being spoken again when nothing actually changes. Record that distinction between visual behavior and assistive-technology behavior.
