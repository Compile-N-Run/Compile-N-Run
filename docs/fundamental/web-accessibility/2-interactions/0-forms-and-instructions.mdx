# Accessible Forms and Instructions

A form is a conversation: ask for information, explain the requirements, and help the person complete the task. Visible labels and native controls provide a strong starting point, but the form also needs understandable instructions and feedback.

**Prerequisites:** [Accessible names](../0-foundations/2-accessible-names.mdx) and [HTML forms](/docs/language/html/html-forms/). Use invented values in these exercises; the examples demonstrate interaction rather than collecting real registrations.

## Put requirements beside the control

Insert this fragment into a fresh practice page. It demonstrates labeled controls, not a submission endpoint:

```html
<form>
  <p id="practice-help">Use invented details. This practice form has no server.</p>
  <p>
    <label for="practice-name">Practice name (required)</label>
    <input id="practice-name" name="practice_name" required
           aria-describedby="practice-help">
  </p>
  <fieldset>
    <legend>Preferred session (required)</legend>
    <p>
      <input id="html-session" type="radio" name="session"
             value="html" required>
      <label for="html-session">HTML structure</label>
    </p>
    <p>
      <input id="css-session" type="radio" name="session"
             value="css" required>
      <label for="css-session">CSS layout</label>
    </p>
  </fieldset>
</form>
```

The label's `for` value matches the input ID. The help paragraph is referenced as a description. The radio buttons share a name, making them one choice group, and the fieldset's legend explains the group. Required information is communicated in words as well as through the native constraint.

Use placeholders only as supplementary examples when appropriate. They disappear during typing and may have insufficient contrast. A short visible hint such as “Enter a number from 1 to 4” is easier to revisit than a placeholder that vanishes after the first character.

## Choose controls for the data

Use a checkbox for an independent on/off choice and a radio group or select for one choice among alternatives. A text field containing “yes” or “no” forces readers to infer an unnecessary input format. Native controls also provide platform keyboard interaction that would be expensive to recreate.

For real personal-information fields, appropriate autocomplete tokens can help identify input purpose and reduce repeated typing. The practice-name field above intentionally does not request a real person's name. Do not disable pasting into fields as an authentication or accessibility shortcut; people may rely on password managers or other input assistance.

## Keep instructions and actions predictable

Do not navigate to another page merely because someone focuses a field. Avoid submitting a form immediately when a select option changes unless the behavior is clearly appropriate and communicated. A visible submit button gives users control over when to proceed.

Disabled fields generally do not participate in normal focus or form submission. Readonly text fields behave differently. Do not disable a required field without explaining how the user can complete the process. A disabled “Continue” button with no explanation can leave people unable to discover what is missing.

## Exercise and checks

Add a seat-count field with a visible label, `type="number"`, `min="1"`, `max="4"`, and a persistent hint. Associate the hint through `aria-describedby` and keep its ID unique.

A successful solution lets you click the label to focus the control, inspect a meaningful accessible name and description, and enter a value using the keyboard. Verify that the two session radios act as one group. The next lesson adds error presentation; naming a field correctly does not by itself explain what happens when its value is invalid.
