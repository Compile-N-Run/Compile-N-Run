# Form Errors and Recovery

An error is useful only if someone can discover it, understand it, and correct it. A red border alone does not identify the problem, and an alert saying “Invalid input” does not identify the field or the expected correction.

**Prerequisites:** [Form instructions](./0-forms-and-instructions.mdx). This lesson shows the rendered state after an invalid submission. The [capstone](../3-testing-and-projects/3-accessibility-capstone.mdx) includes the complete working validator.

## Show a summary and field-level guidance

```html
<section id="error-summary" tabindex="-1" aria-labelledby="error-title">
  <h2 id="error-title">Check your entries</h2>
  <ul><li><a href="#practice-name">Enter a practice name.</a></li></ul>
</section>
<form>
  <label for="practice-name">Practice name (required)</label>
  <input id="practice-name" name="practice_name" required
         aria-invalid="true" aria-describedby="name-help name-error">
  <p id="name-help">Use an invented name for this demonstration.</p>
  <p id="name-error">Enter a practice name.</p>
</form>
```

The summary provides an overview and a route back to the affected field. The inline error stays near the field and participates in its description. Keep the label stable: replacing it with the error can make the field's identity disappear just when the person needs it.

In the real interaction, focus the summary after rendering the errors:

```javascript
const summary = document.querySelector('#error-summary');
summary.hidden = false;
summary.focus();
```

Run that code after handling an invalid submit, not repeatedly on every keystroke. A summary with `tabindex="-1"` can receive programmatic focus without adding another routine Tab stop. Its links provide a direct correction path. Test the focus destination and announcements with the assistive technologies you support.

## Keep state synchronized

Do not mark untouched fields invalid as soon as the page opens. When validation finds an error, update the message, `aria-invalid`, and description references together. When the error is resolved, remove the invalid state and stale error reference while retaining persistent help text.

Native validation can be a useful baseline. If JavaScript supplies a custom summary, enable `noValidate` from the enhancement script rather than placing `novalidate` in static HTML without a working alternative. Otherwise a failed script could leave users with neither native feedback nor custom feedback.

Browser validation improves the input experience; it is not a security boundary. A real server must validate the submitted data independently. If server validation rejects a request, preserve valid input and present those errors through the same understandable recovery flow.

## Avoid duplicate or disruptive feedback

An error summary that receives focus may not also need an assertive announcement of the same complete content. Adding multiple live regions and forced focus changes can produce repeated or competing messages. Choose a feedback strategy, test it, and keep it consistent.

Do not clear the entire form after a failed submission. That makes people repeat correct work. Similarly, do not move focus away while someone is trying to type a correction. Validate at deliberate moments and explain any immediate validation behavior.

## Exercise and acceptance checks

Extend the sample error state to include a missing session. Give the session control its own error ID and add a second summary link. Activate each link and confirm that the intended field receives focus or an appropriate navigation destination in the supported browser.

A successful solution distinguishes both problems, preserves existing values, and removes obsolete errors after correction. Try submitting twice: the summary should contain the current errors once each, not accumulate duplicates from the previous attempt.
