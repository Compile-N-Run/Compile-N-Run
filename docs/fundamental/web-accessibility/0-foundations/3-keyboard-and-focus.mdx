# Keyboard Navigation and Visible Focus

Keyboard access is a functional requirement. People may navigate using a keyboard, switches, voice commands, or software that sends equivalent input. A mouse-free test quickly reveals controls that respond only to pointer actions.

**Prerequisites:** [Accessible names](./2-accessible-names.mdx). Use the introduction's page, then add the following styles in a `style` element in its head.

## Make focus easy to locate

```css
:focus-visible {
  outline: 3px solid #8b1538;
  outline-offset: 4px;
}
.skip-link {
  position: absolute;
  top: -10rem;
  left: 1rem;
  padding: 0.75rem;
  background: white;
  color: #18243a;
}
.skip-link:focus { top: 0.5rem; }
```

Give the existing skip link `class="skip-link"`. It moves into view when focused, rather than disappearing from keyboard navigation. Do not use `display: none` for a skip link that should be reachable. Keep the target as `main id="main" tabindex="-1"` so it can receive focus without adding a routine Tab stop.

The outline is an example design choice, not a complete standards assessment. Test it against the actual backgrounds and in user-selected colors. A focus indicator that blends into a card border can be present in CSS but difficult to see.

## Follow the native interaction model

Tab and Shift+Tab generally move among interactive elements. Enter activates links. Native buttons support Enter and Space. Checkboxes and radio groups have their own keyboard behavior; do not intercept keys unnecessarily.

Keep DOM order logical and avoid positive `tabindex` values. A value such as `tabindex="5"` creates a separate priority sequence that becomes difficult to maintain. Use `tabindex="0"` only when an element genuinely needs to join the natural sequence, and `-1` for deliberate programmatic focus targets.

A click handler on a noninteractive paragraph is not a substitute for a button. Adding `tabindex` alone does not supply the missing role, activation behavior, disabled semantics, or state management. Choose the appropriate native element first.

## Watch for hidden and covered focus

Test sticky headers, cookie notices, dialogs, and expanded panels. An element may receive focus while a fixed overlay covers it. WCAG 2.2 distinguishes visible focus from focus not being entirely obscured by author-created content; passing one does not establish the other. Avoid sticky positioning until the design has been tested with small viewports and enlarged text.

Closing a temporary widget should leave focus somewhere meaningful. If opening a panel removes or hides the initiating control, explicitly plan the return path. A dialog also needs an appropriate focus containment and dismissal model; a general disclosure does not automatically need one.

## Exercise and checks

Navigate the practice page without a mouse. Write down the stops in order, activate the skip link, and reverse the sequence with Shift+Tab. Add a native `details` element with a `summary`, then open and close it using the keyboard.

A successful test has no unexpected traps, a visible focus indicator at every stop, and a sensible next stop after a widget closes. Repeat at 200% zoom. If an element is hard to reach, repair its semantics or source order before trying to fix the sequence with positive tabindex values.
