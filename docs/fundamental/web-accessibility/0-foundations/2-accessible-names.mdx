# Accessible Names, Roles, and Descriptions

A control needs an identity as well as a position. Its role describes what kind of thing it is, its name identifies it, and states communicate properties such as whether it is checked. A description can add instructions without replacing the name.

**Prerequisites:** [Semantic structure](./1-semantic-structure.mdx). Use a fresh copy of the introduction's HTML shell for these body fragments.

## Prefer a visible name

A text button gets a useful name from its content:

```html
<button type="button">Show preparation advice</button>
```

This fragment demonstrates naming only; behavior is added in the interactions chapter. A native button already supplies its role and standard keyboard behavior. A styled `div` with the same text does not become a button merely because it looks clickable.

For a field, connect a visible label with its unique ID:

```html
<label for="display-name">Display name</label>
<input id="display-name" name="display_name"
       aria-describedby="name-help">
<p id="name-help">Use an invented name for this practice form.</p>
```

Here the label supplies the name, while the help paragraph supplies a description. The `name` attribute serves form submission; it does not replace a label. Placeholder text disappears during input and is a poor substitute for a persistent visible label.

## Avoid competing naming systems

Adding `aria-label="Participant"` to the input above can override its visible label in the accessibility tree. A speech-input user who sees “Display name” may then encounter a different programmatic name. Keep visible and accessible names aligned; the visible wording should be included in the accessible name.

When an existing visible heading or phrase should name another element, `aria-labelledby` references its ID. Multiple IDs can combine text into a name, but this adds complexity. Inspect the computed result instead of assuming that every label-like attribute is combined. Naming rules depend on the element and role, and some elements do not support author-provided names.

An icon-only button needs a name that explains the action. For a beginner project, retaining visible text is often easier to understand and test:

```html
<button type="button">
  <span aria-hidden="true">+</span> Add another session
</button>
```

The plus sign is redundant decoration. Hiding it from assistive technologies leaves the useful text intact. Never put `aria-hidden="true"` on the button or a container with focusable controls merely to reduce announcements; that can expose a keyboard stop with no accessible identity.

## Inspect the computed result

Open developer tools, select the field, and find the accessibility information for its role, name, and description. Panel names vary by browser. Expect a text-input role, the name “Display name,” and the practice instruction as its description.

Change the label text to “Practice name” and inspect again. Then temporarily introduce a mismatched ARIA label and observe the difference. Remove the mismatch before keeping the example. This experiment helps distinguish rendered text from the name exposed to accessibility tools.

## Exercise and solution

Create two buttons for separate actions: “Add session” and “Remove session.” Use visible text, and avoid identical generic names such as “Go.” Add a decorative symbol only if the text still explains the action by itself.

A successful solution exposes a distinct button name for each control and leaves neither button unnamed. The next step is implementing real actions, not adding more ARIA attributes.
