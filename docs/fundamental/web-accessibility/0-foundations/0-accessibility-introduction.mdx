# Web Accessibility Introduction

Accessibility means people can perceive information, operate controls, understand the interface, and use it with the technologies they depend on. It belongs in ordinary implementation decisions: choosing a link, naming a field, ordering a document, and explaining an error.

**Prerequisites:** Basic [HTML](/docs/language/html) and [CSS](/docs/language/css). Later interaction lessons use small JavaScript examples. Start with a browser and a plain-text editor; assistive-technology testing comes after the foundational exercises.

## Start with a task and a barrier

Imagine a visitor trying to find a workshop and complete an interest form. A mouse-only control can block a keyboard user. A schedule stored only in a picture can hide information from someone who cannot see it. Tiny fixed-height inputs may lose their labels when a reader enlarges text.

These are different problems, so one tool cannot prove that the whole experience works. Automated checks find certain markup and contrast issues. Keyboard checks reveal interaction problems. Screen-reader checks help inspect the experience exposed through accessibility APIs. Feedback from people with disabilities adds information these checks cannot replace.

## Build a small baseline

Save the following as `index.html` and open it locally:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Workshop Finder</title>
</head>
<body>
  <a href="#main">Skip to main content</a>
  <header>
    <p>Workshop Finder</p>
    <nav aria-label="Main"><a href="#sessions">Browse sessions</a></nav>
  </header>
  <main id="main" tabindex="-1">
    <h1>Find a beginner workshop</h1>
    <p>Choose a topic and review what to bring.</p>
    <h2 id="sessions">Available sessions</h2>
    <ul><li>Bicycle maintenance: Saturday at 10:00.</li></ul>
  </main>
</body>
</html>
```

Tab should reach the skip link and then the navigation link. Enter activates the focused link. The main region can receive focus through the skip link without becoming an extra stop in ordinary Tab navigation. Browser and operating-system keyboard settings can affect which controls receive Tab focus; check those settings before diagnosing missing stops.

The example has no elaborate styling, yet its source already identifies navigation, the primary content, and a meaningful heading hierarchy. That structure is a useful starting point for visual design, speech output, and future maintenance.

## Use standards as requirements, not a badge

This course uses WCAG 2.2 as a technical reference. Its success criteria have levels A, AA, and AAA. Meeting a selected criterion does not establish conformance for an entire website. A complete assessment considers applicable requirements, full pages, and complete processes, including states reached after interaction.

For each feature, record a task, the expected behavior, and a repeatable check. “A keyboard user can correct an invalid field and submit again” gives a reviewer something concrete to test. “Accessible form” alone does not.

## Exercise and acceptance checks

Add a second session and a heading for preparation advice. Keep the main heading and existing navigation. Complete this task without a mouse: enter the page, skip the header, and locate the available sessions.

A successful solution uses list items for the sessions, an `h2` for the new section, and working fragment targets. Enlarge the page to 200% and check that text remains available. Record one observation and one question for a later assistive-technology check.
