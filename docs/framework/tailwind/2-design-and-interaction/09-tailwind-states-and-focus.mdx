# Interaction States and Visible Focus

A component needs usable states, not just a polished default screenshot. Tailwind variants let you style those states, while native HTML controls provide keyboard behavior and semantics. A blue rectangle with `cursor-pointer` is still not a button unless its underlying element behaves like one.

Use links for navigation and buttons for actions. Keep focus visible, and ensure information remains available without hover. The `hover:` variant is an enhancement for pointer interaction, not a substitute for a keyboard path.

## Style native controls

Replace the starter body with this local preference form and rebuild:

```html
<main class="mx-auto max-w-lg p-4">
  <h1 class="text-2xl font-bold">Session preferences</h1>
  <form class="mt-6 rounded-xl bg-white p-6">
    <fieldset>
      <legend class="font-semibold">Practice options</legend>
      <label class="mt-4 flex items-start gap-3">
        <input type="checkbox" name="notes" checked
          class="mt-1 size-5 shrink-0 accent-blue-800 focus-visible:outline-2 focus-visible:outline-offset-4 focus-visible:outline-blue-800">
        <span>Keep notes beside the exercise</span>
      </label>
    </fieldset>
    <button type="reset"
      class="mt-6 rounded-md bg-blue-800 px-4 py-3 font-semibold text-white hover:bg-blue-900 focus-visible:outline-2 focus-visible:outline-offset-4 focus-visible:outline-blue-800">
      Restore default
    </button>
  </form>
</main>
```

The checkbox can be toggled with Space when focused. The reset button restores its original checked state. These behaviors come from HTML, not Tailwind. The utilities give the controls a readable size and a visible outline during keyboard navigation.

## Distinguish related states

`focus:` matches an element with focus. `focus-visible:` lets the browser apply focus-indicator heuristics, which commonly include keyboard interaction. `focus-within:` matches a container when it or a descendant has focus. Use group-level highlighting as an addition to, not a replacement for, an individual control's indicator.

`disabled:` styles truly disabled controls. A faded class or `pointer-events-none` alone does not give a control the same semantics, keyboard behavior, or form behavior as the HTML `disabled` attribute. Similarly, `aria-disabled` communicates a state but does not automatically prevent an action.

`group` on a parent enables child variants such as `group-hover:`. `peer` enables styling based on a previous sibling's state, such as `peer-checked:`. These are selector relationships, so their DOM placement matters. They do not let CSS move focus, save preferences, or implement complete application state.

## Avoid removing useful feedback

Do not add an outline-removal utility globally and assume hover styling is enough. A focus ring can also be clipped by an ancestor's overflow, so test the complete component in context. Native checked indicators are a useful baseline; removing control appearance creates responsibility for every state, including forced colors and disabled styling.

## Exercise and solution

Add `disabled` to the reset button and add `disabled:bg-slate-200 disabled:text-slate-600 disabled:cursor-not-allowed`. Verify that it becomes unavailable to ordinary keyboard activation. Remove the attribute and confirm its behavior returns.

Then tab through the form at 200% zoom. The outline, label, and control must remain visible and connected. Continue with [theme variables](./10-tailwind-theme-variables.mdx).
