# Source Detection and Dynamic Class Names

Tailwind scans source text for candidate class names. It does not execute JavaScript, evaluate template expressions, or query a database to discover every class your application might produce. A class must be discoverable during the build for its CSS to exist in the generated file.

This explains a common failure: a development component constructs a plausible class string at runtime, but the production stylesheet never contains that utility. The browser cannot apply a rule that was never generated.

## Make source boundaries explicit

For the starter project's root-level files, replace `input.css` with:

```css
@import "tailwindcss" source(none);
@source "./index.html";
```

Rebuild. The compiler now scans the explicitly registered HTML file instead of relying on the current working directory's automatic discovery. Source paths are relative to the stylesheet. If you later move templates into a `pages` folder, register that actual folder or update the path.

Automatic detection normally excludes places such as `node_modules`, ignored files, binary assets, and CSS files. If a dependency contains templates with utility classes, register the relevant package source deliberately rather than scanning an entire dependency tree.

## Use complete variant maps

In application code, map a state to whole class strings:

```javascript
const statusStyles = {
  ready: "bg-emerald-100 text-emerald-950",
  waiting: "bg-amber-100 text-amber-950",
};
const selectedClasses = statusStyles.ready;
console.log(selectedClasses);
```

The scanner can see both complete alternatives when this file is registered. Constructing a string from fragments such as a color name inserted between `bg-` and `-100` does not expose those finished tokens to the scanner.

If you place this example in `status.js`, add `@source "./status.js"` to the input stylesheet. Registering only `index.html` will not scan the JavaScript file merely because the browser could load it. Build-time discovery and runtime module loading are separate processes.

For a truly externally supplied, finite set of classes, version 4 supports an explicit inline source:

```css
@source inline("bg-emerald-100 text-emerald-950 bg-amber-100 text-amber-950");
```

Keep such lists narrow. Safelisting every possible color, breakpoint, and state can inflate the stylesheet and hide an unclear component API. Prefer a validated set of named design variants when data controls appearance.

## Debug the whole path

When a class has no effect, confirm that the token is complete, its file is scanned, the build finished, and the page loads the current output file. Then inspect the cascade. A generated declaration overridden by another rule is a different problem from a missing declaration.

Do not edit generated CSS to patch a missing utility; the next build will erase that repair. Fix the source or source registration instead.

## Exercise and solution

Create `extra.html` containing a literal `bg-fuchsia-100` class, but leave it unregistered under `source(none)`. Build and inspect the output. Then add `@source "./extra.html"` and rebuild. The corresponding background utility should now be present.

Remove the experiment afterward so your build includes only real application sources. Continue with [accessibility checks](./14-tailwind-accessibility.mdx).
