# Production Builds and Tailwind Debugging

A production page should load a compiled stylesheet. The CLI generates that file ahead of time, so the browser does not need a Tailwind compiler or npm packages. This also makes the deployed result inspectable: the HTML link should resolve to an actual CSS asset containing the expected utilities.

Use the version-pinned dependencies from the setup lesson and keep the lockfile. Reproducibility depends on the resolved build environment as well as your source files.

## Add repeatable scripts

In the starter's existing `package.json`, add a scripts object while keeping its dependency entries:

```json
{
  "scripts": {
    "dev": "tailwindcss -i ./input.css -o ./output.css --watch",
    "build": "tailwindcss -i ./input.css -o ./output.css --minify"
  }
}
```

Within npm scripts, the installed CLI binary is available by name. This fragment is not a complete replacement package file; retain the pinned `tailwindcss` and `@tailwindcss/cli` dev dependencies.

Run:

```bash
npm run build
```

Expect a successful compilation and a compact `output.css`. Open the HTML and check the Network panel or local file link to confirm that this output is what the browser loads. Minification reduces representation size; it does not fix missing classes, invalid markup, or unnecessary source scanning.

For a fresh copy with the lockfile present, use `npm ci` before building. Serve or publish only the HTML and required static assets. Keep dependency directories and temporary build caches out of the public website.

## Diagnose failures by stage

First confirm source intent: is the class spelled correctly and complete? Next confirm discovery: is its source file registered or automatically scanned? Then confirm compilation: did the watcher finish without an error? Finally confirm delivery: is the browser loading the newly generated output instead of an old cached file or a different path?

Once the rule exists in the browser, inspect the cascade. A crossed-out declaration means a competing rule won. A valid winning width can still produce overflow because a child has a content-based minimum. Tailwind debugging ultimately becomes CSS debugging after the build and delivery stages are correct.

Use the computed-style panel and layout overlays rather than adding stronger utilities at random. If normal unlayered custom CSS beats a layered utility, decide where that custom rule belongs instead of applying importance everywhere.

## Keep the browser baseline explicit

Tailwind 4 relies on modern CSS features. Review its documented browser requirements before using it in an application that must support older engines. A successful build does not polyfill every runtime feature. Test the browsers your project actually supports, including native controls and preference media queries.

## Exercise and solution

Create a clean copy of the project containing only source files, `package.json`, and the lockfile. Run `npm ci` and `npm run build`, then open the page. It should match the original without copying its old output or dependency directory.

Delete a source registration intentionally and observe the resulting missing utility, then restore it. This confirms that the clean build is testing the real source boundary rather than relying on a stale generated file.
