# Node.js Dependencies and Lockfiles

A dependency saves implementation work but adds code, maintenance obligations, and a trust decision. Use a package when it solves a real requirement, and preserve enough metadata for another machine to install the same dependency graph.

**Prerequisites:** [Package manifests](./1-nodejs-package-json-and-scripts.mdx). The course capstone deliberately uses built-in APIs, so no third-party dependency is required for these lessons.

## Separate a request from a resolution

A manifest can request a version range such as `^2.3.0`. Under the ordinary semantic-versioning rules for a nonzero major, this permits compatible updates below 3.0.0. A lockfile records the resolved dependency graph, including exact package versions and integrity information.

A range is the maintainer's compatibility declaration, not proof that every allowed update is bug-free. Your tests still need to check your application's behavior. Major-zero ranges have narrower rules, so do not generalize the same upper bound blindly to `^0.x` packages.

For this dependency-free practice package, generate a lockfile from the project directory:

```bash
npm install --package-lock-only --ignore-scripts
```

Inspect `package-lock.json`. It still records the package and lockfile format even though there is no third-party dependency tree. Commit the manifest and lockfile together when creating a real project repository.

## Choose the installation command intentionally

During dependency changes, `npm install` can update the lockfile to satisfy the manifest. In CI, `npm ci` requires a compatible lockfile, installs from it, and fails instead of silently repairing a mismatch. It also removes an existing `node_modules` before installing.

```bash
npm ci --ignore-scripts
npm test
```

The first command should succeed for the dependency-free project. `--ignore-scripts` suppresses package lifecycle scripts for this installation. Some real packages require install-time steps; decide based on your dependencies rather than blindly applying or removing the option everywhere.

Do not commit `node_modules` as a substitute for the lockfile. It contains platform-sensitive generated material and is not the intended portable source of the dependency graph.

## Review changes before accepting them

When considering a package, inspect its purpose, maintenance, license, dependency footprint, and documented runtime support. Check the exact package name before installation. Audit reports can identify known advisories, but an empty report does not certify the package's overall trustworthiness.

Avoid running an automatic force-upgrade command without reading its proposed breaking changes. A secure upgrade that breaks the application's input validation can still produce a bad outcome. Make changes deliberately, review the lockfile diff, and run relevant tests.

## Practice and check

Explain why a CI job should not delete a lockfile to make `npm ci` pass. The correct repair is to reconcile the manifest and lockfile locally, review the intentional dependency change, and commit both. Deleting the record hides the mismatch and gives CI a different graph to resolve.
