# Node.js Streams and Backpressure

Streams process data incrementally. They are useful when loading an entire resource into memory is unnecessary or unsafe. Backpressure lets a slower destination influence how quickly the source supplies more data.

**Prerequisites:** [Files](./1-nodejs-reading-and-writing-files.mdx) and [buffers](./2-nodejs-buffers-and-encoding.mdx). Create `data/source.txt` containing several lines, then save `src/copy.js`.

```javascript
import { createReadStream, createWriteStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';

const source = new URL('../data/source.txt', import.meta.url);
const destination = new URL('../data/copy.txt', import.meta.url);

try {
  await pipeline(
    createReadStream(source),
    createWriteStream(destination, { flags: 'wx' })
  );
  console.log('Copy completed');
} catch (error) {
  console.error(`Copy failed: ${error.message}`);
  process.exitCode = 1;
}
```

Run `node src/copy.js`. Expect a byte-for-byte copy and a success message after the pipeline completes. A second run should fail because exclusive creation refuses to overwrite the destination.

## Let the pipeline coordinate flow

A writable stream may accept data more slowly than the readable source can produce it. The stream protocol signals when producers should wait. `pipeline` connects the streams, handles backpressure between them, and propagates errors through the composed operation.

Avoid manually listening to every data chunk and calling `destination.write(chunk)` without checking its return value. That pattern can keep queuing memory while the destination falls behind. Streaming only helps if your code preserves bounded flow rather than accumulating all chunks in an array.

The high-water mark is a buffering threshold, not a promise of one exact chunk size and not an absolute process-wide memory cap. Application code and transform stages may allocate additional memory.

## Understand partial output

If the source fails after some bytes were written, a destination file can remain partially written. A pipeline rejection tells you the operation failed; it does not automatically undo all filesystem effects. For a robust publish step, write to an application-owned temporary destination and only promote the result after successful completion, with suitable cleanup and platform assumptions.

Do not delete a preexisting file indiscriminately in a catch block. In this example, the destination might have caused an `EEXIST` error precisely because it belonged to an earlier run. Track ownership before removing output.

A pipeline can also accept an abort signal where supported, tying this pattern to the cancellation lesson. Cancellation still has the same partial-output considerations as other failures.

## Practice and check

Compare source and copy bytes with `readFile` in a small verification script and `assert.deepEqual`. Then rename the source and run to a fresh destination. Confirm failure is reported and avoid treating the presence of a file alone as proof of a successful copy. Restore the source before continuing.
