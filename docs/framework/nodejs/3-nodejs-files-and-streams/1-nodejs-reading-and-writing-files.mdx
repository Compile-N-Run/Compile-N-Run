# Node.js Reading and Writing Files

Reading a file and understanding its contents are separate operations. A successful read proves bytes were available, not that they represent the data your application expects.

**Prerequisites:** [Paths and file URLs](./0-nodejs-paths-and-urls.mdx). Create `data/values.json` with `[2,4,6]`, then save `src/files.js`.

```javascript
import { readFile, mkdir, writeFile } from 'node:fs/promises';

const input = new URL('../data/values.json', import.meta.url);
const outputDirectory = new URL('../output/', import.meta.url);
const output = new URL('../output/result.json', import.meta.url);

const values = JSON.parse(await readFile(input, 'utf8'));
if (!Array.isArray(values) || !values.every(Number.isFinite)) {
  throw new TypeError('Expected an array of finite numbers');
}
const total = values.reduce((sum, value) => sum + value, 0);
await mkdir(outputDirectory, { recursive: true });
await writeFile(output, JSON.stringify({ total }, null, 2) + '\n', {
  encoding: 'utf8',
  flag: 'wx'
});
console.log('Created output/result.json');
```

Run `node src/files.js`. The first successful run creates a JSON file containing a total of 12. A second run should fail with an existing-file error because `wx` requests exclusive creation. This is deliberate: the example refuses to overwrite an earlier result.

## Make replacement a conscious decision

The default write behavior can replace a file's contents. Use it only when replacement is intended. Do not check existence first and assume that guarantees safety: another process can change the path between the check and the write. Let the write operation enforce the relevant condition, then handle its error.

For application state that must survive interruption, writing a temporary file and renaming it can improve replacement behavior, but durability and atomicity depend on filesystem and platform details. A simple `writeFile` example is not a transactional database.

Never start overlapping writes to the same file and hope their order matches call order. Await sequential operations or design a single writer. Multiple processes require coordination beyond an in-memory promise chain.

## Handle distinct failures

A missing input, malformed JSON, invalid data shape, and unwritable output are different problems. Report enough context to explain the failed operation. Inspect stable error codes such as `ENOENT` or `EEXIST` when branching on filesystem failures rather than matching English error-message text.

A `readFile` call loads the whole file into memory. That is fine for a small configuration file; it is not a general strategy for arbitrarily large uploads or logs. The streams lesson provides an alternative.

## Practice and solution

Change the JSON input to `[2,"4",6]`. The validator should reject it rather than concatenate a string. Restore the numbers, remove only the generated `output/result.json`, and rerun. Verify the original input remains unchanged and the output ends with a newline for readable command-line inspection.
