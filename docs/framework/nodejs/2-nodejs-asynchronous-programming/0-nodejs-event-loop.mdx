# Node.js Event Loop and Blocking Work

Node can keep many input/output operations in progress while JavaScript handles their results. That does not mean each JavaScript function runs on its own thread. Long synchronous work still prevents the current JavaScript thread from handling other callbacks.

**Prerequisites:** [Functions and module boundaries](../1-nodejs-modules-and-npm/3-nodejs-module-design.mdx). Save the example as `src/order.js`.

```javascript
console.log('A: start');
setTimeout(() => console.log('D: timer'), 0);
Promise.resolve().then(() => console.log('C: promise'));
console.log('B: end');
```

Run `node src/order.js`. For this example, expect A, B, C, D. The synchronous statements complete before the promise reaction runs, and the timer callback runs afterward. A zero-millisecond delay does not mean “interrupt this function immediately.”

## Understand waiting versus computing

When an asynchronous file read is pending, Node can perform other work instead of blocking JavaScript until the file arrives. Depending on the API and operating system, underlying work may use operating-system facilities or a worker pool. It is inaccurate to summarize the whole runtime as having only one thread.

However, a large loop written in JavaScript executes synchronously unless you explicitly move or divide that work. Adding `async` to a function changes how its result is represented; it does not relocate a CPU-heavy loop to another thread.

Add this experiment to a separate file:

```javascript
const started = performance.now();
setTimeout(() => {
  console.log('Timer observed after', Math.round(performance.now() - started), 'ms');
}, 10);

while (performance.now() - started < 100) {
  // Deliberately block for demonstration only.
}
```

The timer cannot run at 10 milliseconds while the loop occupies JavaScript. Expect roughly 100 milliseconds or later, with actual timing depending on the machine. Do not turn this example into a production waiting strategy.

## Avoid brittle ordering assumptions

The relative ordering of timers, immediate callbacks, and input/output callbacks depends on the scheduling context and runtime behavior. Learn the guarantees required by your program rather than memorizing one observed transcript and assuming it covers every environment.

Use promises to express dependencies: operation B should await operation A because it needs A's result, not because a guessed timer delay is probably long enough. For heavy computation, consider a worker thread or a separate process after measuring the problem and accounting for communication costs.

## Practice and check

Move the blocking loop into an `async` function and call it without awaiting. Does the timer suddenly fire sooner? It should not: the loop runs synchronously before the async function can complete. Explain why an `async` keyword alone is not a parallelism tool.
