# Node.js Promises and Async Error Handling

A promise represents an operation's eventual result. `await` pauses the current async function until that result is available; it does not block every other operation in the process.

**Prerequisites:** [Event-loop behavior](./0-nodejs-event-loop.mdx). Create `message.txt` in the project root containing `Workshop ready`, then save this as `src/read-message.js`.

```javascript
import { readFile } from 'node:fs/promises';

async function loadMessage(path) {
  const text = await readFile(path, 'utf8');
  return text.trim();
}

try {
  console.log(await loadMessage('message.txt'));
} catch (error) {
  console.error(`Unable to read the message: ${error.message}`);
  process.exitCode = 1;
}
```

Run from the project root with `node src/read-message.js`. Expect `Workshop ready`. Rename the file temporarily and rerun. The operation should fail, print a diagnostic, and set a nonzero exit status. Restore the file afterward.

## Await inside the intended error boundary

The `try` catches the rejection because it awaits the promise. Calling `loadMessage('missing.txt')` inside a `try` without awaiting does not make a later rejection synchronously catchable there. You must await, return the promise to a caller that handles it, or attach a rejection handler deliberately.

An async function always returns a promise. A returned ordinary value becomes its fulfillment value; a thrown error becomes a rejection. This gives related asynchronous functions a consistent way to propagate failure.

Avoid catching every error and returning an empty string. That makes “the file was empty” indistinguishable from “the file could not be read.” Choose a fallback only when the program's requirements say it is valid.

## Preserve useful context

If a lower-level error needs more application context, wrap it with a cause:

```javascript
async function loadRequiredMessage(path) {
  try {
    return await loadMessage(path);
  } catch (error) {
    throw new Error(`Could not load workshop message from ${path}`, { cause: error });
  }
}
```

At a human-facing command boundary, a concise message may be enough. During debugging, the cause and stack help identify the underlying failure. Do not expose internal paths or stack traces directly to arbitrary HTTP clients when they are not needed.

Finally blocks are useful for cleanup, but their own failures can obscure the original error. Prefer resource APIs that clearly define ownership and ensure one layer is responsible for closing the resource.

## Practice and solution

Call the loader for a nonexistent path and verify that its promise rejects. Then replace the missing-file case with an intentionally empty file. The empty file should succeed with an empty string, while the absent file should fail. This demonstrates that failure and valid empty content remain distinct.
