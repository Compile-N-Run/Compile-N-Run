# Node.js Cancellation and Timeouts

Cancellation is a request that an operation stop. It works only when the operation supports and observes the signal. A timeout that rejects a wrapper promise does not necessarily stop the underlying work.

**Prerequisites:** [Promise coordination](./2-nodejs-concurrency.mdx). Save the following as `src/cancel.js`.

```javascript
import { setTimeout as delay } from 'node:timers/promises';

const controller = new AbortController();
const cancellation = setTimeout(() => controller.abort(), 30);

try {
  await delay(1000, 'finished', { signal: controller.signal });
  console.log('Completed');
} catch (error) {
  if (error.name === 'AbortError') {
    console.log('Canceled before completion');
  } else {
    throw error;
  }
} finally {
  clearTimeout(cancellation);
}
```

Run `node src/cancel.js`. Expect `Canceled before completion`, not `Completed`. The promise-based timer accepts an abort signal and rejects when canceled. The cleanup clears the cancellation timer if the operation has already finished for another reason.

## Use a deadline with a compatible API

Node 22 provides `AbortSignal.timeout(milliseconds)`. For example, the built-in `fetch` accepts a signal:

```javascript
const response = await fetch('http://127.0.0.1:3000/health', {
  signal: AbortSignal.timeout(2000)
});
if (!response.ok) {
  throw new Error(`Health request failed with status ${response.status}`);
}
console.log(await response.json());
```

This fragment requires the local HTTP server from the later [HTTP lesson](../4-nodejs-applications-and-testing/0-nodejs-http-server.mdx). It is not expected to succeed before that server is running. A network failure rejects `fetch`; an HTTP error status such as 404 normally yields a response that you must inspect.

Different APIs and abort causes can produce different error details. The timer example handles its documented `AbortError`; do not assume every timeout everywhere has exactly that name. Preserve unexpected errors rather than labeling every exception as cancellation.

## Respect the limits

An abort cannot roll back a side effect that already happened. Canceling a request after a server accepted a payment does not mean the payment was undone. Real state-changing APIs need explicit business rules and idempotency where appropriate.

A synchronous CPU loop also cannot be interrupted merely by creating a timer that will abort it: the callback cannot run while the loop blocks the JavaScript thread. Long computation needs cooperation, task boundaries, or a worker strategy.
