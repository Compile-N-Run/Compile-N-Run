# Node.js Testing with the Built-in Runner

A useful test fails when an important behavior breaks. Node's built-in test runner and strict assertion module are sufficient for a small dependency-free project.

**Prerequisites:** [Module design](../1-nodejs-modules-and-npm/3-nodejs-module-design.mdx). Keep `src/summarize.js` from that lesson and create a `test` directory.

Save `test/summarize.test.js`:

```javascript
import test from 'node:test';
import assert from 'node:assert/strict';
import { summarize } from '../src/summarize.js';

test('summarizes finite numeric values', () => {
  assert.deepEqual(summarize([2, 4, 6]), {
    count: 3, total: 12, average: 4
  });
});

test('rejects an empty collection', () => {
  assert.throws(() => summarize([]), /nonempty array/);
});

test('rejects strings instead of coercing them', () => {
  assert.throws(() => summarize([2, '4']), TypeError);
});
```

Run `node --test` or the `npm test` script. Expect three passing tests. Temporarily change the total's starting value to 1 and confirm the first test fails; restore the implementation afterward. This check demonstrates that the assertion can detect a meaningful defect.

## Test promises with promise-aware assertions

For asynchronous code, return or await the work inside the test. Use `await assert.rejects(...)` when an operation should reject. `assert.throws` checks synchronous throws and is not the right assertion for a promise that rejects later.

A test that starts an operation without awaiting it can finish before the behavior occurs. Avoid arbitrary sleep delays as synchronization; await the result or a specific event. Timing thresholds can make tests flaky on a busy CI runner.

## Test boundaries as well as functions

The pure function tests do not prove that a CLI parses arguments, emits valid JSON, or exits correctly. A subprocess test can run Node with the CLI path, supply a small fixture, then inspect stdout, stderr, and exit status.

Use temporary directories for files created by tests and clean them up in a finally block or test cleanup hook. Do not make tests overwrite a real user's sample file. The [capstone](./3-nodejs-cli-project.mdx) includes subprocess and local HTTP checks with this separation.

## Keep expectations relevant

Assert structured results rather than an entire platform-dependent stack trace. A stable error type or deliberately public message can be part of your contract. Incidental whitespace, absolute paths, and execution duration usually are not.

Tests should cover normal input, boundary values, malformed data, and important resource failures. They cannot prove the absence of every bug, but clear tests make the supported behavior reviewable.

## Practice and solution

Add a test for negative values, such as `[-2, 2]`. The current contract permits finite negatives, so the correct result is count 2, total 0, average 0. If your application should reject negatives, change the contract explicitly and update both implementation and tests rather than making the test silently redefine the requirements.
